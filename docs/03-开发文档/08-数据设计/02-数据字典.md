# 数据字典(全量 114 表)

> **版本**:v1.10.0  **更新日期**:2026-08-29
> **定位**:系统全部数据表的白话说明书——每张表是干什么的、里面存什么、和谁有关联。
> **适用读者**:新手开发者、接手维护的人员、需要理解数据结构的任何人。**不需要会写代码**也能读懂。
> **数据来源**:与 `backend/app/models/` 源码逐表核对生成;表结构以 Alembic 迁移(`backend/alembic/versions/`)为准。

## 0. 如何读这本字典(2 分钟)

**一句话总结**:把数据库想象成一个装满"Excel 工作簿"的柜子——每张表(worksheet)存一类东西,每一行是一条记录,字典告诉你每张工作簿存什么、哪些格子之间有"引用关系"。

- **表(Table)**:一类东西的集合。比如 `funds` 表存所有经费记录。
- **字段(Column)**:表里的一列。比如经费表里的 `amount`(金额)。
- **外键(FK)**:一张表里指向另一张表的"引用格子"。比如经费表里有 `project_id`,意思是"这笔钱属于哪个项目"——它存的是项目表的编号。**看到 `_id` 结尾的字段,基本就是外键**。
- **主键(PK)**:每行记录的身份证号,通常叫 `id`。
- **关联(Relationship)**:两个表之间"一对多/多对一"的业务关系。经费表里很多行可以指向同一个项目 → 项目对经费是"一对多"。

**状态枚举**:很多字段只允许取几个固定值(比如经费状态只能是"待审/已批准/已拨付…"),这类字段的全部可选值统一收录在 **附录 A**,正文用 `状态: FundStatus` 标注。

**快速找表**:第 1~9 章按业务域组织,先想清楚你要找的东西属于哪个业务(钱?村?用户?数据包?),再看对应章节;也可以直接搜索表名。

## 0.2 全库通用的建模约定(必读)

以下约定适用于几乎所有表,了解后各表的字段说明就不再重复解释:

| 约定 | 白话解释 | 长什么样 |
|------|---------|---------|
| **时间戳** | 每张表自动带"创建时间/更新时间",由 `TimestampMixin` 统一提供 | `created_at`、`updated_at` |
| **增量同步版本号** | 每行数据有个自动递增的"改动次数"。两台电脑之间同步数据时,只传"版本号比上次新的"记录,不用整库拷贝 | `sync_version`(每次 UPDATE 自动 +1) |
| **软删除(两种写法并存)** | 删除不是真把行从表里抹掉,而是打上"已删"标记——这样还能恢复、还能审计 | **旧写法**(帮扶村/学校/项目/经费/政策):`is_active=False` + `deleted_at`;**新写法**(`SoftDeleteMixin`,新模型专用):`is_deleted` + `deleted_at` + `deleted_by` |
| **数据隔离** | 几乎所有业务表都带 `organization_id`(这条数据属于哪个单位)和 `created_by`(谁创建的)。查询时系统按登录人的数据范围自动过滤——A 单位的人看不到 B 单位的数据 | `organization_id`、`created_by` |
| **主键两种风格** | 普通业务表用自增数字 `id`;RBAC 权限那几张表用 36 位随机字符串(UUID)——历史原因,别混用 | `id: Integer` vs `id: String(36)` |
| **金额精度** | 金额一律 `Numeric(15,4)`(4 位小数),不是普通小数,避免精度丢失 | `amount: Numeric(15,4)` |
| **敏感字段加密** | 身份证号等敏感信息入库前经 `EncryptionService` 加密,表里存的是密文 | 字段注释标"加密存储" |

> ⚠️ **命名陷阱速查**(详见《数据库设计总览》"命名陷阱"专节):
> ① `projects.village_id`、`funds.village_id`、`work_logs.village_id` 等字段名虽叫 village,实际指向 **`supported_villages`(帮扶村)**,不是 `villages`(自然村字典);
> ② `villages`(自然村基础信息)与 `supported_villages`(帮扶村主档)是**两套互不关联的表**;
> ③ 少数字段(如 `policies.organization_id`、`school.created_by`)是裸整数,**没有外键约束**,数据库不会帮你校验它指没指对。

## 1. 用户与权限域(16 表)

> **一句话总结**:回答"谁能用系统、能进哪些单位的数据、在哪台电脑上用"。账号存在 `users`,单位树存在 `organizations`,细粒度授权在 `rbac_*` 系列,离线激活靠 `machine_codes`。

### 1.1 User — 用户表 `users`

存系统账号:用户名、密码(加密哈希)、角色、所属单位、数据范围,以及登录安全相关字段。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 用户编号 |
| username | String | 登录名(唯一) |
| hashed_password | String | 密码哈希(绝不存明文) |
| **role** | String | **角色**:super_admin / admin / user / viewer(四选一,见附录 A.0) |
| **organization_id** | FK → organizations | 所属单位(数据隔离的锚点) |
| **data_scope** | String | 数据范围四档:`all`(全部)/`org`(本单位)/`org_children`(本单位及下级)/`self`(仅自己创建的) |
| permission_pack_id | FK → permission_packs | 绑定的权限包(见 §1.11;解析优先级:用户自定义 allowed_menus > 权限包 > 角色默认) |
| allowed_menus / allowed_permissions | JSON | 用户级菜单/权限自定义覆盖 |
| is_active / is_superuser | Boolean | 是否启用 / 是否超管 |
| token_version | Integer | 令牌版本号:登出/改密后 +1,旧登录凭证立即全部失效 |
| must_change_password | Boolean | 首次登录须改密 |
| failed_login_count / locked_until | Integer / DateTime | 连续失败计数 / 锁定截止时间(防暴力破解) |

关联:`organization`(所属单位)、`two_factor_auth`(双因素,1:1)、`projects`(创建的项目,1:N)。

### 1.2 Organization — 组织机构 `organizations`

单位树(军地单位层级),是数据隔离的根。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 单位编号 |
| name / code | String | 单位名称 / 单位编码 |
| **parent_id** | FK → organizations(自引用) | 上级单位。所有单位靠它连成一棵树 |
| org_type | String | department(部门)/ support_unit(帮扶单位)/ other |
| level | String | 层级(level_1 ~ level_5) |
| path | String | 物化路径(整条祖先链,如 `/1/5/12/`,用于"查某单位及全部下级") |
| region_code | String | 行政区划编码(配合帮扶村的辖区前缀匹配) |
| is_active | Boolean | 是否启用 |

关联:`children`/`parent`(上下级,1:N 自引用)、`funds`(单位相关经费)。

### 1.3 UserOrganization — 用户↔单位(多对多) `user_organizations`

一个人在多个单位有身份时用(比如既是 A 单位成员又是 B 单位观察员)。字段:`user_id`(FK→users)、`organization_id`(FK→organizations)、`role`(admin/member/viewer,在该单位内的身份)。唯一约束:(user_id, organization_id)。

### 1.4 ~ 1.9 RBAC 细粒度权限六件套 `rbac_*`

> **一句话总结**:`role` 字段是"粗权限"(决定看哪些菜单),RBAC 六件套是"细权限"(决定某个具体操作允不允许)。全部用 UUID 主键。

| 表 | 用途 | 关键字段 |
|----|------|---------|
| **RbacRole** `rbac_roles` | 角色定义 | name、priority(数字越小权限越高)、is_system(内置角色不可删)、is_active |
| **UserRole** `rbac_user_roles` | 用户↔角色分配 | user_id(FK→users)、role_id(FK→rbac_roles)、granted_by(谁授的)、expires_at(授权到期时间,可做临时授权) |
| **RolePermission** `rbac_role_permissions` | 角色拥有哪些权限标识 | role_id(FK)、permission(权限串,如 `fund:approve`) |
| **UserPermission** `rbac_user_permissions` | 给个人单独授/收某条权限 | user_id(FK)、permission、granted_by、expires_at |
| **ResourceAccessControl** `rbac_resource_access` | 对某个具体资源(某条记录)授权读/写/删 | user_id(FK)、resource_type、resource_id、access_level(read/write/delete) |
| **AccessLog** `rbac_access_logs` | 每次权限判定的留痕(允许/拒绝) | user_id(注意:字符串,无外键约束)、resource、access_granted(是否放行) |

### 1.10 MachineCode / MachineCodePermission — 机器码授权 `machine_codes` / `machine_code_permissions`

> **类比**:机器码 = 这台电脑的"指纹";通行码 = 上级签发的"激活码"。离线环境无法联网验证 license,靠这套机制做硬件级授权。

**MachineCode** `machine_codes`:每台装机电脑一条记录。

| 字段 | 说明 |
|------|------|
| machine_code | 硬件指纹(由 wmic+MAC+主机名 生成) |
| user_id(FK→users) | 绑定哪个账号(machine_binding_required 时该账号只能在这台机器登录) |
| organization_id(FK→organizations) | 属于哪个单位 |
| status | pending(待激活)/ active(已激活)/ revoked(已吊销) |
| pass_code / verification_code | 通行码 / 校验码(上级生成后线下告知下级;下级用通行码注册账号) |
| restrict_permissions | JSON:该机器可用的功能白名单 |
| allow_subordinate_generation | 是否允许这台机器给它的下级再生成通行码(授权链) |

**MachineCodePermission** `machine_code_permissions`:机器码的功能权限明细,`machine_code_id`(FK→machine_codes)、`granted_by`、`expires_at`。

### 1.11 PermissionPack — 权限包 `permission_packs`

> **类比**:预制套餐。把"一组菜单"打包命名(如"驻村工作队基础包"),给同类人员一键套用,不用逐人勾菜单。

字段:name、description、`menu_keys`(JSON:菜单 key 列表,对应前端 menu-config 的 key)、is_active、created_by(FK→users)。**生效优先级**:用户自定义 allowed_menus > 权限包 > 角色默认菜单。

### 1.12 OrgModulePolicy — 组织模块策略 `org_module_policies`

上级对下级单位的"模块开关":该单位能用哪些模块、能编辑还是只读。字段:`organization_id`(裸整数,无 FK)、`module_key`、`visibility`(visible/hidden)、`edit_mode`(full_edit/read_only/disabled)。唯一约束:(organization_id, module_key)。随"管控配置包"下发(见 §7 数据上报域)。

### 1.13 SubordinateInstance — 下级实例注册表 `subordinate_instances`

多机协同的"花名册":上级把每台下级单机系统登记在册。字段:`organization_id`(裸整数)、`machine_code`、`app_version`、`license_status`(pending/active/expired/revoked)、`status`(online/offline/unknown)、`config_package_hash`(下发的配置包指纹)。

### 1.14 TwoFactorAuth — 双因素认证 `two_factor_auth`

用户的 TOTP 动态口令(类似手机验证码App)。字段:`user_id`(FK→users,唯一)、`secret`(加密存储)、`enabled`。开启后登录需要"密码 + 动态码"两道。

### 1.15 TokenBlacklist — 令牌黑名单 `token_blacklist`

已作废的登录凭证名单(登出/改密/被吊销的 token 的 jti)。字段:`user_id`(FK)、`jti`(凭证唯一号)、`reason`(logout/password_change/revoked/expired)、`expires_at`。每次请求都会查这张表,命中即拒绝——保证"登出后旧凭证立刻失效"。

## 2. 帮扶对象与区域域(31 表)

> **一句话总结**:帮扶的"对象"是谁。核心是**帮扶村**(主档 + 11 张年度板块子表),外加第二条帮扶线**学校**,以及自然村的地理基础信息。

### 2.1 SupportedVillage — 帮扶村主档 `supported_villages`(全库第二枢纽)

> **一句话总结**:一个"帮扶对子"= 某个帮扶单位结对帮扶某个村。这张表是村的主档案,村里每年的各类数据分拆在 11 张子表里(按年一村一版)。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | Integer PK | 村编号 |
| village_name | String | 村名 |
| province / city / county / department | String | 省 / 市 / 县 / 所属部门 |
| **organization_id** | FK → organizations | 帮扶单位(谁在帮这个村) |
| created_by | FK → users | 建档人 |
| longitude / latitude | Float | 经纬度(地图落图用) |
| **transition_status** | String | 过渡期状态:none / entering / in_transition / exiting / completed(衔接乡村振兴的阶段) |
| is_revitalization_tier | Boolean | 是否乡村振兴重点帮扶村 |
| **12 个区域标记** | Boolean | is_three_regions(三区三州)、is_key_county(重点县)、is_ethnic_area(民族地区)、is_border_area、is_old_revolution_area、is_poor_county、is_mountain、is_remote、is_limestone(喀斯特)、is_wetland、is_geological_disaster、is_drought —— 多选标记,用于筛选和分类统计 |
| transition_fund_military_total / transition_fund_local_total | Numeric | 过渡期经费军地投入合计(汇总冗余字段,明细在过渡经费接口) |
| **is_active / deleted_at** | Boolean / DateTime | 软删除(旧写法) |

**11 张年度板块子表**(结构统一,都是"村+年份"一行,唯一约束 (supported_village_id, year)):

| 表 | 中文名 | 存什么 |
|----|--------|--------|
| `village_population` | 人口 | 户数、人口、脱贫监测户分类等 |
| `village_income` | 收入 | 村集体收入、人均收入等 |
| `force_investment` | 部队投入 | 出动人次、投入情况 |
| `industry_support` | 产业帮扶 | 产业项目数、产值等 |
| `infrastructure_improvement` | 基础设施 | 道路/饮水/电网等改善 |
| `party_building_support` | 党建帮扶 | 党建活动、结对共建 |
| `medical_support` | 医疗帮扶 | 义诊、医疗设备援助 |
| `consumption_support` | 消费帮扶 | 农产品采购帮销 |
| `employment_support` | 就业帮扶 | 技能培训、岗位输送 |
| `education_support` | 教育帮扶 | 助学、支教 |
| `support_funding` | 帮扶经费(过渡期跟踪) | 按 (村, 年, funding_type) 一行 |

全部子表都有 `supported_village_id`(FK→supported_villages,CASCADE:村删则子数据级联删)和 `year`(Integer),并在主档上以 `population_data`、`income_data` 等关系名反查。

### 2.2 村委会(2 表)

- **VillageCommitteeInfo** `village_committee_info`:村委会年度概况(村+年一行),含本届任期等。
- **VillageCommitteeMember** `village_committee_members`:成员明细。`committee_info_id`(FK→committee_info)、`supported_village_id`(FK)、`name`、`position`(职务)、`is_veteran`(是否退役军人)。

### 2.3 VillageAttachment — 帮扶村附件 `village_attachments`

村相关的照片/文件。`supported_village_id`(FK)、`file_name`、`file_path`、`file_type`、`created_by`(FK→users)。

### 2.4 Village 及其家族(6 表)— 自然村基础信息

> ⚠️ **注意**:`villages`(自然村)与 `supported_villages`(帮扶村)是**两套互不关联的表**。前者是地理/产业基础字典,后者是帮扶业务主档。

| 表 | 用途 | 关键字段/关联 |
|----|------|--------------|
| **Village** `villages` | 村庄地理与经济概况 | organization_id(FK)、region_code、status(active/inactive/developing/completed)、is_active;关联 villagers/industries/tea_plantations/cactus_fruit_plots |
| **Villager** `villagers` | 村民 | village_id(FK→villages)、name、is_poverty(是否脱贫户)、is_household_head |
| **Industry** `industries` | 村庄产业 | village_id(FK)、name、is_featured(是否特色产业) |
| **TeaPlantation** `tea_plantations` | 茶园(贵州特色) | village_id(FK)、面积/品种,含喀斯特品质评估算法字段 |
| **CactusFruitPlot** `cactus_fruit_plots` | 刺梨园(贵州特色) | village_id(FK)、面积/产量,含喀斯特适应性评估字段 |
| **Region** `regions` | 行政区划(省/市/县) | code、name、level(province/prefecture/county)、parent_code(用编码关联的树,无外键)、GeoJSON 边界(地图用) |

### 2.5 School 家族(5 表)— 帮扶学校线

> **一句话总结**:军队"助学兴教"的第二条帮扶线,与帮扶村并列,不强制归属某村。

| 表 | 用途 | 关键字段 |
|----|------|---------|
| **School** `schools` | 学校主档 | name、code;`type`(SchoolType:primary/middle/high/vocational/other);`support_status`(SupportStatus:active 帮扶中/inactive/completed);student_count / teacher_count;support_unit(帮扶单位名)、support_start/end;**is_active + deleted_at 软删**;organization_id(FK→organizations) |
| SchoolAttachment `school_attachments` | 附件 | school_id(FK)、file_name/path |
| SchoolSupport `school_supports` | 帮扶资金流水 | school_id(FK)、amount、support_type |
| SchoolProject `school_projects` | 帮扶项目 | school_id(FK)、name、`phase`(ProjectPhase:research/approval/implementation/acceptance/completed) |
| ScholarshipStudent `scholarship_students` | 受资助学生 | school_id(FK)、name、`status`(ScholarshipStatus:pending/approved/disbursed/completed) |

### 2.6 Annual* 年度统计四表 `annual_*`

较新的年度统计实现(结构与 §2.1 子表同类,均 unique(村,年)):**AnnualIncome** `annual_income`(收入)、**AnnualIndustry** `annual_industry`(产业)、**AnnualInfrastructure** `annual_infrastructure`(基建)、**AnnualPopulation** `annual_population`(人口)。均 `supported_village_id`(FK→supported_villages) + `year`,采用新 `BaseModel` 基类(带 sync_version)。

### 2.7 ReportSubscription — 报表订阅 `report_subscriptions`

定时给某人生成/推送报表。`user_id`(FK→users)、`report_type`、`frequency`(如 weekly)、`output_format`(pdf/excel)、`is_active`。

## 3. 项目与资金域(24 表)

## 4. 审批与流程域(4 表)

> **一句话总结**:一个可配置的"多级签批流水线"。任何模块的重要变更(经费申请、数据修改…)都可以自动送进这条流水线,由配置好的审批人逐级签批,最后把结果"写回"业务数据。

**四张表的关系**:Workflow(流程模板,≤5 级)→ Node(每一级的审批人配置)→ Task(一次具体的待办)→ Record(每一次同意/驳回/转交的留痕)。

| 表 | 用途 | 关键字段 |
|----|------|---------|
| **ApprovalWorkflow** `approval_workflows` | 流程配置(按实体类型) | `entity_type`(如 fund/school/project——哪个模块用这条流程)、name、`is_active`、created_by(FK)。**单机模式下若无活跃流程会自动建一条"单节点默认流程"** |
| **ApprovalNode** `approval_nodes` | 每级的审批人 | workflow_id(FK,CASCADE)、`level`(第几级,1 起)、`approver_type`(user 指定人 / role 指定角色)、approver_id(用户ID或角色ID) |
| **ApprovalTask** `approval_tasks` | 一次待办签批 | workflow_id(FK)、`submitter_id`/`current_approver_id`(FK→users)、`status`(pending/approved/rejected/withdrawn;**approved_apply_failed** = 审批通过但写回业务失败,可重试)、`current_level`(当前第几级)、`original_data`/`change_data`(JSON:改前/改后快照,用于页面"变更对比") |
| **ApprovalRecord** `approval_records` | 签批留痕 | task_id(FK)、`approver_id`/`transfer_to_id`(FK→users,转交时记录转给谁)、`action`(**approve/reject/transfer**)、opinion(意见) |

> 闭环保障:任务全部通过时系统**自动把结果写回业务实体**(如经费 pending→approved);写回失败不静默——任务标成 `approved_apply_failed`,可人工触发重试,保证"批了但没生效"不会永久发生。审批通过/驳回都会给申请人发站内消息。

## 7. 数据上报与同步域(8 表)

> **一句话总结**:系统是"单机离线"的,两台电脑之间不联网,数据靠**加密数据包文件**(U 盘拷贝)传递。这组表管理"包的一生":生成→加密→导出→接收→校验→导入,以及围绕包的一次"报送-签收-审批"(上报单)。

**两种包**:Task(任务包,上级→下级,下发任务和数据)/ Report(上报包,下级→上级,报送成果)。

| 表 | 用途 | 关键字段 |
|----|------|---------|
| **DataPackage** `data_packages` | 数据包档案 | `org_id`(FK→organizations)、`type`(**task 任务包/report 上报包**)、`status`(**draft→pending→validated→imported**,或 failed/cancelled)、file_name/file_path、checksum(SHA256 校验和)、**加密四件套**(is_encrypted、algorithm=AES-256-GCM、salt、iterations=PBKDF2 轮数)、created_by/imported_by(FK) |
| **DataReport** `data_reports` | 上报单(围绕包的业务流程) | package_id(FK→data_packages)、`source_org_id`/`target_org_id`(FK→organizations,谁报给谁)、`status`(**draft→submitted→approved/rejected/cancelled**)、submitted_by/reviewed_by(FK)、deadline |
| PackageVersion `package_versions` | 包的版本管理 | package_id(FK)、version、file 快照、created_by(FK) |
| **ImportExportHistory** `import_export_history` | 包操作审计 | package_id(FK)、org_id(FK)、`operation_type`(export/import/preview/validate/confirm/cancel/delete)、`result`(success/failed/partial)、user_id(FK)、error_message |
| ImportHistory `import_histories` | Excel 批量导入历史(普通 Excel,非加密包) | user_id(FK)、`import_mode`(incremental 增量/full 全量)、`status`(pending/processing/completed/failed)、成功/失败行数 |
| ExportTask `export_tasks` | 异步导出任务(大文件后台生成) | user_id(FK)、task_id(UUID)、`status`(pending/processing/completed/failed/expired)、file_path、expires_at |
| **DataSyncLog** `data_sync_logs` | .rrs 增量同步包日志 | user_id(FK)、`sync_type`(export/import)、`status`(pending/processing/completed/failed)、`conflict_strategy`(skip/overwrite/merge/manual)、记录数统计 |
| **DataConflict** `data_conflicts` | 同步冲突清单 | sync_log_id(FK→data_sync_logs)、`conflict_type`(duplicate/modified/deleted)、`resolution`(keep_local/use_import/merge/skip)、resolved |

> **增量同步原理**(小白版):每行数据都有 `sync_version`(改动一次 +1)。导出增量包 = 把"版本号大于上次同步点"的行打包;导入时按 ID 存在与否决定新增/更新(**保留原 ID**,避免外键变孤儿)。详见《需求规格说明书》流程四。
