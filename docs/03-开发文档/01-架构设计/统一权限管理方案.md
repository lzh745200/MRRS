## 0. 先说结论：不要另起一套

系统里已经有一套相当完整的权限积木，缺的不是"再造一层"，而是**把三层积木接到同一根轴上**。
盘点如下（都已在生产代码里跑着）：

| 能力 | 现有实现 | 位置 |
|---|---|---|
| 权限目录（页面清单） | `MENU_DEFINITIONS`：扁平条目 + `children` + `tabs`，`kind` 分 `page`/`group` | `app/api/v1/menus.py:69` |
| 菜单可见性解析 | `_get_user_accessible_menu_keys`：用户白名单 > 权限包 > 角色默认，再并公开项 | `app/api/v1/menus.py:1367` |

| 前端按钮级指令 | `v-permission` 四种模式：角色数组 / 权限码 / `{menu}` / `{module,level}` | `frontend/src/directives/permission.ts` |
| 前端模块权限表 | `authStore.modulePermissions`：由 `permissions` 码推导 `{module:{view,edit}}` | `frontend/src/stores/auth.ts:74` |

**四个真实缺口**（本方案要补的）：

| 编号 | 缺口 | 后果 |
|---|---|---|
| G1 | `check_permission` 只经 `POST /rbac/check`（`auth/rbac.py:120`）查询暴露；`permission_utils.require_permission`（`:359`）虽是装饰器却**零路由使用**，**没有任何路由依赖** | 按钮级权限只靠前端 `v-permission` 隐藏；绕过前端直接调接口不受限 |
| G2 | `PERMISSION_OPTIONS` 是 17 条**扁平静态码**，与菜单树无关联 | 勾选界面无法表达"这个页面下有哪些按钮" |
| G3 | `/users/form-options` 返回角色/数据范围/权限码/组织树，**不返回菜单树** | 账户创建界面拿不到页面清单，只能另调 `/menus/all` 自行拼装 |
| G4 | 无"权限版本号"，`authStore.user.permissions` 登录后不再刷新（菜单只在首次导航时 `fetchMenus`） | 管理员改了某人权限，该用户不重新登录就看不到变化 |

### 0.1 必须先解决的既有债务：三套命名空间

这是本方案最容易翻车的地方，**先摆事实**（都已核对过代码）：

| 命名空间 | 形态 | 证据 |
|---|---|---|
| 菜单 key（`MENU_DEFINITIONS`） | **复数**：`villages` / `projects` / `funds` / `schools` / `rural-works` | `app/api/v1/menus.py:69` |
| 写守卫 module（`write_route_map`） | **复数，但包含 32 个无导航页的后端模块**：`villages` / `projects` / `funds` / `users-orgs` / `roles` / `audit` | `app/core/write_route_map.py:46-138` |
| 按钮码前缀（`PERMISSION_OPTIONS`） | **单数**：`village:manage` / `project:manage` / `fund:manage` | `app/api/v1/auth/users.py:59-61` |

也就是说：**页面与模块不是同一套 key**。模块 key 是页面 key 的超集，另有 32 个
只有写接口、没有导航页的模块；按钮码前缀则混有单数历史码。三者必须靠目录归一。

**结论（本方案强制约定）**：

1. **页面 key ⊂ 模块 key**（v1.3 修正，见 §0.3-F1）：`module_key` 是 page key 的**超集** ——
   **54 个可导航动作页**（48 page + 6 console）之外还有 **32 个纯后端模块**
   （`analytics`/`audit`/`backup`/`users-orgs`/`organizations`/`roles`…）。
   另有 15 个 `kind=page` 的 legacy key 没有 path，只能当历史权限 key，不能当动作页面。
   因此动作码分**两层**：
   - 页面级 `<page_key>:<action>`：可在勾选界面渲染；
   - 模块级 `<module_key>:<action>`：只供后端接口判定，UI 不渲染。
   两层共用同一套 action 枚举，`all_codes` 是二者并集。
2. 动作码写作 `<key>:<action>`，`key` 一律**复数**（页面或模块）；
3. 现有 17 条单数码作为 **legacy 别名**保留，用一张显式映射表过渡（见 §1.2），
   **不允许**再新增单数前缀的码；
4. 前端 `PermissionTreePanel.vue` 历史上写的是**单数**前缀（`village:read`），
   故必须提供 **单数 → 复数** 的前缀别名（见 §0.3-F3），否则存量 RBAC 行会被判为未知码。
5. §2.5 不能再写 `pages ∩ modules`：`dashboard`、`bigscreen` 等只读页面没有写模块，
   会被交集误删。**页面可见性只由 L1 决定**；L2 仅对“存在 module 的页面”追加可写判定，
   没有 module 的页面按只读处理。


> 若不先钉死这条，动作码前缀（`village`）与菜单 key（`villages`）永远对不上。

**v1.3 补充（核验后精确表述）**：前端 `v-permission` 的模式 4
（`{ module, level }`）**要求 `module` 与 `level` 两个键同时存在**，少一个会落到
`permission.ts:75-82` 的 fail-closed 分支（直接隐藏），而不是"匹配不到"。它查的是
`authStore.modulePermissions`（`frontend/src/stores/auth.ts:74-104`），而该表是按
**权限码 `:` 前的部分**（`parts[0]`）建键的 —— 所以现有模式 4 写的是**单数**
`{ module: 'village' }`，对**存量单数码**恰好能匹配。一旦动作码切到复数 `villages:write`，
**必须同步把模式 4 的 `module` 改成复数**，否则同一批按钮会从"可见"变成"被隐藏"。
这条是切换动作码时最容易漏的连带改动，必须与 §1.2 的别名切换同批完成。

## 1. 权限粒度划分策略

采用**三级、单向收窄**的结构：页面可见 ⊃ 模块可写 ⊃ 动作可执行。
上一级不通过，下一级无意义；下一级勾选不能扩大上一级。

### 1.1 三级定义

| 级别 | 标识 | 语义 | 存储位置 | 裁决函数 |
|---|---|---|---|---|
| **L1 页面级** | `menu_key`（与 `MENU_DEFINITIONS` 同源） | 左侧导航是否出现、路由是否放行 | `users.allowed_menus` / `permission_packs.menu_keys` | `_get_user_accessible_menu_keys` |
| **L2 模块级** | `module_key`（页面 key 或纯后端模块 key） | 该模块只读还是可写 | `org_grants.level` / `permission_packs.grants` | `GrantMatrix.can_view/can_edit` |
| **L3 动作级** | `<module>:<action>` | 具体按钮（新建/编辑/删除/导出/审批…） | `users.allowed_permissions` | 既有 `require_permission`（`permission_utils.py:359`），本方案把它**改造为路由依赖**（§4.2） |

> **为什么 L2 与 L1 分开**：`org_grants` 已经以模块为粒度、按组织树继承；页面级用菜单 key
> 是为了能表达"只给看某一个子页面"。两者不是重复，而是"导航可见性"与"数据写入权"的分离 ——
> 这也是现有 `grant_guard` 的既有语义，不要合并。

### 1.2 动作码命名规范

```
<page_key>:<action>        # page_key 一律复数，与 MENU_DEFINITIONS 一致
```

`action` 只允许以下枚举（新增需在本表登记，避免各写各的）：

| action | 含义 | 典型按钮 | 前端 `modulePermissions` 可推导？ |
|---|---|---|---|
| `read` | 查看详情（列表已由 L1 控制，这里指详情/弹窗） | 查看 | ✅ → `view=true` |
| `write` | 写入（新建/修改/导入等所有变更） | 新增、编辑、启用/停用、导入 | ✅ → `edit=true` |
| `delete` | 删除（含软删） | 删除、批量删除 | ✅ → `edit=true` |
| `manage_roles` | 角色/授权管理 | 分配角色、分配权限 | ✅ → `edit=true` |
| ~~`create`~~ | ~~新建~~ | — | ❌（前端不认识，会推导出 `view=false, edit=false`） |
| ~~`update`~~ | ~~修改~~ | — | ❌ 同上 |
| ~~`export`~~ | ~~导出/下载~~ | — | ❌ 同上 |
| ~~`import`~~ | ~~导入/上传~~ | — | ❌ 同上 |
| ~~`approve`~~ | ~~审批处理~~ | — | ❌ 同上 |
| ~~`assign`~~ | ~~分配/授权~~ | — | ❌ 同上 |

> **v1.2 结论**：上表后 6 行是 v1.1 提出、但与前端**不兼容**的枚举，已划掉。
> 落地时只允许前 4 个 action；若确需区分"新建"与"修改"，**必须同时**扩展
> `authStore.modulePermissions` 的映射（见下方更正说明），否则按钮会被 fail-closed 隐藏。
> 把 `export` / `import` 这类"是否显示导出按钮"的需求，落到 `write` 或独立的
> **页面级** 能力（而不是动作码），是更省事的做法。

示例（**收窄后的枚举**，见下方 v1.2 更正）：`villages:write`、`funds:read`、`users:delete`。

> **v1.2 重要更正（动作枚举与前端词汇必须同时改）**：v1.1 的 `action` 枚举与**前端现有
> 推导逻辑不兼容**。`authStore.modulePermissions`（`frontend/src/stores/auth.ts:74-104`）
> 目前只认识四类 action 后缀：
>
> ```js
> if (action === 'read')            module.view = true
> if (action === 'write' | 'delete' | 'manage_roles')  module.edit = true
> ```
>
> 也就是说，若按 v1.1 的枚举落到 `villages:create` / `villages:export` / `villages:approve`，
> 前端**只会得到 `view=false, edit=false`**，模式 4 的按钮会被全部隐藏 —— 表现为
> "明明勾了权限，按钮却不见了"。落地时**必须二选一并同批完成**：
>
> 1. **收窄枚举**到前端已认识的 `read / write / delete / manage_roles`（推荐，改动最小）；
>    或
> 2. **扩展前端映射**，把 `create/update/export/import/approve/assign` 显式映射到
>    `view` / `edit`，并与 §1.3 的门禁同步。
>
> 本方案其余章节示例按**收窄后的枚举**书写（`read` / `write` / `delete`）。

- `permission_packs` 是"模板"（可批量套用），`allowed_*` 是"实例"（可个性化），

- 审计需求由 `AuditLogger` + `write_work_log` + `rbac_access_logs` 承担，不需要额外的关联表来记录历史。

### 2.3 唯一新增列：`users.permissions_version`

```python
# app/models/user.py
permissions_version = Column(Integer, nullable=False, default=0, server_default="0",
                             comment="权限版本号：任何权限相关字段变更时 +1，供客户端即时刷新")
```

迁移：`alembic/versions/user_permissions_version_001.py`（`ADD COLUMN ... DEFAULT 0 NOT NULL`，
SQLite 支持 `ADD COLUMN` 带默认值；需按仓库约定附"能手工构造旧库状态"的自证测试）。

**为什么要它**：G4 的根因是客户端把 `user.permissions` 缓存在内存里，登录后不再取。
有了版本号，服务端在任何响应里带一个 `X-Perm-Version` 头，客户端一比就知道该刷新，
**不需要轮询、也不需要用户重新登录**。

**必须在哪些地方自增**（漏一处就有一条路径不生效，这是本节最容易做漏的点）：

> **v1.2 提示**：下表列出的**每一个写点目前都没有版本号自增**（grep 全仓无
> `permissions_version`）。所以本表是**待实施清单**，不是现状描述。实现时建议在
> `resolve()` 之外单独提供一个 `bump_permissions_version(db, user)` 纯函数，让各写点
> 只调用它 —— 避免在 8 个入口各写一遍 `user.permissions_version = (user.permissions_version or 0) + 1`，
> 那样漏改的概率和 §2.3 描述的一样高。

| 变更入口 | 实际位置 |
|---|---|
| 创建账户 / 更新账户 / 权限分配 | `app/api/v1/auth/users.py`：`POST /users`（`:704-817`）、`PUT /users/{user_id}`（`:821`）、`PUT /users/{user_id}/permissions`（`:939-1018`） |
| 设置菜单权限 | `app/api/v1/menus.py:1606`（`set_user_menu_config`） |
| 角色授予 / 撤销 | `app/services/rbac_service.py`：`assign_role`（`:350`）、`revoke_role`（`:394`） |
| 角色变更 / 角色权限变更 | `rbac_service.py`：`create_role`（`:623`）、`grant_permission`（`:405`）、`grant_permissions_batch`（`:438`）、`revoke_permission`（`:488`） |
| 权限包绑定变更 | `users.permission_pack_id` 的写入点 |
| 权限包导入 | `app/services/permission_package_service.py`：`confirm_import`（`:510`）、`_import_user_legacy`（`:990`，写 `allowed_menus` 于 `:963-977`） |
| 离线账号包导入 | `app/services/account_package_service.py`：`allowed_menus` 写入（`:220`）、导入调用（`:353`） |
| 单位授权矩阵变更 | **不刷用户**：`org.grant_version` 已由 `app/api/v1/org_grants.py:223/241/300/349/416` 递增，直接参与复合版本串（见下） |

> 注意 `role`、`data_scope`、`is_active` 变更**同样要 bump** —— 它们影响的是"能看到哪些数据"
> 和"能不能登录"，不只影响按钮。漏掉这几个字段，会出现"权限改了、数据范围没刷新"的半更新状态。


> **单位矩阵那一条要特别处理**：矩阵是**单位级**的，改一次影响该单位所有用户。
> 但**不能用 `max(user.permissions_version, org.grant_version)`** —— 两个计数器
> 各自独立递增、量纲不同，会漏刷新。反例：用户版本 5、单位版本 100，响应头取 100；
> 之后该用户权限变更（版本 6），响应头仍是 100，客户端认为没变 → 不刷新。
>
> **正确做法：复合版本串**
>
> ```python
> header = f"{user.permissions_version}.{org.grant_version or 0}"
> ```
>
> 客户端只做字符串不等比较；任一维变化都会变。单位级变更无需逐个用户刷库，
> 也不需要额外列。若担心可读性，也可发两个独立头
> （`X-Perm-Version` + `X-Grant-Version`），但**不要合并成一个数字**。

### 2.5 有效权限的合并顺序（唯一算法）

```
1. base     = 角色权限集合（rbac_service.get_user_permissions，rbac_service.py:260）
2. if ADMIN_ALL in base: base = ALL_ACTION_CODES
3. if user.allowed_permissions 非空: base &= allowed_permissions      # 只收窄
4. base    -= 机器码受限动作   （rbac_service._get_cached_restricted_permissions:247）
5. modules = 单位矩阵 ∩ 权限包 grants（深者优先、deny 不被浅层翻回）
6. pages   = _get_user_accessible_menu_keys()      # 页面可见性只由 L1 决定，不交 modules
7. base    &= {code for code in base
               if code.split(":")[0] in modules or code.split(":")[0] in pages}
8. 组织模块策略 read_only → modules 降为 view，并扣掉非 read 动作；
   disabled → 从 pages / modules / actions 一并移除
9. actions  = base ∪ legacy 别名展开（见 §1.2，仅读路径）
```

第 5-6 步的 `modules` 与 `pages` **不是同一集合**：`modules` 有 32 个无页面的后端模块，
`pages` 有 `dashboard`/`bigscreen` 等无写模块的只读页。因此不能让 `pages` 与
`modules` 取交集；L1 决定页面是否可见，L2 只对存在的模块追加 edit 上限。

第 7 步是关键补充：**动作权限不能越过模块级授权**。若模块存在，动作前缀必须在
`modules` 内；若页面没有对应模块，只允许其页面级 read。否则"单位只给了 view，
但用户白名单里有 `villages:delete`"就会形成可删不可写的矛盾状态
（现有实现里 `allowed_permissions` 只与角色权限取交集，**没有与单位矩阵取交集**，
这是本次要补的口子）。

第 9 步的别名展开只在**读**路径发生，写入永远落新码（见 §1.2 双读单写）。

#### 2.5.1 菜单可见性的真实分支（**v1.2 据实补全，v1.1 漏掉了最关键的一条**）

`_get_user_accessible_menu_keys`（`app/api/v1/menus.py:1367`）**不是一个统一的"取交集"**，
而是**两条互斥分支**，文档若只写 §2.5 第 6 步会误导实现者：

```python
def _get_user_accessible_menu_keys(db, user):
    if _is_superuser(user):
        return _flatten_menu_keys(MENU_DEFINITIONS)        # 超管全量

    matrix = get_grant_matrix(db, user)
    if matrix.active:                                       # ── 分支 A：矩阵生效
        keys = matrix.visible_keys()                        # 不并 _PUBLIC_ACCESS_KEYS
        keys.add(_DASHBOARD_MENU_KEY)                       # dashboard 恒定可见
        keys &= set(user.allowed_menus_list or [])          # 用户级只能收窄
        keys.add(_DASHBOARD_MENU_KEY)
        return keys
                                                            # ── 分支 B：矩阵未生效
    keys = allowed_menus_list or []                         # 用户白名单优先
    if not keys and pack:
        keys = pack.menu_keys                              # 绑定权限包
    if not keys:
        keys = _get_role_default_menu_keys(user.role)      # 角色默认
    keys |= _PUBLIC_ACCESS_KEYS                             # 最后并公开项
    return keys
```

**分支 A 的两条强约束（实现时最容易做漏，必须写进 `resolve()`）**：

1. **矩阵生效时不并 `_PUBLIC_ACCESS_KEYS`**（`menus.py:1381-1399`）。
   理由：上级单位"收掉数据分析"的意图不能被强制公开项抵消 —— 否则上级收不干净。
   代码注释原话：「否则上级'收掉数据分析'的意图会被强制公开项抵消」。
2. **矩阵生效时用户级 `allowed_menus` 只收窄不放宽**（`keys &= set(allowed)`）。
   理由：防下级管理员用 `allowed_menus` 绕过上级授权。
3. **`dashboard` 在两条分支里都恒定可见**（`_DASHBOARD_MENU_KEY = "dashboard"`，`menus.py:1350`）。
   理由（代码注释原话）：「单位授权矩阵生效时也恒定可见，否则被授权单位登录即白屏」。

**分支 B 的 `_PUBLIC_ACCESS_KEYS`**（`menus.py:1356`）：
`policies`、`helpData`、`data-analysis`、`analytics`、`analytics-dashboard`、`analytics-map`、`work-analysis`。

> 这三条是**既有实现的硬约束**，不是本方案新增。v1.1 把它们漏掉，会直接导致
> `resolve()` 算出的 `pages` 与 `_get_user_accessible_menu_keys()` 的**实际返回不一致** ——
> 表现为"菜单显示了但按钮没有"或"菜单被收掉了"的静默错位。

第 5-7 步已在 `menus.py` 与 `grant_guard.py` 里实现，方案只要求**把它们收口到一个函数**
（见 §4.1），避免菜单侧与写守卫侧各算一遍、结论不一致（历史上出过这种不一致）。
`grant_guard` 这一侧**已经**额外叠加了组织模块策略（R48 阶段 4，
`app/middleware/org_module_policy_gate.py`），所以第 8 步在写守卫上是**已实现**的，
`resolve()` 必须把同一策略也纳入，否则菜单侧与写守卫侧结论不一致。

### 3.2 三种勾选态与"来源"标识

### 3.3 动作面板的联动规则

- 选中某页面 → 右侧列出该页面的动作（数据来自 `MENU_ACTION_INDEX`，见 §1.3）；
- 页面未选 → 动作面板整体禁用（页面都进不去，给按钮权限没有意义）；
- 模块 `level=view`（单位只给只读）→ 动作里只保留 `read`，其余置灰；
- 勾选任一写动作 → 自动勾上 `read`（隐含依赖，避免"能删不能看"的畸形组合）；
- 全不勾 → 写入 `allowed_permissions = []`（明确"无动作权限"，而非继承）。

### 3.4 批量授权

两个层次，都复用现有结构：

1. **模板批量**（推荐日常用）：先建权限包（勾选一套页面 + 动作），创建账户时选包，
   或对多个已有账户批量套用；
2. **直选批量**：勾选多个账户 → 「批量设置权限」→ 弹出同一套勾选界面 →
   选择覆盖模式（**覆盖** / **取交集** / **取并集**，默认取交集，符合"只收窄"铁律）。

批量接口见 §4.4。

### 3.5 实时预览

底部统计随勾选实时变化：`可见 N 页 / 可写 M 模块 / K 个操作`。
保存前调用一次 `POST /users/permission-preview`（见 §4.3）做服务端复核，
若与前端算出的不一致（例如单位矩阵刚变），以服务端为准并提示差异 —— 避免"看着能勾、存了不生效"。

## 4. 后端接口层的校验实现

### 4.1 单一裁决点：`effective_permission_service`

新增 `app/services/effective_permission_service.py`，对外只暴露一个数据结构：

```python
@dataclass(frozen=True)
class EffectivePermissions:
    pages: set[str]                    # 可见页面 key
    modules: dict[str, str]            # module_key -> "view" | "edit"
    actions: set[str]                  # 可执行动作码
    denied: dict[str, str]             # key -> 拒绝原因（machine/org_grant/org_policy/role）
    version: int                       # = user.permissions_version

def resolve(db, user) -> EffectivePermissions: ...
```

内部按 §2.5 的九步合并，复用 `get_grant_matrix` / `_get_user_accessible_menu_keys` /
`rbac_service.get_user_permissions`。**所有调用方（菜单下发、写守卫、动作守卫、账户预览）
都走它**，禁止各处自行拼装。

#### 4.1.1 两级缓存（否则每请求多 6-10 次查询）

`resolve()` 的原始成本：组织链逐级查询（树深 3-5 层）+ 角色权限 + 权限包 + 用户行，
一次约 6-10 次 SQL。不加缓存，等于给**每个已认证请求**都加一遍。

| 级别 | 载体 | 键 | 生命周期 |
|---|---|---|---|
| 请求内 | `request.state.effective` | 一次请求 | 请求结束即弃 |
| 进程内 | 模块级 dict（上限 512，触顶整体清空，与 `effective_grant_service._CACHE` 同风格） | `(user_id, user.permissions_version, org_id, org.grant_version)` | 直到版本号变化 |

版本号参与键，**不需要显式失效**（旧 entry 自然不再命中）；但用户删除/组织迁移时
要调一次 `clear_cache()`，避免脏 entry 长期驻留。

#### 4.1.2 与 `grant_guard` 的重复解析（必须收口）

现状：`grant_guard` 作为 app 级依赖，**自己开 `SessionLocal`、自己解 token、自己算矩阵**
（`grant_guard.py:110-124`）。如果动作守卫再算一遍，同一请求就有两次用户查询 + 两次矩阵解析，
既浪费又有"两边结论不一致"的风险。

> **v1.2 据实补充（现状比 v1.1 描述的还多一层）**：`enforce_write_grant` 除了自开
> `SessionLocal`（`grant_guard.py:114`）自解 token（`:116`）自算矩阵（`:119`）之外，
> **已经额外叠加了组织模块策略**（R48 阶段 4）——
> `evaluate_org_policy(db, user, module)`（`app/middleware/org_module_policy_gate.py`），
> 非空即 `_deny("org_policy:...")`（`grant_guard.py:126`）。默认 `off` 时不走这条，
> 但它是**已实现的语义**。
>
> 含义：`resolve()` **必须把组织模块策略一并纳入**，否则菜单侧与写守卫侧的结论
> 会在这一层再次分叉 —— 表现就是"菜单隐藏了、按钮也点不动（更严）"或
> "菜单可见、按钮被拒（更松）"两种静默错位。

收口方案：新增一个轻量中间件（或复用现有认证中间件），在**认证完成后**解析一次
`EffectivePermissions` 存入 `request.state.effective`：

- `require_permission` 直接读 `request.state.effective`（无则现算）；
- `grant_guard` 改为优先读 `request.state`，读不到再走原有兜底逻辑
  （它是 app 级依赖，执行早于路由依赖，需要保留兜底路径）；
- 两者都只做"读"，不做缓存写入竞争。

> 这一步不做的话，性能问题和"两套结论"问题会同时存在，且很难在上线后才发现。

> **v1.2 补充**：`grant_guard` 的模块 docstring 明确**故意不用 `Depends(get_current_user)`**，
> 而是在函数体内惰性解析用户（避免每个请求都多一次依赖解析开销），并且 `off` 模式
> 零开销、零行为变化。收口时**不要为了"统一"而牺牲这条**：`grant_guard` 保留自己的
> 惰性解析 + 兜底路径，只是把"算矩阵"换成"读 `request.state.effective`"（读不到才自算）。


### 4.2 动作级依赖：`require_permission`

> **v1.2 重要更正：`require_permission` 已经存在，不要新增第二份。**
> `app/core/permission_utils.py:359` 已有**装饰器形式**的 `require_permission`：
> 内部用 `permission.partition(":")` 拆 resource/action 后调 `check_permission`
> （`permission_utils.py:402`）。历史缺陷是"整串当 resource"会拼出尾冒号导致恒 403，**已修复**。
>
> 但它**没有任何路由实际使用**（仅单测引用）——这正是 G1 缺口的另一半。
> 本方案**不新增第二个同名函数**，而是：
>
> 1. 保留 `permission_utils.require_permission` 作为**唯一实现**；
> 2. 在 `app/api/v1/deps.py` 只加一个**薄包装**，把它适配成 FastAPI 依赖
>    （带 `request`，以便读 `request.state.effective` 与写审计）；
> 3. 所有调用点统一用依赖形式，装饰器形式保留给非路由场景（如服务层内部校验）。

```python
# app/api/v1/deps.py —— 薄包装，不是新实现
def require_permission(code: str, *, mode: str | None = None):
    """声明式动作守卫。未授权 → 403，detail 带可读原因。"""
    def _dep(request: Request, current_user=Depends(get_current_user), db: Session = Depends(get_db)):
        eff = get_effective_permissions(request, db, current_user)   # 请求内缓存
        if code in eff.actions:
            return
        reason = eff.denied.get(code.split(":")[0], "no_permission")
        _deny_or_log(mode, request, code, reason)                    # shadow 只记日志
    return _dep
```

用法（示例，改造 `villages` 模块；注意是复数，见 §0.1）：

```python
@router.post("", dependencies=[Depends(require_permission("villages:write"))])
async def create_village(...): ...

@router.delete("/{village_id}", dependencies=[Depends(require_permission("villages:delete"))])
async def delete_village(...): ...
```

**配套门禁（否则永远有接口"忘了声明"）**

新增 `scripts/check_action_coverage.py`（挂 `static-analysis`）：

1. 遍历运行时路由表，取出所有写方法（POST/PUT/PATCH/DELETE）的接口；
2. 排除豁免清单（登录、匿名反馈、健康探针、授权包自举 —— 与 `write_route_map.EXEMPT_PREFIXES` 同源）；
3. 断言每个写接口的依赖里含 `require_permission(...)`，否则**列入基线并禁止新增**
   （棘轮模式：基线只减不增，与 `.type-debt-baseline.json` 同思路）；
4. 断言声明的动作码都在 `ALL_ACTION_CODES` 内（防止拼错成 `villages:creat` 后静默失效）。

> 为什么必须棘轮而不是一次清零：现存写接口数百个，一次补齐不现实；
> 但"新增接口必须有动作码"这条从第一天就能守住，否则新接口会持续稀释覆盖率。

**legacy 双读（§1.2 的落地）**：`require_permission` 内部判定为

```python
def _allowed(code, eff):
    if code in eff.actions:
        return True
    return any(expand(alias) 包含 code for alias in eff.actions if alias in LEGACY_ACTION_ALIAS)
```

这样端点改判新码后，只持有 `data:create` 的存量用户**不会**立刻 403。


**与 `grant_guard` 的分工**（重要，别重复实现）：

| 守卫 | 粒度 | 覆盖方式 | 什么时候用 |
|---|---|---|---|
| `enforce_write_grant`（已有） | 模块级（edit/none） | **全局兜底**，app 级依赖，URL 前缀映射 | 保留兜底语义，但改为优先复用 `request.state.effective`（§4.1.2），避免重复解析 |
| `require_permission`（新增） | 动作级 | **逐接口显式声明** | 需要区分"能改但不能删"这类细粒度时 |

两者同时生效时取**更严者**：动作守卫 403 直接返回；模块守卫在 app 级先跑。
`GRANT_GUARD_MODE=off` 时动作守卫仍独立工作（它不依赖矩阵是否 active）。

### 4.3 账户创建/编辑接口的收口

**现状（必须先说清，否则"同一界面勾选"落不了地）**：权限字段分在两个接口里 ——

| 字段 | 写入接口 | 实际位置与说明 |
|---|---|---|
| `allowed_permissions` | `POST /users`（schema 名 **`UserCreateBody`**）、`PUT /users/{user_id}/permissions` | `users.py:92` / `:110`；schema 里是 **JSON 数组字符串**（`Optional[str]`），另有历史遗留的 `permissions` **逗号分隔**字段，`POST /users` 会把它转成 JSON（`users.py:778-785`） |
| `allowed_menus` | **`PUT /menus/user-menus/{user_id}`**（`menus.py:1552`） | 页面 key；`UserCreateBody`（`users.py:92`）里**没有**这个字段 |

也就是说：现在"建账户 + 配权限"至少要两次请求，第二次失败就留下一个**半配账户**
（有动作权限、没有页面权限），现场很难发现。这是本方案必须收口的点。

> **v1.2 据实修正：收口的工作量比 v1.1 估计的小一半，但有一个必须修的隐患。**
>
> - **服务层已具备**：`user_service.create_user` 已有 `allowed_menus: Optional[list]` 参数
>   （`user_service.py:136`），`:176-177` 会按 `_iter_definition_keys()` 过滤后 `json.dumps`，
>   `:194` 写入 `User(...)`。所以收口只需补 **API schema 与调用**，不必改服务层。
> - **但 `POST /users` 目前并不走 `user_service.create_user`**：它直接在
>   `users.py:788-802` 构造 `User(...)` 落库，因此**没有** `allowed_menus` 的过滤逻辑、
>   也没有 `create_user` 里已有的其他校验。这是一个**真实的可维护性隐患** ——
>   两条创建路径（`user_service.create_user` 与 `POST /users` 内联构造）会各自漂移。
>   收口时**必须把 `POST /users` 改为调用 `user_service.create_user`**（或把内联逻辑
>   抽成公共函数），否则"服务层已支持 `allowed_menus`"这句话对 `POST /users` 这条路径
>   是**不成立的**。
> - **`UserUpdateBody`（`users.py:124`）没有任何权限字段**，所以"编辑账户时调权限"
>   实际全部走 `PUT /users/{user_id}/permissions`（`users.py:939-1018`）。该接口目前
>   **无权限越界校验、无 `permissions_version` 自增**。

**改造（推荐）**：

1. `UserCreateBody` / `UserUpdateBody` 增加 `allowed_menus: Optional[list[str]]`；
   `POST /users` **改为调用 `user_service.create_user`**，在同一事务里写
   `allowed_menus` 与 `allowed_permissions`，避免半配；
2. 把 `set_user_menu_config` 里已有的校验抽成公共函数复用（不要复制）：
   - key 必须在 `_iter_definition_keys()` 内（否则 400 并列出无效 key）；
   - 目标用户必须在调用者组织子树内（`_assert_menu_config_target_allowed`，`menus.py:1532`）；
   - 不允许改自己（防管理员锁死自己）；
3. 旧的 `PUT /menus/user-menus/{id}` **保留不动**（前端已有调用、账号包导入也依赖它），
   只是新建账户不再需要额外调它。

另外三点收口：

- **合法性校验**：`allowed_permissions` 的每个码必须在 `ALL_ACTION_CODES`（由
  `MENU_ACTION_INDEX` 派生，见 §1.3）集合内
  （现有接口对动作码未做白名单校验，只有菜单 key 做了）；
- **收窄校验**：提交的页面/动作必须是"上级允许集合"的子集，越界返回 400 并指出越界项
  （**不静默裁剪** —— 静默裁剪会让管理员以为勾上了）；
- **版本号自增**：任何权限字段变更 → `user.permissions_version += 1`
  （`role` / `data_scope` / `is_active` 同样要 bump，见 §2.3）。

新增 `POST /users/permission-preview`（管理员）：入参为拟提交的勾选，
返回服务端算出的 `pages/modules/actions` 与 `denied` 原因，供 §3.5 的保存前复核。

### 4.4 批量接口

```
POST /users/batch-permissions
body: { user_ids: [int], mode: "intersect"|"replace"|"union",
        allowed_menus?: [str], allowed_permissions?: [str], pack_id?: int }
```

- 逐用户做 §4.3 的收窄校验，**任一越界则整批回滚**（事务内，避免"改了一半"）；
- `intersect`（默认）只减不增；`replace` 覆盖；`union` 需 `is_superuser` 才允许，
  **且仍要与单位矩阵取交集**（`union` 只是相对"用户当前值"取并，不能突破 §2.5 第 5-7 步的上限）；
- 逐用户校验组织可达性（复用已有 `_assert_user_org_reachable`），任一不可达即整批 400；
- 成功后批量 `permissions_version += 1`，并写 `write_work_log`（一条汇总 + 每用户明细）。

**SQLite 下的两个硬约束**（离线单机部署，不能按"服务端集群"来设计）：

1. **分块提交**：`user_ids` 上限 200，服务端按 100 条/事务分块提交。
   一次性更新上千行会长时间持写锁，期间所有业务写入排队 —— 现场表现就是"点保存后全站卡住"。
2. **可续跑**：返回 `processed_user_ids` 与 `failed`，失败时前端可只重试失败块，
   不必整批重来（避免"改了 800 个，第 801 个失败，全部回滚"的挫败感）。

> **v1.2 补充（避免写出第三套批量逻辑）**：服务层**已有**批量授权工具
> `rbac_service.grant_permissions_batch`（`rbac_service.py:438`）与
> `revoke_permission`（`:488`）、`grant_permission`（`:405`）。
> 它们操作的是 `rbac_user_permissions`（直接授权表），而本节批量接口操作的是
> `users.allowed_menus` / `allowed_permissions`（JSON 字段）—— **两者不是一回事**。
> 实现时应当把"分块提交 + 可续跑"抽成一个通用帮助函数，让两条通道共用，
> 而不是在 `users.py` 里再手写一遍分块循环（否则又变成"同一语义、三套实现"）。


### 4.5 迁移与灰度

| 阶段 | 动作 | 判据 |
|---|---|---|
| P1 | `effective_permission_service` + `require_permission`（默认 `shadow`） | 全量测试绿；shadow 日志统计"将被拦"清单 |
| P2 | 按模块逐批把 `shadow` 改 `enforce` | 该模块 shadow 清单清零、且 e2e 覆盖主要按钮 |
| P3 | 前端接入 `denied` 原因展示 | 置灰项与后端 403 一致 |

`shadow` 模式下只记日志不拦截，日志格式沿用 `grant_guard` 的
`R33 授权守卫[shadow] ...`，便于用同一条 grep 汇总。

### 4.6 可观测性与回滚开关

**可观测性**（shadow 期没有量化指标，就没法判断"能不能切 enforce"）：

- 新增计数器 `perm_denied_total{code, reason, mode}`（`reason ∈ role/whitelist/machine/org_grant/org_policy`），
  暴露在现有 `/metrics`；shadow 与 enforce 都计数，只是前者不 403；
- 切 enforce 的判据写成可执行的形式：**该模块 shadow 命中数连续 7 天为 0，且 e2e 覆盖其主按钮**；
- 日志里同时记 `user_id` 与 `module`，便于现场定位"是谁被拦了"（不要只记 code）。

**回滚开关**（离线现场不能靠"改环境变量 + 重启"）：

- `GRANT_GUARD_MODE` 是进程级开关，切一次影响全站，粒度太粗
  （实现见 `grant_guard.current_mode():40`：读 `GRANT_GUARD_MODE`，**非法值按 `off`**，
  `off` 时零查询零行为变化）；
- 增加**模块级** kill switch：`PERM_ENFORCE_MODULES=villages,funds`（白名单式，
  不在列表里的模块一律按 shadow 处理）。出问题时只需去掉一个模块名，不必全站回退；
- 该配置建议落 `SystemConfig`（已有配置表），支持运维页面热改，避免重启。

> **v1.2 建议**：动作守卫**不要复用** `GRANT_GUARD_MODE` —— 两者语义不同
> （前者是"模块级写授权"，后者是"动作级显式声明"），共用开关会让"只回退动作守卫"
> 无法实现。建议独立配置 `ACTION_GUARD_MODE`（`off|shadow|enforce`，默认 `shadow`），
> 避免把 V1 的授权矩阵回退连带 V2 的动作守卫一起关掉。

## 5. 三个关键场景怎么落地

### 5.1 权限继承（由粗到细，只收不放）

```
角色默认  →  权限包  →  用户白名单  →  单位授权矩阵  →  机器码授权  →  组织模块策略
 (基础)      (模板)     (个例)        (上级约束)       (本机约束)      (运维开关)
```

- 越靠右**优先级越高、方向只能是"收窄"**；
- 单位矩阵 `active=False`（未下发授权）时整层跳过，回落 legacy —— 这条已有实现，
  新方案不得改变（否则升级会改变存量行为）；
- 超管豁免：`is_superuser` 直接拿全量，不参与上述收窄（已有实现，保持一致）。

### 5.2 批量授权

- 日常：维护若干权限包（如"村级录入员""乡镇审核员"），建账户时选包；
- 存量调整：`POST /users/batch-permissions` 按组织树批量套用（默认 `intersect`）；
- 离线场景：权限包可随账号包（`.apkg`）下发，导入时按包写入每个账户的 `allowed_*`
  —— 这条链路已存在（`account_package_service`），方案只要求导入时同样做 §4.3 的合法性校验。

### 5.3 权限变更后的即时生效

问题现状：`menuStore.fetchMenus()` 只在**首次导航**时调用（`router/guards.ts:100`），
`authStore.user.permissions` 登录后不再刷新 —— 管理员改完权限，用户不重登就看不到。

> **v1.2 据实更正（这一条会直接决定方案能否落地，必须放在最前面）：**
>
> 1. `router/guards.ts:99-101` 的真实逻辑是
>    `if (!menuStore.loaded) await menuStore.fetchMenus()` —— **只在 `loaded` 为 false 时拉**，
>    `routeGuard` 里**没有**任何 `force` 参数；`menuStore.fetchMenus`（`menu.ts:397-417`）
>    本身也没有 `force` 形参，只有 `_inflight` 去重。所以本文下面写的
>    `menuStore.fetchMenus(force=true)` **当前不存在**，属于**待新增**能力。
> 2. `authStore` **没有 `refreshUser`**。store 实际暴露的是
>    `token / user / error / mustChangePassword / isAuthenticated / isAdmin / canViewDeleted /
>    modulePermissions / logout / lockSession / login / verifyTwoFactorLogin / fetchUser / getAuthData`。
> 3. 更麻烦的是**现有 `fetchUser`（`auth.ts:318-329`）本身就刷新不了权限**：
>    `if (!token.value || user.value) return` —— **已有 user 时直接短路返回**，
>    后面 `user.value = res.data` 根本走不到。
>
> 结论：本方案要补的前置能力是 **3 个**（`menuStore.fetchMenus(force)`、`authStore.refreshUser`、
> 响应头+拦截器），不是 v1.1 说的 1 个。漏掉前两个中的任何一个，拦截器都会在
> **`refreshUser is not a function`** 或 **`fetchMenus` 直接返回缓存**处静默失败，
> 现场表现就是"改了权限没反应"，**比不实现更糟**。

方案（两层，先做便宜的）：

1. **响应头版本号（推荐，零额外请求）**
   - 后端在认证中间件给每个已认证响应加 `X-Perm-Version: "{user_ver}.{grant_ver}"`（复合串，见 §2.3）；
   - 前端 axios 响应拦截器比较本地缓存值，不一致则触发
     `authStore.refreshUser()`（**待新增**，见上） + `menuStore.fetchMenus(force=true)`
     （**待新增 force 参数**）；
   - `/auth/me` 已返回 `permissions`（`auth.py:378`），`refreshUser` 只需强制重取它并覆盖
     `user.value`，**不要再走 `fetchUser` 的短路路径**；
   - **注意：刷新 store ≠ 界面立刻变化**。`v-permission` 的 `updated` 钩子依赖组件重渲染，
     而主内容区的真实写法是 `frontend/src/layouts/DefaultLayoutSafe.vue:318-324`：
     ```vue
     <router-view v-slot="{ Component }">
       <component :is="Component" v-if="Component" />
     </router-view>
     ```
     **没有 `:key`、也没有 `keep-alive`**（v1.2 已核验两个 layout 与 `App.vue`，
     全仓无 `keep-alive`）—— 所以字面量绑定（`v-permission="'villages:write'"`）
     不会建立响应式依赖，"下一次点击即生效"**不成立**，实际要等下一次导航导致组件重建。
     （v1.1 把这处写在 `App.vue`，位置不准；`App.vue:4-14` 另有一层 `router-view`，
     但业务页面的实际容器是 `DefaultLayoutSafe.vue`。）
   - 因此必须补一个**重渲染触发器**：在 `DefaultLayoutSafe.vue` 维护 `permEpoch` ref，模板改为
     ```vue
     <component :is="Component" :key="`${route.fullPath}:${permEpoch}`" />
     ```
     拦截器检测到版本变化时 `permEpoch++`。代价是当前页会重建一次（会重新拉列表数据），
     但权限变更本就是低频操作，可接受；比"用户以为没生效、反复点"要好。
   - **没有 `keep-alive` 是好事**（v1.2 核验）：不存在"key 变化导致 `include` 列表失配"的副作用，
     `:key` 改造只需关注重建本身。


2. **主动失效（可选，用于强制场景）**
   - 管理员「立即生效」按钮 → 递增 `permissions_version` 并写审计；
   - 用户下一次任意请求就会被拦截器捕获，无需重登；
   - 若需更强，可复用现有 `token_version` 机制强制下线（已有 `revoke_all_tokens`），
     但**不建议**把权限变更做成强制下线 —— 现场体验太差。

**不采用轮询**：离线单机部署、内网多机同步的场景下，轮询只会增加无意义负载。

## 6. 机器码授权的接入点

机器码授权（ADR-0008）在权限链路里扮演"**本机能力上限**"，与"账户权限"正交：

- 现有：`rbac_service._get_cached_restricted_permissions` 从权限集合里**减去**受限项；
- 本方案：把它产出的受限集合**并入 `EffectivePermissions.denied`**，标记 `machine`；
- 交互：勾选界面里被机器限制的项置灰，tooltip「本机未获得该模块授权，请联系上级申请授权码」；
- 导出账号包时：`allowed_*` 必须**先与机器授权取交集**再打包，避免"导出一个本机都跑不动的权限"。

这样"机器码授权 → 单位授权 → 账户权限"三者在 UI 上呈现为同一条链，而不是三套独立开关。

## 8. 风险与不做什么

**风险**

1. **两套守卫结论不一致**：`grant_guard` 用 URL 前缀映射模块，`require_permission` 用显式声明。
   必须保证同一接口两边结论一致，否则会出现"模块守卫放行、动作守卫拦"的诡异 403。
   缓解：按 §4.1.2 收口到同一份 `request.state.effective`，而不是各算各的。
2. **存量数据兼容**：`allowed_menus` 为 `NULL` 与 `[]` 语义相反，批量操作极易写错。
   缓解：批量接口显式要求 `mode`，不提供"默认覆盖"。
3. **权限目录漂移**：新页面忘记登记 `actions` → 该页面永远勾不出动作。
   缓解：§1.3 的门禁（page 必须声明 actions）。
4. **shadow 期过长**：一直不开 enforce，等于没有动作级防护。
   缓解：§4.6 的可执行判据（shadow 命中 7 天为 0 + e2e 覆盖）与模块级 kill switch。
5. **动作码切换误伤存量用户**（本次评审新增）：端点改判新码后，只持有 `data:create` 的用户立刻 403。
   缓解：§1.2 的 legacy 别名双读，按命中数退场。
6. **动作权限越过模块级授权**（本次评审新增）：现有 `allowed_permissions` 只与角色权限取交集，
   没有与单位矩阵取交集 → "单位给 view、白名单里有 delete"的矛盾状态。
   缓解：§2.5 第 7 步强制 `base &= modules`。
7. **即时生效被高估**（本次评审新增）：刷新 store 不等于界面变化，`v-permission` 依赖重渲染。
   缓解：§5.3 的 `permEpoch` 强制重建。
8. **SQLite 写锁**（本次评审新增）：批量授权一次更新上千行会卡住全站写入。
   缓解：§4.4 的分块提交与可续跑。

**v1.2 代码核验新增的风险**（都是"看代码才发现"、评审讨论里没暴露的）

9. **动作码切换会让前端按钮集体消失**：`authStore.modulePermissions` 只认
   `read / write / delete / manage_roles` 四类后缀（`auth.ts:74-104`），
   若按 v1.1 的 `create/update/export/approve` 直接落库，前端推导结果恒为
   `view=false, edit=false`，**模式 4 的按钮全部隐藏**（fail-closed）。
   缓解：§1.2 的枚举收窄 + §7 的 0b 同批交付。
10. **`POST /users` 与 `user_service.create_user` 是两条创建路径**：
    前者在 `users.py:788-802` 内联构造 `User(...)`，不走后者；后者才带
    `allowed_menus` 过滤（`user_service.py:176-194`）。只改 schema 不改调用，
    会出现"服务层支持、接口不生效"的半吊子状态。缓解：§4.3 的强制收口。
11. **矩阵生效时菜单不并公开项**：这是**既有实现**（`menus.py:1381-1399`），
    若 `resolve()` 按 v1.1 的"最后并公开项"统一处理，会**放大**上级已收回的菜单。
    缓解：§2.5.1 的两分支必须分开实现。
12. **空菜单 DoS**：`set_user_menu_config` 的 `menu_keys=[]` 可把他组织/超管账号
    的可用性清空（`menus.py:1552` 代码注释已指出）。缓解：§3.2 的二次确认
    + §4.3 的越界校验 + 审计。
13. **`fetchUser` 的短路**：`if (!token.value || user.value) return`（`auth.ts:318`）
    使"刷新权限"在已有 user 时静默无效。缓解：§5.3 / §7-4b 新增 `refreshUser`。

**明确不做**

- **不新建第二套动作级关系表**（v1.2 措辞修正：`rbac_user_roles` /
  `rbac_role_permissions` / `rbac_user_permissions` **已存在**，见 §2.1；
  不新建的是"与它们并行的又一套动作表"）；
- 不把菜单 key 换成数字 ID（`MENU_DEFINITIONS` 的 key 已是事实标准，且权限包/账号包都按 key 存）；
- 不做"权限审批流"（超出本期范围，且离线场景没有审批人）；
- 不引入前端权限框架（现有 `v-permission` 四模式已覆盖页面/模块/动作，换框架要重写全站）；
- **不做资源级权限**（如"只能改自己创建的村"）—— 本期只到动作级；`EffectivePermissions`
  的解析器预留 `code:scope` 扩展位，但不实现，避免协议反复改。

## 9. 一页速查

- **一个命名空间**：`module_key` 是**菜单 page/console key 的超集**（含 32 个无页面的后端模块），
  动作码 `<page_or_module_key>:<action>`；
  旧的单数码走别名表双读（**17 条全覆盖**，见 §1.2 实际清单），不再新增。
- **三级粒度**：页面 → 模块 `view/edit` → 动作，逐级收窄，动作不得越过模块级。
- **一个裁决点**：`effective_permission_service.resolve()`，菜单/守卫/预览都调它，两级缓存；
  **它必须复刻 §2.5.1 的两条分支**（矩阵 active 时不并公开项、用户级只收窄）。
- **一处声明（目标态）**：`actions` 最终内嵌在 `MENU_DEFINITIONS` 的 page/console 条目；
  v1.3 先由 `permission_catalog` 从菜单 + 写路由派生，门禁防漂移。
- **一条铁律**：任何个性化配置只能收窄，不能扩大（`&=` 与 `intersection`，绝不 `|=`）。
- **一个复合版本**：`"{user_ver}.{grant_ver}"` + `permEpoch` 强制重渲染，改完真能看见；
  **前置**是 `authStore.refreshUser()` 与 `menuStore.fetchMenus(force)` 先存在（§5.3）。
- **一个前端词汇**：`modulePermissions` 只认 `read/write/delete/manage_roles`，
  动作枚举必须与它对齐，否则按钮全隐藏（§1.2 / §7-0b）。
- **一个界面**：组织树下建账户，左树勾页面、右侧勾按钮，不可选项置灰并说明来源。
