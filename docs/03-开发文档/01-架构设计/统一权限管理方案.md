# 统一权限管理方案（机器码授权 × 权限包 × 账户创建）

> 版本：v1.1（多维度评审后修订，变更见 §10）｜ 2026-11-22 ｜ 基线代码：v1.18.58
>
> 目标：超级管理员在组织机构下创建账户、设置密码时，**在同一界面**勾选该账户可访问的页面
> 与可操作的功能，并让这套勾选与「单位授权矩阵」「权限包」「机器码授权」收敛到同一个裁决点。

---

## 0. 先说结论：不要另起一套

系统里已经有一套相当完整的权限积木，缺的不是"再造一层"，而是**把三层积木接到同一根轴上**。
盘点如下（都已在生产代码里跑着）：

| 能力 | 现有实现 | 位置 |
|---|---|---|
| 权限目录（页面清单） | `MENU_DEFINITIONS`：扁平条目 + `children` + `tabs`，`kind` 分 `page`/`group` | `app/api/v1/menus.py:69` |
| 菜单可见性解析 | `_get_user_accessible_menu_keys`：用户白名单 > 权限包 > 角色默认，再并公开项 | `app/api/v1/menus.py:1367` |
| 单位授权矩阵 | `org_grants(organization_id, module_key, level)`，`level ∈ {none,view,edit}`，沿组织树向上合并、深者优先 | `app/models/org_grant.py`、`app/services/effective_grant_service.py` |
| 写接口守卫 | `enforce_write_grant`（app 级依赖）：URL → 模块，矩阵 `can_edit` 不过则 403；支持 `off/shadow/enforce` | `app/core/grant_guard.py:98`、`app/core/write_route_map.py` |
| 组织模块策略 | `org_module_policy_gate.evaluate_org_policy`：`read_only` / `disabled` | `app/middleware/org_module_policy_gate.py` |
| 角色权限 + 用户白名单 + 机器码扣减 | `permissions = 角色权限 ∩ allowed_permissions − 机器码受限` | `app/services/rbac_service.py:300-350` |
| 权限包 | `permission_packs.menu_keys`（可见性）+ `grants`（模块 → edit/view/none） | `app/models/permission_pack.py` |
| 账户权限字段 | `users.allowed_menus`（NULL=继承）、`allowed_permissions`（JSON）、`permission_pack_id` | `app/models/user.py:69-75` |
| 前端按钮级指令 | `v-permission` 四种模式：角色数组 / 权限码 / `{menu}` / `{module,level}` | `frontend/src/directives/permission.ts` |
| 前端模块权限表 | `authStore.modulePermissions`：由 `permissions` 码推导 `{module:{view,edit}}` | `frontend/src/stores/auth.ts:74` |

**四个真实缺口**（本方案要补的）：

| 编号 | 缺口 | 后果 |
|---|---|---|
| G1 | `check_permission` 只作为 `/rbac/check-permission` 查询接口暴露，**没有作为路由依赖使用** | 按钮级权限只靠前端 `v-permission` 隐藏；绕过前端直接调接口不受限 |
| G2 | `PERMISSION_OPTIONS` 是 17 条**扁平静态码**，与菜单树无关联 | 勾选界面无法表达"这个页面下有哪些按钮" |
| G3 | `/users/form-options` 返回角色/数据范围/权限码/组织树，**不返回菜单树** | 账户创建界面拿不到页面清单，只能另调 `/menus/all` 自行拼装 |
| G4 | 无"权限版本号"，`authStore.user.permissions` 登录后不再刷新（菜单只在首次导航时 `fetchMenus`） | 管理员改了某人权限，该用户不重新登录就看不到变化 |

### 0.1 必须先解决的既有债务：三套命名空间

这是本方案最容易翻车的地方，**先摆事实**（都已核对过代码）：

| 命名空间 | 形态 | 证据 |
|---|---|---|
| 菜单 key（`MENU_DEFINITIONS`） | **复数**：`villages` / `projects` / `funds` / `schools` / `rural-works` | `app/api/v1/menus.py:69` |
| 写守卫 module（`write_route_map`） | **复数，与菜单 key 对齐**：`villages` / `projects` / `funds` | `app/core/write_route_map.py:60-65` |
| 按钮码前缀（`PERMISSION_OPTIONS`） | **单数**：`village:manage` / `project:manage` / `fund:manage` | `app/api/v1/auth/users.py:59-61` |

也就是说：**页面与模块是同一套 key（复数），只有按钮码前缀是单数**，三者并不一致。

**结论（本方案强制约定）**：

1. `module_key ≡ 菜单 page key`，**一律复数**；
2. 动作码写作 `<page_key>:<action>`，即 `villages:create`、`funds:export`；
3. 现有 17 条单数码作为 **legacy 别名**保留，用一张显式映射表过渡（见 §1.2），
   **不允许**再新增单数前缀的码；
4. 由此 §2.5 的 `pages ∩ modules` 才有定义 —— 两边是同一命名空间，交集才成立。

> 若不先钉死这条，动作码前缀（`village`）与菜单 key（`villages`）永远对不上，
> 前端 `v-permission="{ module: 'village' }"` 会永远匹配不到任何权限。

## 1. 权限粒度划分策略

采用**三级、单向收窄**的结构：页面可见 ⊃ 模块可写 ⊃ 动作可执行。
上一级不通过，下一级无意义；下一级勾选不能扩大上一级。

### 1.1 三级定义

| 级别 | 标识 | 语义 | 存储位置 | 裁决函数 |
|---|---|---|---|---|
| **L1 页面级** | `menu_key`（与 `MENU_DEFINITIONS` 同源） | 左侧导航是否出现、路由是否放行 | `users.allowed_menus` / `permission_packs.menu_keys` | `_get_user_accessible_menu_keys` |
| **L2 模块级** | `module_key`（= 页面 key 的模块根） | 该模块只读还是可写 | `org_grants.level` / `permission_packs.grants` | `GrantMatrix.can_view/can_edit` |
| **L3 动作级** | `<module>:<action>` | 具体按钮（新建/编辑/删除/导出/审批…） | `users.allowed_permissions` | 新增 `require_permission(code)` |

> **为什么 L2 与 L1 分开**：`org_grants` 已经以模块为粒度、按组织树继承；页面级用菜单 key
> 是为了能表达"只给看某一个子页面"。两者不是重复，而是"导航可见性"与"数据写入权"的分离 ——
> 这也是现有 `grant_guard` 的既有语义，不要合并。

### 1.2 动作码命名规范

```
<page_key>:<action>        # page_key 一律复数，与 MENU_DEFINITIONS 一致
```

`action` 只允许以下枚举（新增需在本表登记，避免各写各的）：

| action | 含义 | 典型按钮 |
|---|---|---|
| `read` | 查看详情（列表已由 L1 控制，这里指详情/弹窗） | 查看 |
| `create` | 新建 | 新增、导入新建 |
| `update` | 修改 | 编辑、启用/停用 |
| `delete` | 删除（含软删） | 删除、批量删除 |
| `export` | 导出/下载 | 导出 Excel、下载模板 |
| `import` | 导入/上传 | 导入、上传附件 |
| `approve` | 审批处理 | 通过、驳回 |
| `assign` | 分配/授权 | 分配角色、分配权限 |

示例：`villages:create`、`funds:export`、`projects:approve`、`users:assign`。

**legacy 别名表（过渡期必需，否则切换即误伤存量用户）**

现有 17 条是**单数前缀 + 粗粒度**，且 `data:*` / `approve:*` 跨模块，无法一一对应到页面。
切换端点判定时若直接改判新码，只持有旧码的用户会立刻 403。因此定义显式别名：

```python
# app/api/v1/menus.py
LEGACY_ACTION_ALIAS: dict[str, tuple[str, ...]] = {
    "village:manage":  ("villages:read", "villages:create", "villages:update", "villages:delete"),
    "project:manage":  ("projects:read", "projects:create", "projects:update", "projects:delete"),
    "fund:manage":     ("funds:read", "funds:create", "funds:update", "funds:delete"),
    "school:manage":   ("schools:read", "schools:create", "schools:update", "schools:delete"),
    "data:create":     ("*:create",),          # 跨模块通配，见下
    "data:edit":       ("*:update",),
    "data:delete":     ("*:delete",),
    "data:view":       ("*:read",),
    "data:export":     ("*:export",),
    "data:import":     ("*:import",),
    "approve:view":    ("*:read",),
    "approve:submit":  ("*:create",),
    "approve:process": ("*:approve",),
}
```

判定规则（**双读单写**）：

```
allowed(code) = code ∈ eff.actions
                or 任意 alias ∈ eff.actions 使 code 在其展开集合内
```

- **读**：新旧都认，存量配置立刻生效，不需要一次性迁移数据；
- **写**：勾选界面只产出新码（复数 + 精确 action），legacy 码在界面里折叠为"历史权限"只读展示；
- **退场**：`/metrics` 统计 legacy 命中数，连续两个版本为 0 后删除别名表。

> `*` 通配只在别名展开时使用，**不允许**出现在 `eff.actions` 或用户配置里 ——
> 否则等于开后门。校验层必须拒绝含 `*` 的提交值。


### 1.3 权限目录单一源

**不要把动作表写成第二份 dict** —— 那只是把漂移从"菜单 vs 权限码"挪到了"菜单 vs 动作表"。
正确做法是**把 `actions` 直接放进 `MENU_DEFINITIONS` 的 page 条目**，让页面与动作物理上
在同一行定义、同一次评审：

```python
# app/api/v1/menus.py
{"key": "villages", "label": "帮扶村管理", "path": "/villages", "kind": "page",
 "actions": ("read", "create", "update", "delete", "import", "export")},
```

再由它派生一个只读索引供运行时用（纯计算，不落库）：

```python
MENU_ACTION_INDEX: dict[str, tuple[str, ...]] = {
    e["key"]: e.get("actions", ())
    for e in _flatten_entries(MENU_DEFINITIONS)   # 含 children / tabs
    if e.get("kind") == "page"
}
ALL_ACTION_CODES: frozenset[str] = frozenset(
    f"{k}:{a}" for k, acts in MENU_ACTION_INDEX.items() for a in acts
)
```

配套门禁（`scripts/check_permission_catalog.py`，挂到 `static-analysis` 作业）：

1. 每个 `kind == "page"` 条目必须有非空 `actions`（防止新页面漏配动作）；
2. `actions` 里的每个值必须在 §1.2 的 action 枚举内；
3. `group` / `tab` 条目**不得**声明 `actions`（动作只挂在能承载按钮的页面上）；
4. `PERMISSION_OPTIONS` 里的每个码，必须能通过 §1.2 的别名表展开到 `ALL_ACTION_CODES`；
5. `ALL_ACTION_CODES` 里不允许出现 `*`。

> 这条门禁是本方案的**地基**：动作目录一旦与页面清单脱钩，勾选界面就会勾到不存在的页面，
> 而这类漂移靠人眼极难发现（`check_doc_numbers` 数字漂移十来个版本才被发现，就是前例）。

## 2. 权限与账户的关联数据模型

### 2.1 不新增关系表

**结论：沿用现有字段，只加一列。** 理由：

- `users.allowed_menus` / `allowed_permissions` 已经是"账户 × 权限"的实例化结果，
  再建 `user_permissions` 关系表会形成**双写**，任何一处漏同步就是权限错乱；
- `permission_packs` 是"模板"（可批量套用），`allowed_*` 是"实例"（可个性化），
  这个"模板 → 实例"的关系已经够用；
- 审计需求由 `AuditLogger` + `write_work_log` 承担，不需要额外的关联表来记录历史。

### 2.2 字段语义（必须写清，否则容易配错）

| 字段 | 类型 | NULL 语义 | 空值语义 | 生效方式 |
|---|---|---|---|---|
| `users.allowed_menus` | Text(JSON) | **继承**（权限包 → 角色默认） | `[]` = **一个页面都不给** | 与上级取交集（只收窄） |
| `users.allowed_permissions` | Text(JSON) | 继承角色权限 | `[]` = 无任何动作权限 | 与角色权限取**交集** |
| `users.permission_pack_id` | Integer | 未绑定 | — | 低于 `allowed_menus` 优先级 |
| `users.role` / `data_scope` | String | — | — | 决定基础权限与数据域 |

> 现有实现已经保证"只收窄不放宽"：`menus.py:1393-1397` 明确
> `keys &= set(allowed)`，`rbac_service` 用 `intersection`。新方案保持这条铁律，
> **不允许任何路径通过 `allowed_*` 扩大权限**。

### 2.3 唯一新增列：`users.permissions_version`

```python
# app/models/user.py
permissions_version = Column(Integer, nullable=False, default=0, server_default="0",
                             comment="权限版本号：任何权限相关字段变更时 +1，供客户端即时刷新")
```

迁移：`alembic/versions/user_permissions_version_001.py`（`ADD COLUMN ... DEFAULT 0 NOT NULL`，
SQLite 支持 `ADD COLUMN` 带默认值；需按仓库约定附"能手工构造旧库状态"的自证测试）。

**为什么要它**：G4 的根因是客户端把 `user.permissions` 缓存在内存里，登录后不再取。
有了版本号，服务端在任何响应里带一个 `X-Perm-Version` 头，客户端一比就知道该刷新，
**不需要轮询、也不需要用户重新登录**。

**必须在哪些地方自增**（漏一处就有一条路径不生效，这是本节最容易做漏的点）：

| 变更入口 | 位置 |
|---|---|
| 创建账户 / 更新账户 / 权限分配 | `app/api/v1/auth/users.py`（`POST /users`、`PUT /users/{id}/permissions`） |
| 设置菜单权限 | `app/api/v1/menus.py:1606`（`set_user_menu_config`） |
| 角色授予 / 撤销 | `app/services/rbac_service.py`（`assign_role` / `revoke_role`） |
| 权限包绑定变更 | `users.permission_pack_id` 的写入点 |
| 权限包导入 | `app/services/permission_package_service.py:975` 附近 |
| 离线账号包导入 | `app/services/account_package_service.py:353` 附近 |
| 单位授权矩阵变更 | **不刷用户**：`org.grant_version` 已由 `org_grants.py:223` 递增，直接参与复合版本串（见下） |

> 注意 `role`、`data_scope`、`is_active` 变更**同样要 bump** —— 它们影响的是"能看到哪些数据"
> 和"能不能登录"，不只影响按钮。漏掉这几个字段，会出现"权限改了、数据范围没刷新"的半更新状态。


> **单位矩阵那一条要特别处理**：矩阵是**单位级**的，改一次影响该单位所有用户。
> 但**不能用 `max(user.permissions_version, org.grant_version)`** —— 两个计数器
> 各自独立递增、量纲不同，会漏刷新。反例：用户版本 5、单位版本 100，响应头取 100；
> 之后该用户权限变更（版本 6），响应头仍是 100，客户端认为没变 → 不刷新。
>
> **正确做法：复合版本串**
>
> ```python
> header = f"{user.permissions_version}.{org.grant_version or 0}"
> ```
>
> 客户端只做字符串不等比较；任一维变化都会变。单位级变更无需逐个用户刷库，
> 也不需要额外列。若担心可读性，也可发两个独立头
> （`X-Perm-Version` + `X-Grant-Version`），但**不要合并成一个数字**。


### 2.4 可选增强：权限包携带动作

```python
# permission_packs 新增（可空，向后兼容）
actions = Column(Text, nullable=True,
                 comment="动作白名单(JSON数组，如 [\"village:create\"])；空则由 menu_keys 派生")
```

沿用 `grants` 的兼容策略：为空时由 `menu_keys` 派生"全部动作"，保证老包行为不变。
这样"权限包"就能从"页面套餐"升级为"页面 + 按钮套餐"，批量授权才有意义。

### 2.5 有效权限的合并顺序（唯一算法）

```
1. base     = 角色权限集合（rbac_service.get_user_permissions）
2. if ADMIN_ALL in base: base = ALL_ACTION_CODES
3. if user.allowed_permissions 非空: base &= allowed_permissions      # 只收窄
4. base    -= 机器码受限动作                                            # 机器授权缺口
5. modules = 单位矩阵 ∩ 权限包 grants（深者优先、deny 不被浅层翻回）
6. pages   = _get_user_accessible_menu_keys() ∩ set(modules)
7. base    &= {code for code in base if code.split(":")[0] in modules}   # 动作不得越过模块级
8. 组织模块策略 read_only → modules 降为 view，并扣掉非 read 动作；
   disabled → 从 pages / modules / actions 一并移除
9. actions  = base ∪ legacy 别名展开（见 §1.2，仅读路径）
```

第 5-6 步的 `modules` 与 `pages` 是**同一命名空间**（都是复数页面 key，见 §0.1），
所以交集有定义 —— 这是 §0.1 必须先钉死的原因。

第 7 步是关键补充：**动作权限不能越过模块级授权**。否则"单位只给了 view，
但用户白名单里有 `villages:delete`"就会形成可删不可写的矛盾状态
（现有实现里 `allowed_permissions` 只与角色权限取交集，**没有与单位矩阵取交集**，
这是本次要补的口子）。

第 9 步的别名展开只在**读**路径发生，写入永远落新码（见 §1.2 双读单写）。


第 5-7 步已在 `menus.py` 与 `grant_guard.py` 里实现，方案只要求**把它们收口到一个函数**
（见 §4.1），避免菜单侧与写守卫侧各算一遍、结论不一致（历史上出过这种不一致）。

## 3. 权限勾选交互设计

### 3.1 入口与布局

在「组织机构 → 选中单位 → 新增账户」的抽屉里，分三段（同屏，不跳页）：

```
┌─ 新增账户 ─────────────────────────────────────────────┐
│ ① 基本信息   用户名 / 姓名 / 初始密码 / 手机            │
│ ② 归属与角色  组织（默认当前单位）/ 角色 / 数据范围      │
│ ③ 功能权限   ┌ 左：页面树（复选）  ┬ 右：动作面板 ┐     │
│              │ ☑ 帮扶村管理       │ ☑ 新建 ☑ 编辑    │     │
│              │   ☑ 村情档案      │ ☑ 删除 ☐ 导出    │     │
│              │   ☐ 一户一档      │                  │     │
│              └──────────────────┴──────────────────┘     │
│ 底部：可见 12 页 / 可写 8 模块 / 26 个操作   [取消][保存] │
└────────────────────────────────────────────────────────┘
```

### 3.2 三种勾选态与"来源"标识

每个页面节点左侧三态复选（全选 / 半选 / 未选，父子联动），右侧显示**该权限从哪来**：

| 徽章 | 含义 | 可否取消勾选 |
|---|---|---|
| `角色` | 角色默认带出来的 | 可以（取消即写入 `allowed_menus` 收窄） |
| `权限包` | 绑定包带出来的 | 可以（同上） |
| `单位` | 上级单位授权矩阵给的 | **不可**（置灰 + tooltip「上级单位未授权此模块」） |
| `本机` | 机器码授权允许的 | **不可**（置灰 + tooltip「本机未获得该模块授权」） |
| `公开` | `_PUBLIC_ACCESS_KEYS` 里的 | 不可（本来全角色可见） |

**这是本方案交互上的关键点**：让管理员一眼看出"这个勾我为什么勾不动"，
而不是勾了保存后没生效、回来反复试。

### 3.3 动作面板的联动规则

- 选中某页面 → 右侧列出该页面的动作（数据来自 `MENU_ACTIONS`）；
- 页面未选 → 动作面板整体禁用（页面都进不去，给按钮权限没有意义）；
- 模块 `level=view`（单位只给只读）→ 动作里只保留 `read`，其余置灰；
- 勾选任一写动作 → 自动勾上 `read`（隐含依赖，避免"能删不能看"的畸形组合）；
- 全不勾 → 写入 `allowed_permissions = []`（明确"无动作权限"，而非继承）。

### 3.4 批量授权

两个层次，都复用现有结构：

1. **模板批量**（推荐日常用）：先建权限包（勾选一套页面 + 动作），创建账户时选包，
   或对多个已有账户批量套用；
2. **直选批量**：勾选多个账户 → 「批量设置权限」→ 弹出同一套勾选界面 →
   选择覆盖模式（**覆盖** / **取交集** / **取并集**，默认取交集，符合"只收窄"铁律）。

批量接口见 §4.4。

### 3.5 实时预览

底部统计随勾选实时变化：`可见 N 页 / 可写 M 模块 / K 个操作`。
保存前调用一次 `POST /users/permission-preview`（见 §4.3）做服务端复核，
若与前端算出的不一致（例如单位矩阵刚变），以服务端为准并提示差异 —— 避免"看着能勾、存了不生效"。

## 4. 后端接口层的校验实现

### 4.1 单一裁决点：`effective_permission_service`

新增 `app/services/effective_permission_service.py`，对外只暴露一个数据结构：

```python
@dataclass(frozen=True)
class EffectivePermissions:
    pages: set[str]                    # 可见页面 key
    modules: dict[str, str]            # module_key -> "view" | "edit"
    actions: set[str]                  # 可执行动作码
    denied: dict[str, str]             # key -> 拒绝原因（machine/org_grant/org_policy/role）
    version: int                       # = user.permissions_version

def resolve(db, user) -> EffectivePermissions: ...
```

内部按 §2.5 的九步合并，复用 `get_grant_matrix` / `_get_user_accessible_menu_keys` /
`rbac_service.get_user_permissions`。**所有调用方（菜单下发、写守卫、动作守卫、账户预览）
都走它**，禁止各处自行拼装。

#### 4.1.1 两级缓存（否则每请求多 6-10 次查询）

`resolve()` 的原始成本：组织链逐级查询（树深 3-5 层）+ 角色权限 + 权限包 + 用户行，
一次约 6-10 次 SQL。不加缓存，等于给**每个已认证请求**都加一遍。

| 级别 | 载体 | 键 | 生命周期 |
|---|---|---|---|
| 请求内 | `request.state.effective` | 一次请求 | 请求结束即弃 |
| 进程内 | 模块级 dict（上限 512，触顶整体清空，与 `effective_grant_service._CACHE` 同风格） | `(user_id, user.permissions_version, org_id, org.grant_version)` | 直到版本号变化 |

版本号参与键，**不需要显式失效**（旧 entry 自然不再命中）；但用户删除/组织迁移时
要调一次 `clear_cache()`，避免脏 entry 长期驻留。

#### 4.1.2 与 `grant_guard` 的重复解析（必须收口）

现状：`grant_guard` 作为 app 级依赖，**自己开 `SessionLocal`、自己解 token、自己算矩阵**
（`grant_guard.py:110-124`）。如果动作守卫再算一遍，同一请求就有两次用户查询 + 两次矩阵解析，
既浪费又有"两边结论不一致"的风险。

收口方案：新增一个轻量中间件（或复用现有认证中间件），在**认证完成后**解析一次
`EffectivePermissions` 存入 `request.state.effective`：

- `require_permission` 直接读 `request.state.effective`（无则现算）；
- `grant_guard` 改为优先读 `request.state`，读不到再走原有兜底逻辑
  （它是 app 级依赖，执行早于路由依赖，需要保留兜底路径）；
- 两者都只做"读"，不做缓存写入竞争。

> 这一步不做的话，性能问题和"两套结论"问题会同时存在，且很难在上线后才发现。


### 4.2 动作级依赖：`require_permission`

```python
# app/api/v1/deps.py
def require_permission(code: str, *, mode: str | None = None):
    """声明式动作守卫。未授权 → 403，detail 带可读原因。"""
    def _dep(request: Request, current_user=Depends(get_current_user), db: Session = Depends(get_db)):
        eff = get_effective_permissions(request, db, current_user)   # 请求内缓存
        if code in eff.actions:
            return
        reason = eff.denied.get(code.split(":")[0], "no_permission")
        _deny_or_log(mode, request, code, reason)                    # shadow 只记日志
    return _dep
```

用法（示例，改造 `villages` 模块；注意是复数，见 §0.1）：

```python
@router.post("", dependencies=[Depends(require_permission("villages:create"))])
async def create_village(...): ...

@router.delete("/{village_id}", dependencies=[Depends(require_permission("villages:delete"))])
async def delete_village(...): ...
```

**配套门禁（否则永远有接口"忘了声明"）**

新增 `scripts/check_action_coverage.py`（挂 `static-analysis`）：

1. 遍历运行时路由表，取出所有写方法（POST/PUT/PATCH/DELETE）的接口；
2. 排除豁免清单（登录、匿名反馈、健康探针、授权包自举 —— 与 `write_route_map.EXEMPT_PREFIXES` 同源）；
3. 断言每个写接口的依赖里含 `require_permission(...)`，否则**列入基线并禁止新增**
   （棘轮模式：基线只减不增，与 `.type-debt-baseline.json` 同思路）；
4. 断言声明的动作码都在 `ALL_ACTION_CODES` 内（防止拼错成 `villages:creat` 后静默失效）。

> 为什么必须棘轮而不是一次清零：现存写接口数百个，一次补齐不现实；
> 但"新增接口必须有动作码"这条从第一天就能守住，否则新接口会持续稀释覆盖率。

**legacy 双读（§1.2 的落地）**：`require_permission` 内部判定为

```python
def _allowed(code, eff):
    if code in eff.actions:
        return True
    return any(expand(alias) 包含 code for alias in eff.actions if alias in LEGACY_ACTION_ALIAS)
```

这样端点改判新码后，只持有 `data:create` 的存量用户**不会**立刻 403。


**与 `grant_guard` 的分工**（重要，别重复实现）：

| 守卫 | 粒度 | 覆盖方式 | 什么时候用 |
|---|---|---|---|
| `enforce_write_grant`（已有） | 模块级（edit/none） | **全局兜底**，app 级依赖，URL 前缀映射 | 保留兜底语义，但改为优先复用 `request.state.effective`（§4.1.2），避免重复解析 |
| `require_permission`（新增） | 动作级 | **逐接口显式声明** | 需要区分"能改但不能删"这类细粒度时 |

两者同时生效时取**更严者**：动作守卫 403 直接返回；模块守卫在 app 级先跑。
`GRANT_GUARD_MODE=off` 时动作守卫仍独立工作（它不依赖矩阵是否 active）。

### 4.3 账户创建/编辑接口的收口

**现状（必须先说清，否则"同一界面勾选"落不了地）**：权限字段分在两个接口里 ——

| 字段 | 写入接口 | 说明 |
|---|---|---|
| `allowed_permissions` | `POST /users`（`UserCreate`）、`PUT /users/{id}/permissions` | 动作码 |
| `allowed_menus` | **`PUT /menus/user-menus/{user_id}`**（`menus.py:1552`） | 页面 key；`UserCreate` 里**没有**这个字段 |

也就是说：现在"建账户 + 配权限"至少要两次请求，第二次失败就留下一个**半配账户**
（有动作权限、没有页面权限），现场很难发现。这是本方案必须收口的点。

**改造（推荐）**：

1. `UserCreate` / `UserUpdateBody` 增加 `allowed_menus: Optional[list[str]]`；
   `user_service.create_user` 在同一事务里写 `allowed_menus` 与 `allowed_permissions`，
   避免半配；
2. 把 `set_user_menu_config` 里已有的校验抽成公共函数复用（不要复制）：
   - key 必须在 `_iter_definition_keys()` 内（否则 400 并列出无效 key）；
   - 目标用户必须在调用者组织子树内（`_assert_menu_config_target_allowed`）；
   - 不允许改自己（防管理员锁死自己）；
3. 旧的 `PUT /menus/user-menus/{id}` **保留不动**（前端已有调用、账号包导入也依赖它），
   只是新建账户不再需要额外调它。

另外三点收口：

- **合法性校验**：`allowed_permissions` 的每个码必须在 `MENU_ACTIONS` 派生集合内
  （现有接口对动作码未做白名单校验，只有菜单 key 做了）；
- **收窄校验**：提交的页面/动作必须是"上级允许集合"的子集，越界返回 400 并指出越界项
  （**不静默裁剪** —— 静默裁剪会让管理员以为勾上了）；
- **版本号自增**：任何权限字段变更 → `user.permissions_version += 1`。

新增 `POST /users/permission-preview`（管理员）：入参为拟提交的勾选，
返回服务端算出的 `pages/modules/actions` 与 `denied` 原因，供 §3.5 的保存前复核。

### 4.4 批量接口

```
POST /users/batch-permissions
body: { user_ids: [int], mode: "intersect"|"replace"|"union",
        allowed_menus?: [str], allowed_permissions?: [str], pack_id?: int }
```

- 逐用户做 §4.3 的收窄校验，**任一越界则整批回滚**（事务内，避免"改了一半"）；
- `intersect`（默认）只减不增；`replace` 覆盖；`union` 需 `is_superuser` 才允许，
  **且仍要与单位矩阵取交集**（`union` 只是相对"用户当前值"取并，不能突破 §2.5 第 5-7 步的上限）；
- 逐用户校验组织可达性（复用已有 `_assert_user_org_reachable`），任一不可达即整批 400；
- 成功后批量 `permissions_version += 1`，并写 `write_work_log`（一条汇总 + 每用户明细）。

**SQLite 下的两个硬约束**（离线单机部署，不能按"服务端集群"来设计）：

1. **分块提交**：`user_ids` 上限 200，服务端按 100 条/事务分块提交。
   一次性更新上千行会长时间持写锁，期间所有业务写入排队 —— 现场表现就是"点保存后全站卡住"。
2. **可续跑**：返回 `processed_user_ids` 与 `failed`，失败时前端可只重试失败块，
   不必整批重来（避免"改了 800 个，第 801 个失败，全部回滚"的挫败感）。


### 4.5 迁移与灰度

| 阶段 | 动作 | 判据 |
|---|---|---|
| P1 | `effective_permission_service` + `require_permission`（默认 `shadow`） | 全量测试绿；shadow 日志统计"将被拦"清单 |
| P2 | 按模块逐批把 `shadow` 改 `enforce` | 该模块 shadow 清单清零、且 e2e 覆盖主要按钮 |
| P3 | 前端接入 `denied` 原因展示 | 置灰项与后端 403 一致 |

`shadow` 模式下只记日志不拦截，日志格式沿用 `grant_guard` 的
`R33 授权守卫[shadow] ...`，便于用同一条 grep 汇总。

### 4.6 可观测性与回滚开关

**可观测性**（shadow 期没有量化指标，就没法判断"能不能切 enforce"）：

- 新增计数器 `perm_denied_total{code, reason, mode}`（`reason ∈ role/whitelist/machine/org_grant/org_policy`），
  暴露在现有 `/metrics`；shadow 与 enforce 都计数，只是前者不 403；
- 切 enforce 的判据写成可执行的形式：**该模块 shadow 命中数连续 7 天为 0，且 e2e 覆盖其主按钮**；
- 日志里同时记 `user_id` 与 `module`，便于现场定位"是谁被拦了"（不要只记 code）。

**回滚开关**（离线现场不能靠"改环境变量 + 重启"）：

- `GRANT_GUARD_MODE` 是进程级开关，切一次影响全站，粒度太粗；
- 增加**模块级** kill switch：`PERM_ENFORCE_MODULES=villages,funds`（白名单式，
  不在列表里的模块一律按 shadow 处理）。出问题时只需去掉一个模块名，不必全站回退；
- 该配置建议落 `SystemConfig`（已有配置表），支持运维页面热改，避免重启。

## 5. 三个关键场景怎么落地

### 5.1 权限继承（由粗到细，只收不放）

```
角色默认  →  权限包  →  用户白名单  →  单位授权矩阵  →  机器码授权  →  组织模块策略
 (基础)      (模板)     (个例)        (上级约束)       (本机约束)      (运维开关)
```

- 越靠右**优先级越高、方向只能是"收窄"**；
- 单位矩阵 `active=False`（未下发授权）时整层跳过，回落 legacy —— 这条已有实现，
  新方案不得改变（否则升级会改变存量行为）；
- 超管豁免：`is_superuser` 直接拿全量，不参与上述收窄（已有实现，保持一致）。

### 5.2 批量授权

- 日常：维护若干权限包（如"村级录入员""乡镇审核员"），建账户时选包；
- 存量调整：`POST /users/batch-permissions` 按组织树批量套用（默认 `intersect`）；
- 离线场景：权限包可随账号包（`.apkg`）下发，导入时按包写入每个账户的 `allowed_*`
  —— 这条链路已存在（`account_package_service`），方案只要求导入时同样做 §4.3 的合法性校验。

### 5.3 权限变更后的即时生效

问题现状：`menuStore.fetchMenus()` 只在**首次导航**时调用（`router/guards.ts:100`），
`authStore.user.permissions` 登录后不再刷新 —— 管理员改完权限，用户不重登就看不到。

方案（两层，先做便宜的）：

1. **响应头版本号（推荐，零额外请求）**
   - 后端在认证中间件给每个已认证响应加 `X-Perm-Version: "{user_ver}.{grant_ver}"`（复合串，见 §2.3）；
   - 前端 axios 响应拦截器比较本地缓存值，不一致则触发
     `authStore.refreshUser()`（`/auth/me` 已返回 `permissions`，见 `auth.py:378`）
     + `menuStore.fetchMenus(force=true)`；
   - **注意：刷新 store ≠ 界面立刻变化**。`v-permission` 的 `updated` 钩子依赖组件重渲染，
     而 `App.vue` 的 `<component :is="Component" />` 没有 `:key`，字面量绑定
     （`v-permission="'villages:create'"`）也不会建立响应式依赖 —— 所以"下一次点击即生效"
     **不成立**，实际要等下一次导航导致组件重建。
   - 因此必须补一个**重渲染触发器**：layout 维护 `permEpoch` ref，模板改为
     ```vue
     <component :is="Component" :key="`${route.fullPath}:${permEpoch}`" />
     ```
     拦截器检测到版本变化时 `permEpoch++`。代价是当前页会重建一次（会重新拉列表数据），
     但权限变更本就是低频操作，可接受；比"用户以为没生效、反复点"要好。


2. **主动失效（可选，用于强制场景）**
   - 管理员「立即生效」按钮 → 递增 `permissions_version` 并写审计；
   - 用户下一次任意请求就会被拦截器捕获，无需重登；
   - 若需更强，可复用现有 `token_version` 机制强制下线（已有 `revoke_all_tokens`），
     但**不建议**把权限变更做成强制下线 —— 现场体验太差。

**不采用轮询**：离线单机部署、内网多机同步的场景下，轮询只会增加无意义负载。

## 6. 机器码授权的接入点

机器码授权（ADR-0008）在权限链路里扮演"**本机能力上限**"，与"账户权限"正交：

- 现有：`rbac_service._get_cached_restricted_permissions` 从权限集合里**减去**受限项；
- 本方案：把它产出的受限集合**并入 `EffectivePermissions.denied`**，标记 `machine`；
- 交互：勾选界面里被机器限制的项置灰，tooltip「本机未获得该模块授权，请联系上级申请授权码」；
- 导出账号包时：`allowed_*` 必须**先与机器授权取交集**再打包，避免"导出一个本机都跑不动的权限"。

这样"机器码授权 → 单位授权 → 账户权限"三者在 UI 上呈现为同一条链，而不是三套独立开关。

## 7. 落地清单（按可独立交付的顺序）

| 序号 | 交付物 | 触及文件 | 验收标准（可执行） |
|---|---|---|---|
| 0 | **命名约定落地**：菜单 page 条目补 `actions`；`LEGACY_ACTION_ALIAS` 表 | `app/api/v1/menus.py` | `check_permission_catalog.py` 通过；别名表覆盖现有 17 条码 |
| 1 | 权限目录门禁 | `scripts/check_permission_catalog.py` | 挂 `static-analysis`；故意删一个 `actions` 能让 CI 红 |
| 2 | 有效权限裁决点 + 两级缓存 | `app/services/effective_permission_service.py` | 单测覆盖 §2.5 九步各分支、legacy 回落、`active=False` 回落；缓存命中率断言 |
| 3 | 动作守卫 + 覆盖率棘轮 | `app/api/v1/deps.py`、`scripts/check_action_coverage.py` | 单测：有/无权限、shadow/enforce、超管豁免；基线只减不增 |
| 4 | 复合版本号 + 重渲染触发 | `users.permissions_version` + 迁移 + 中间件 + `permEpoch` | 手工：A 改 B 权限 → B 停留在原页 → 下一次任意请求后**按钮自动变化** |
| 5 | 账户创建单事务收口 | `UserCreate` 增 `allowed_menus`；复用 key 校验 | 单测：两次写入变一次；菜单非法 key 返回 400 并列出 |
| 6 | 批量授权（分块 + 可续跑） | `POST /users/batch-permissions` | 单测：三种模式、越界整批回滚、201 个用户分 3 块、失败可续 |
| 7 | 可观测性 + 模块级回滚 | `/metrics` 计数器、`PERM_ENFORCE_MODULES` | 手工：shadow 期计数可见；去掉模块名后该模块立即回 shadow |
| 8 | 机器码联动可视化 | 勾选界面 `denied.machine` 置灰 | 手工：断授权后置灰项与后端 403 完全一致 |

顺序：0-2 先合（纯后端、零界面变化、可 shadow 运行）；3-4 随后；5-8 视排期。
**每个阶段都必须能独立回滚**，不允许"要上一起上"。

## 8. 风险与不做什么

**风险**

1. **两套守卫结论不一致**：`grant_guard` 用 URL 前缀映射模块，`require_permission` 用显式声明。
   必须保证同一接口两边结论一致，否则会出现"模块守卫放行、动作守卫拦"的诡异 403。
   缓解：按 §4.1.2 收口到同一份 `request.state.effective`，而不是各算各的。
2. **存量数据兼容**：`allowed_menus` 为 `NULL` 与 `[]` 语义相反，批量操作极易写错。
   缓解：批量接口显式要求 `mode`，不提供"默认覆盖"。
3. **权限目录漂移**：新页面忘记登记 `actions` → 该页面永远勾不出动作。
   缓解：§1.3 的门禁（page 必须声明 actions）。
4. **shadow 期过长**：一直不开 enforce，等于没有动作级防护。
   缓解：§4.6 的可执行判据（shadow 命中 7 天为 0 + e2e 覆盖）与模块级 kill switch。
5. **动作码切换误伤存量用户**（本次评审新增）：端点改判新码后，只持有 `data:create` 的用户立刻 403。
   缓解：§1.2 的 legacy 别名双读，按命中数退场。
6. **动作权限越过模块级授权**（本次评审新增）：现有 `allowed_permissions` 只与角色权限取交集，
   没有与单位矩阵取交集 → "单位给 view、白名单里有 delete"的矛盾状态。
   缓解：§2.5 第 7 步强制 `base &= modules`。
7. **即时生效被高估**（本次评审新增）：刷新 store 不等于界面变化，`v-permission` 依赖重渲染。
   缓解：§5.3 的 `permEpoch` 强制重建。
8. **SQLite 写锁**（本次评审新增）：批量授权一次更新上千行会卡住全站写入。
   缓解：§4.4 的分块提交与可续跑。

**明确不做**

- 不新建 `user_permissions` / `role_permissions_v2` 关系表（与现有字段双写，风险大于收益）；
- 不把菜单 key 换成数字 ID（`MENU_DEFINITIONS` 的 key 已是事实标准，且权限包/账号包都按 key 存）；
- 不做"权限审批流"（超出本期范围，且离线场景没有审批人）；
- 不引入前端权限框架（现有 `v-permission` 四模式已覆盖页面/模块/动作，换框架要重写全站）；
- **不做资源级权限**（如"只能改自己创建的村"）—— 本期只到动作级；`EffectivePermissions`
  的解析器预留 `code:scope` 扩展位，但不实现，避免协议反复改。

## 9. 一页速查

- **一个命名空间**：`module_key ≡ 菜单 page key`（复数），动作码 `<page_key>:<action>`；
  旧的单数码走别名表双读，不再新增。
- **三级粒度**：页面 → 模块 `view/edit` → 动作，逐级收窄，动作不得越过模块级。
- **一个裁决点**：`effective_permission_service.resolve()`，菜单/守卫/预览都调它，两级缓存。
- **一处声明**：`actions` 内嵌在 `MENU_DEFINITIONS` 的 page 条目里，配门禁防漂移。
- **一条铁律**：任何个性化配置只能收窄，不能扩大（`&=` 与 `intersection`，绝不 `|=`）。
- **一个复合版本**：`"{user_ver}.{grant_ver}"` + `permEpoch` 强制重渲染，改完真能看见。
- **一个界面**：组织树下建账户，左树勾页面、右侧勾按钮，不可选项置灰并说明来源。
