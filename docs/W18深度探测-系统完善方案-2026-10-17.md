# W18 深度探测：系统完善方案（务实版）

> 探测时间：2026-10-17　基线：`d7246dc`（v1.12.18），已在 R27/R28 两轮修复交付之后。
> 定位：**不看「还缺什么功能」，只看「已经做的东西会在什么情况下出错/说不清」**。
> 约束：全部结论带 `文件:行号`；关键结论用真实 SQLite 跑过实证（脚本在 `.scratch/w18-deep-probe/_probe_*.py`）。

## 0. 结论速览

前两轮（R27 静态排查 115 条 / R28 修复 + 补漏）解决的是**「代码写错了没有」**。
本轮换个角度问三个问题，得到的结论比逐条找 bug 更值得做：

| 问题 | 发现 | 严重度 |
|---|---|---|
| 同一指标，不同页面算的是同一个东西吗？ | **不是。** 总人口在 dashboard 与 statistics 两处口径不同，实测差 500 人 | **P0（用户拿去汇报会错）** |
| 传了 `data_scope` 参数，就真的隔离了吗？ | **不是。** `_avg_per_capita_income` 收下 `data_scope` 后**一次没用**，4 处调用点全在裸奔 | **P0（越权）** |
| 报表/导出的合计，是总数还是被截断后的数？ | **是被截断的。** `total_villages = len(limit(100) 的结果)` | **P1（数字错）** |
| 备份恢复后连接池刷新了吗？ | **已正确 dispose（两次）。** 初判为缺陷，复核后撤销 | ~~P1~~ 已修 |

**最该先做的 3 件事**：
1. 建**指标字典 + 单一计算层**，把「总人口/总经费/人均收入/村数」每个指标收敛成**一个函数**，全仓只此一份（现在至少 3 套口径并存）。
2. 修 `_avg_per_capita_income` 的**形参不接线**（传了 `data_scope` 却不使用）——这是「看起来已隔离、实际没隔离」的最危险形态。
3. 把 `total_villages` 这类**分页/截断后的 len() 当总数**的写法全仓扫一遍（这是系统性错误，不止报表一处）。

## 1. P0 条目

### P0-1 同一指标两套口径：总人口相差 500 人（跨页面数字打架）

- **位置 A（错）**：`backend/app/api/v1/data/data/dashboard.py:113-133`
  ```python
  # 人口/户数：取最新年份的汇总数据
  latest_year_sub = db.query(func.max(VillagePopulation.year)).scalar()   # ← 全库最大年份
  ...
  .filter(
      VillagePopulation.year == latest_year_sub,                          # ← 只加总该年
      VillagePopulation.supported_village_id.in_(...)
  )
  ```
- **位置 B（对）**：`backend/app/api/v1/data/data/statistics.py:477-502`
  ```python
  # 注释写明「取每个村最新年人口（避免 N+1）」
  pop_subq = db.query(VillagePopulation.supported_village_id,
                      func.max(VillagePopulation.year).label("max_year"))
             .group_by(VillagePopulation.supported_village_id).subquery()
  ```
- **现象**：`village_population` 是「每村每年一行」。取**全库**最大年份再求和，会**漏掉今年还没上报的村**。
- **实证**（`.scratch/w18-deep-probe/_probe_metric_divergence.py`，3 个村、C 村未报 2025）：
  ```
  dashboard/KPI 口径（全库最大年）  : 1950
  statistics 口径（每村各自最新年） : 2450
  差额                              : 500
  ```
- **真实后果**：
  1. 工作台大屏与统计分析页**同时打开显示不同人口总数**，且无任何提示；
  2. 只要有村补报新年份，**总人口会突然跳变**（这次从 1950 → 2450），用户会以为数据丢了；
  3. 年度汇报里引用的数字，取决于截图取自哪个页面。
- **为什么前几轮没发现**：R27/R28 检查的是「有没有加数据域过滤」「有没有防注入」——**两处都加了**。
  没人把两个页面的同一个指标放在一起对数值（单看代码，两处都"看起来合理"）。
- **修法**：
  1. 新增 `backend/app/services/metrics/` 单一计算层，提供 `latest_population_by_village(db, scope)` 等函数；
  2. `dashboard.py` / `statistics.py` / `analytics_service.py` / `ai_service.py` 四处**全部改调它**；
  3. 加**一致性守护测试**：同一 fixture 下，两个端点的 `total_population` 必须相等（这类测试能一次性锁死未来漂移）。
- **改动面**：4 个文件 + 1 个新模块 + 1 个新测试；约 200 行。

### P0-2 形参收下了 `data_scope` 却从未使用（越权但不报警）

- **位置**：`backend/app/api/v1/data/data/dashboard.py:678-708`
  ```python
  def _avg_per_capita_income(db: Session, data_scope: OrgScopeFilter, year: Optional[int] = None) -> float:
      """人均收入: ... 未指定年份时取最大可用年份列的平均值。"""
      try:
          ...
          query = db.query(func.coalesce(func.avg(col), 0))
          if hasattr(AnnualIncome, "supported_village_id"):
              query = query.filter(
                  AnnualIncome.supported_village_id.in_(
                      db.query(SupportedVillage.id).filter(SupportedVillage.is_active == True)  # ← 只过滤软删
                  )
              )
          val = query.scalar()      # ← data_scope 一次都没用
  ```
- **实证**（`.scratch/w18-deep-probe/_probe_income_scope.py`）：
  ```
  data_scope 出现在函数体中: False
  filter_by_org_ids 出现:    False
  含 scope 的行 1: def _avg_per_capita_income(db: Session, data_scope: OrgScopeFilter, ...)  ← 仅签名
  ```
- **对比**：同文件 `_query_village_stats`（第 106 行）**确实**调了 `data_scope.filter_by_org_ids` —— 所以该文件是「一半接线、一半没接」。
- **真实后果**：部门级 admin 与普通用户在 `/dashboard/kpi-trends`、`/dashboard/stats`、`/dashboard/yearly-trends`
  拿到的**人均收入是全库所有村的平均值**（跨组织）。属军审红线 S2 的「跨组织数据外泄」。
- **为什么前几轮没发现**：函数签名里写着 `data_scope: OrgScopeFilter`，**审查看签名会认为已隔离**；
  且 R28 的自动化门禁（`check_*`）扫的是「是否出现危险模式」，不会扫「参数声明了但没用」（静态分析最常见盲区）。
- **全仓精确扫描结论**（`.scratch/w18-deep-probe/_probe_unused_scope_only.py`，AST 级）：
  ```
  数据域形参未使用: 1
    backend/app/api/v1/data/data/dashboard.py:678  _avg_per_capita_income()  unused=['data_scope']
  ```
  **只此一处** —— 说明这不是普遍性腐化，而是一个漏网的孤立缺陷，修复 + 加门禁的成本很低、收益明确。
  （注：另有 108 个函数的 `current_user` 形参未被使用，但绝大多数是 FastAPI 端点的**依赖占位**
   —— 依赖本身已执行鉴权，属合法用法，不能一刀切当缺陷。）
- **修法**：
  1. 函数体内接 `data_scope.filter_by_org_ids(query, AnnualIncome 关联村字段)`；
  2. 加一条**门禁**：新增 `scripts/check_unused_scope_params.py` —— AST 扫描「形参名含 scope 但函数体内零引用」的函数，
     一旦出现即失败。这条能一次性防住同类问题（预计全仓还有若干处）。
- **改动面**：1 个函数 + 1 个门禁脚本 + 测试；约 120 行。

## 2. P1 条目

### P1-1 `len(limit(100))` 当总数：报表总数封顶 100

- **位置**：`backend/app/api/v1/data/data/reports.py:771-782`
  ```python
  villages = villages_query.limit(100).all()
  report_data["villages"] = [...]
  report_data["total_villages"] = len(villages)     # ← 最多 100
  ```
- **现象**：`total_villages` 语义应是「命中总数」，实际是「本页条数」。
- **后果**：村数 > 100 时报表头写「共 100 个村」，而后面的统计表可能写 128 —— 同一份报表内部自相矛盾。
- **同类风险点**（需一并扫）：所有 `total = len(items)` 且 items 带 `limit()` / `offset()` 的写法。
- **修法**：`total` 用独立 `count()` 查询；加 AST 门禁防复发。

### P1-2 未关联村的经费（`village_id IS NULL`）无条件纳入统计

- **位置**：`backend/app/api/v1/data/data/dashboard.py:184-189`、`:629`
  ```python
  query = query.filter(or_(
      Fund.village_id.in_(village_query),
      Fund.village_id.is_(None),        # 未关联帮扶村的经费也纳入统计
  ))
  ```
- **问题**：`village_id IS NULL` 的经费**没有任何组织归属判据**，被无条件计入所有用户可见的合计。
  注释写的是「与原语义完全一致」——即**沿用了一个未审计的口径**。
- **后果**：非管理员看到的「总经费」包含其它组织的未关联村经费金额。
- **修法**：改为按 `Fund.organization_id` 判域（Fund 有 organization_id），无归属则仅全局管理员可见。

### P1-3 诊断包不含「业务是否在正常跑」

- **现状**：`backend/app/api/v1/system/diagnostics.py` 的快照覆盖
  `版本/平台/迁移/数据库/日志/资源`（`_build_snapshot` 第 128 行起），**全是基础设施**。
- **现场最常问的三句，诊断包里答不出来**：
  1. 「昨晚备份成功了吗？」→ 需 `last_backup_at / last_backup_status`；
  2. 「提醒/审批提醒为什么没发出来？」→ 需调度器 `last_run / next_run / last_error`；
  3. 「导入导出为什么失败？」→ 需最近失败任务与原因（现有任务表可查，但未进诊断包）。
- **修法**：`_build_snapshot` 增加 `business` 段（备份状态 / 调度器状态 / 最近失败任务），
  同样遵守「只出类名不出原文」的脱敏边界。
- **代价**：小（读现有表即可），收益是**把「打电话问开发」变成「导出诊断包」**。

## 2b. P1 条目（离线/现场维度补充）

### P1-4 ~~恢复备份后不重启会继续用旧连接池读旧库~~ —— **复核后确认已修，本条撤销**

> 探测初判为缺陷，写报告时按源码复核后**撤回**。保留记录以说明"看起来像缺陷、实际已做对"的判断过程。

- **初判依据**：`backend/app/api/v1/system/backup.py:753-763` 只提示「建议重启应用以确保数据库连接正确」，
  看起来像是把收尾工作交给了用户。
- **复核结果（推翻初判）**：真正的收尾在服务层且已做对 ——
  `backend/app/services/backup_service.py`：
  ```python
  # 623: 释放后由下方 engine.dispose() 一并关闭池内连接
  # 630: engine.dispose()
  # 647: copy 后再次 dispose: 清理恢复窗口期间新建的池连接,
  # 648: #      使后续请求重新打开已替换的数据库文件
  # 651: _engine.dispose()
  ```
  即：替换数据库文件**之后**又 dispose 了一次，确保恢复窗口期间新建的连接也被作废。
  这是正确做法（两次 dispose 分别对应"替换前"与"替换后新建"两类连接）。
- **结论**：无需改动。API 层的「建议重启」提示属于保守兜底文案，不是缺陷。
- **留下的经验**：判定这类问题**不能停在 API 层**——必须顺着调用链看到 service 层真正的收尾动作。

### P1-5 卸载/重装后「删除用户数据」的口径只在文档里，没有运行时自检

- **背景**：R28 H11 已修 `nsis-hook` 的目录口径（改为真实 `userData`）。
- **遗留**：三处口径（`electron/main.js` 的 userData 设定、NSIS 钩子、`backend/app/utils/paths.py`）
  依赖**人工保持一致**，无任何自动校验；下次任何人改其中一个都会静默漂移。
- **真实后果**：卸载时删错目录 → 用户数据残留（隐私）或删空用户数据（灾难），且**只有卸载时才暴露**。
- **修法**：加一个 CI 门禁脚本 `scripts/check_userdata_path_consistency.py`：从三处源码里抽取路径表达式并比对，
  不一致即失败。这是「用门禁替代记忆」的典型场景。

### P1-6 数据包/备份文件**无累计清理**，长期运行会撑满磁盘

- **现状**：备份有 `cleanup_by_retention_days`（`backup_service.py:922`，调度器与手动端点均已接线），
  **但数据包导出目录（`data-packages`）没有对应的保留策略**。
- **真实后果**：单机离线环境下用户频繁导出数据包（每个数十~数百 MB），一年后磁盘满 →
  备份失败、导入失败，且首页不会提前预警。
- **修法**：复用备份的保留策略实现（按天数/个数），在诊断摘要里暴露「数据包占用空间」，超阈值提示。

## 3. P2 条目

### P2-1 全仓无「指标字典」，同一概念多处定义
共享词/口径散落：`万元 vs 元`、`总人口 vs 常住人口`、`拨付 vs 使用`。建议在 `CONTEXT.md` 增加「指标字典」小节，
每个指标写明：定义、公式、数据源表、口径负责人。这是**用文档换掉一类 bug**。

### P2-2 前端错误提示仍有直连 axios 文案的路径
`fe` 已在 R28 统一 `getErrorMessage`，但建议加**门禁**：ESLint 规则禁止 `.catch(e => ElMessage.error(e.message))` 形态，
否则新代码会重新长出旧问题。

### P2-3 离线环境自检项偏少
启动自检建议补：磁盘剩余空间阈值、系统时钟与数据最新日期偏差、数据库文件可写、`ENCRYPTION_KEY` 可解密既有密文。
后两项若失败，现在的表现是「运行时某功能莫名报错」，而不是「启动时说清楚」。

## 5. 一句话总结

> 前两轮把「写错的代码」修掉了；这一轮发现**真正贵的缺陷不在代码写错，而在「同一件事有两种写法 / 做了一半」**：
> 同一指标两套口径（P0-1）、同一参数一处用一处不用（P0-2）、同一个人数一处 count 一处 len（P1-1）。
> （探测中另有 P1-4 初判为缺陷，复核后确认已修并撤销——**判断必须下钻到 service 层，不能停在 API 层**。）
>
> 这类问题的解法不是逐条修，而是**给每个概念指定唯一实现 + 加一道能自动发现分叉/半接线的门禁**：
> `check_unused_scope_params.py`（防"传了不用"）、指标一致性测试（防"两套口径"）、
> `check_userdata_path_consistency.py`（防"三处漂移"）。
>
> **如果只做一件事**：做 B1 的 P0-2 修复 + 那道门禁脚本 —— 它能在 CI 里持续抓出"看起来隔离了、其实没有"的地方，
> 而这类缺陷是所有审计里最难靠人眼发现、后果又最重的（越权且无告警）。
