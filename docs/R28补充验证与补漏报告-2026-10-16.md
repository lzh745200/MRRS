## 1. 已修复缺陷

### F1（阻塞级）后端全量跑必死的死锁用例

- **文件**：`backend/tests/unit/test_task_queue.py:260` `test_worker_timeout_error_continue`
- **根因**：mock 用 `AsyncMock.side_effect = asyncio.TimeoutError()`（**异常实例**）。被 await 时
  协程**同步立即抛出、从不挂起**，于是 `asyncio.wait_for` 不会让出事件循环 →
  `LocalTaskQueue._worker` 的 `while self._running` 退化成**不 yield 的紧循环** →
  用例里的 `await asyncio.sleep(0.05)` 与 `q.stop()` 永不执行 → 死锁。
- **影响**：`pytest-timeout`(thread 模式) 超时后 dump 全部线程栈并**直接终止整个 pytest 进程**，
  因此全量跑在 ~91% 处被杀，**无汇总、无覆盖率** —— 上一轮"覆盖率 99.71%"其实是残缺口径。
- **修复**：side_effect 换成"先 `await asyncio.sleep(0)` 再抛"的协程，让出点恢复；
  并补两条真实断言（`worker 仍存活` + `get.await_count >= 2`）锁住 `continue` 分支语义。
- **验证**：修复前单跑挂起（`+++ Timeout +++`）；修复后
  `tests/unit/test_task_queue.py` → **45 passed in 5.12s**。

### F3 集成测试夹具的两处竞态/污染（可复现）

- **文件**：`backend/tests/integration/conftest.py`（`setup_database`，`autouse` 函数级）
- **现象**（修复前，`tests/integration/test_comprehensive_functional.py` 单独跑即可复现）：
  ```
  ERROR at teardown of TestWorkLogsComprehensive.test_list_work_logs
  E  sqlite3.OperationalError: database table is locked   [SQL: DROP TABLE permission_packs]
  ERROR at setup of TestWorkLogsComprehensive.test_calendar_view
  E  sqlite3.IntegrityError: UNIQUE constraint failed: users.username
  → 73 passed, 1 error
  ```

- **根因（两层）**：
  1. `app/core/audit_middleware` 有一个进程内 daemon 线程每 5s 走 `SessionLocal()` 写 `APIAccessLog`。
     本 conftest 把 `SessionLocal` 换成了 `TestingSessionLocal`，而测试库是
     `sqlite://` + `StaticPool`（**全进程共用同一条 DBAPI 连接**）——该线程与 teardown 的

  2. `drop_all` 抛错后，排在它**之后**的全局状态恢复（`dependency_overrides.clear()` /
     `SessionLocal`/`engine` 还原 / `DATABASE_URL` 等环境变量还原）**全部被跳过** →
     污染其后所有用例（含会继承 `os.environ` 的子进程用例）。
- **修复**：teardown 先 `_stop_audit_flusher()`（置停止事件 + 排空缓冲 + join），

- **位置**：`app/services/machine_code_service.py:57 _collect_wmic_info()`、`:237`、`:252`

  现存通行码/激活码集体失效。这属于「产品需先定迁移策略（读时兼容旧码 / 写时新码双轨）」的
  变更，风险远大于收益，**不在本轮代码级修复范围**。已在报告登记，建议单独立项。
- **本轮已做**：确认降级路径正确、超时齐全，因此不构成可用性缺陷。

### F6 本地打包把**旧构建指纹**打进了安装包

- **文件**：`backend/app/core/_build_info.json`（gitignore 的构建期生成物）
- **现象**：本地 `PyInstaller` + `electron-builder` 出的安装包，启动后 `/health` 返回
  ```json
  {"status":"ok","version":"1.12.12","git_hash":"790bf99", ...}
  ```
  而本次构建的版本是 **1.12.17**、HEAD 是 **6a6bf30**。
- **根因**：`_build_info.json` 是 CI 在打包前由 `scripts/generate_build_info.py` 覆写的
  构建期产物（本地被 gitignore）。工作区里残留的是 **v1.12.12 那次 CI 构建**的文件
  （`build_time: 2026-10-03`、`builder: ci`），本地打包直接把它打进了产物 →
  发布件对外谎报版本与提交号。`app/core/build_info.py::get_build_info` 优先读该文件，
  只有文件缺失时才回退 `settings.PROJECT_VERSION`。
- **修复**：打包前补跑 CI 的同一步骤 `python scripts/generate_build_info.py v1.12.17`
  → 文件变为 `{version: 1.12.17, git_hash: <release commit>, build_time: ..., builder: ci}`，
  再重跑 PyInstaller 与 electron-builder。
  **顺序要求**：`generate_build_info.py` 里的 `git_hash` 取 `git rev-parse --short HEAD`，
  因此必须在**发布提交之后**再跑，否则指纹会指向提交前的历史。
- **验证**：重打包后对 `win-unpacked` 内的 `assistance-backend.exe` 做真实启动冒烟（见 §6）。

### F7 另一处 `importlib.reload` 造成的跨用例污染（数据域用例在批量跑下 401）

- **文件**：`backend/tests/unit/test_branch_gaps_group_d.py:668`
  `test_static_mounts_skipped_when_dirs_missing`
- **现象**（分片跑 S2 时复现，单跑全绿）：
  ```
  FAILED tests/unit/api/test_data_quality_auth_scope.py::TestValidateRulesDataScope::test_admin_sees_only_own_org
  FAILED tests/unit/api/test_data_quality_auth_scope.py::TestValidateRulesDataScope::test_super_admin_sees_all
  E  AssertionError: {"detail":"未提供认证凭证"}   assert 401 == 200
  ```
- **根因**：该用例用 `importlib.reload(app.main)` 来重跑模块级静态挂载逻辑。
  reload 会**重建 `FastAPI` 实例**并把模块属性 `app` 重新绑定到新对象 —— 原实现只在
  `finally` 里再 `reload` 一次「还原模块状态」，注释写的是"还原"，实际**只换成了另一个新实例**。
  而 `tests/unit/api/test_data_quality_auth_scope.py`（以及根 `conftest` 的 `client` 夹具）是
  **模块导入期就 `from app.main import app`** 的旧引用：依赖覆盖（`dependency_overrides`）
  打在旧实例上，`TestClient` 却打到新实例 → 认证覆盖失效 → 401。
  这与 2026-09 已在 `tests/unit/test_branch_final_core_api.py` 修过的
  "reload 无法恢复对象身份、必须回填 `__dict__`" 是同一类缺陷，本处被漏掉。
- **修复**：按同一模式 —— reload 前快照 `dict(main_mod.__dict__)`，结束后
  `main_mod.__dict__.clear(); update(original_ns)` 回填原命名空间，**恢复对象身份**。
- **验证**：
  - 修复前：`test_branch_gaps_group_d.py + test_data_quality_auth_scope.py` → **68 passed, 2 failed**
  - 修复后：同样组合 → **70 passed**
  - 分片跑（S2 前 2000+ 用例 + api + interfaces）修复前 **2 failed, 2041 passed**；
    修复后重跑见 §5。

同一份代码，CI 与本地串行的结论会相反。本次实测：

并以 `calls >= 13` 断言证明真的发生了回绕（防止弱断言）。
另扫全仓确认：`app/` 下含随机取用的控制流分支**仅此一处**

**本地跑法与 CI 的差异（重要，避免误读）**：本机沙箱在**覆盖率插桩下**会出现偶发
