## 0. 结论速览

| 问题                            | 实测结论                                                           | 严重度               |
| ----------------------------- | -------------------------------------------------------------- | ----------------- |
| 换机 / 用户目录损坏后，密钥文件读不出来会怎样？     | **静默生成新密钥并覆盖原文件**，旧密钥永久消失，历史 PII 全部解不开                         | **P0（数据毁灭，且无告警）** |
| 备份包能独立恢复吗？                    | **不能**。包内只有 `db + backup_info.json`，密钥不在包里；而自动备份本身又用同一把运行时密钥加密 | **P0（灾难恢复断链）**    |
| 有没有「密钥导出/托管」这条退路？             | **没有**。全仓无此能力，文档也从未要求单独保存密钥                                    | **P0（同上，无兜底）**    |
| 启动预检说能发现「既有密文解不开」？            | **做不到**。原实现只做「自己加密、自己解回来」的自证，密钥被换掉照样通过                         | **P1（已修）**        |
| 恢复旧版本备份后不重启会怎样？               | schema 不迁移，新代码查新列 → `no such column`；接口只回「建议重启」                | P1（未修，有方案）        |
| 审计日志能证明没被改过吗？                 | **不能**。无哈希链、无锚点，直接改库即改历史                                       | P1（军审场景）          |
| `datetime.now()` 有没有写进 UTC 列？ | 全仓 143 处，**只有 1 处**真的写进了 UTC 列（备份记录）                           | P2（已修）            |

**一句话**：这个系统对「代码正确性」的防护已经相当厚（两轮修复 + 6 道棘轮门禁），  
但&#x5BF9;**「数据还能不能读」**&#x51E0;乎没有任何运行时证据——密钥丢了不报警、备份不自包含、  
审计日志不可证。这类问题的共同点是：**平时完全看不出来，出事时无法补救**。

## 1. P0-1 密钥文件不可读时，静默重建并覆盖（实测）

### 位置

`electron/main.js`（修复前 `getOrCreateSecrets()`，第 110–146 行）

```js
if (canEncrypt) {
  try { data = JSON.parse(safeStorage.decryptString(raw)); }
  catch (_) {
    try { data = JSON.parse(raw.toString('utf-8')); _writeSecrets(data, true); }
    catch (__) { data = {}; }        // ← 读不出来就当"没有"
  }
}
...
if (data.SECRET_KEY && data.CSRF_SECRET_KEY) { ... return data; }
const secrets = { SECRET_KEY: ..., CSRF_SECRET_KEY: ..., ENCRYPTION_KEY: crypto.randomBytes(32)... };
_writeSecrets(secrets, canEncrypt);   // ← 直接覆盖原文件
```

### 实测（`.scratch/w18b-probe/_probe_secrets_rebuild.js`，抽取真实函数进 vm 沙箱）

修复前（`git show HEAD:electron/main.js`）：

```
=== 场景 2：换机 / DPAPI 解不开（文件不是 JSON）===
  FAIL  产生了隔离备份                              → false
  FAIL  备份内容 == 原始字节（旧密钥可事后取回）      → NO_BACKUP
=== 场景 3：文件损坏（JSON 截断）===
  FAIL  产生了隔离备份                              → false
=== 场景 4：能解析但缺关键项（只剩 ENCRYPTION_KEY）===
  FAIL  产生了隔离备份                              → false
结果: 6 项失败
```

### 触发条件（都不罕见）

1. **换 Windows 账号 / 重装系统 / 迁移到新机器**：`safeStorage` 是 DPAPI 绑定用户+机器的，     
   换了环境就解不开 → 走 `data = {}` → 覆盖；
2. **用户目录被杀软/清理工具动过**，`secrets.json` 变成截断文件；
3. **老版本密钥文件只剩部分字段**（历史升级残留）→ 缺 `SECRET_KEY` → 覆盖。

### 真实后果（为什么是 P0）

- `secrets.json` 里的 `ENCRYPTION_KEY` 是 `users.phone`、`village.id_card`、`village.phone`、    
  `school/project/organization.contact_phone` 等 **9 张表加密列**的唯一解钥（ADR-0005）；
- 覆盖后：应用照常启动、登录、列表正常，**只有身份证号/电话变成 `enc.v1:...` 乱码**；
- 旧行为只留一行 `console.warn`，用户与现场运维都看不到 —— 事后连"是什么时候坏的"都查不出来；
- 更致命的是**原文件被覆盖**：即使事后想用备份里的旧密钥救，也再没有那把钥匙。

### 已修（本轮）

`electron/main.js`：

- 新增 `_quarantineSecretsFile(reason)`：写新密钥前，把原文件**原样另存**为    
  `secrets.json.<reason>-<时间戳>.bak`（先 `copyFileSync`，失败再 `renameSync`）；
- 覆盖前区分三种不可用原因（`unreadable` / `incomplete` / `read-error`），任一命中即隔离；
- 新增 `getSecretsQuarantineInfo()`；`app.whenReady()` 里检测到隔离就**弹窗告知**    
  （含备份路径与"先别继续录敏感数据"的处置建议），并写入诊断日志。

修复后同一脚本：**12 项断言全 PASS**（含"备份字节 == 原始字节"、只读磁盘时"不谎报备份成功"）。

> 这是本轮最值得做的一处：**改动只在 Electron 主进程（CI 只做 `node --check`），>   
> 风险面极小，但挡住的是不可逆的数据毁灭路径。**

## 2. P0-2 备份包不自包含：换机后连备份都打不开

### 实测（真实备份包）

```
backups/backup_20260813_195718_280.zip
条目数: 2
  data/rural_revitalization.db
  backup_info.json
含密钥文件: []
```

生成逻辑：`backend/app/services/backup_service.py:372`（只写 db）与 `:389-396`（只写元信息）。

### 两个独立的断点

1. **自动备份是加密的，口令也在运行时密钥里**：     
   `backup_scheduler.py:137` 用 `get_or_create_secret("BACKUP_ENCRYPTION_KEY")` 作口令，     
   `backup.py:81-96` 恢复时自动取同一把 → 本机恢复没问题；     
   **但机器没了，口令也跟着没了** → 备份包连解开都做不到（不是"解不开 PII"，是**整个包打不开**）。
2. **即使包是明文的**，恢复出来的库里 PII 仍是密文，而 `ENCRYPTION_KEY` 不在包里     
   → 身份证号/电话全部乱码。

### 建议方案（B2，未实施，需你拍板）

| 选项                     | 做法                                                                                                 | 代价            | 风险                          |
| ---------------------- | -------------------------------------------------------------------------------------------------- | ------------- | --------------------------- |
| **A. 备份清单加密钥指纹**（推荐先做） | `backup_info.json` 增 `pii_key_fingerprint`（SHA-256 前 16 位，不泄露密钥）；恢复时比对，不一致就在响应里明确标注 `key_mismatch` | 1 个字段 + 1 段校验 | 无（不改密钥存放位置）                 |
| **B. 单独的「密钥托管」动作**     | 管理员显式导出 `key-escrow-<日期>.json`（口令保护），**不进备份包**，按保密要求另行归档                                           | 新端点 + 前端 + 审计 | 中：等于多一份密钥副本，必须配审批与审计        |
| C. 密钥直接进备份包            | 简单                                                                                                 | 低             | **不建议**：备份包一旦外流，等于库和钥匙一起给出去 |

> 现实约束：这是**军审场景**，密钥副本本身是敏感物。建议 A 先做（只做"能不能读"的判定，>   
> 不产生新副本），B 走审批流程再做，C 不做。

## 3. P0-3 没有「密钥托管」这条退路，文档也没写

- 全仓检索 `密钥备份|备份密钥|导出密钥` → **0 命中**（backend / frontend / docs 全部）；
- `SecretsManagement.vue` 只提供「轮换 / 创建 / 撤销 / 清理」，    
  **轮换是把旧密钥作废**，对历史密文没有任何回填或再加密能力；
- `docs/adr/0005-pii-encryption.md` 只说明"多机部署应配置相同 ENCRYPTION_KEY"，没有    
  "密钥丢了怎么办"的处置流程。

**结论**：P0-1 的隔离备份是"止损"，但没有"恢复"路径 —— 拿到 `.bak` 之后，现场没有工具  
把旧密钥重新装回去、也没有批量重加密的脚本。建议在 B2 里一并补：

1. `scripts/restore_pii_key.py`：从 `.bak` 取回 `ENCRYPTION_KEY` 写回运行环境（带二次确认与审计）；
2. 或 `scripts/reencrypt_pii.py`：旧密钥 → 新密钥的**批量重加密**（先 dry-run 统计行数，再执行）。

两者都要能在**不启动 Web 服务**的情况下跑（现场常常是"服务能起但数据不能看"）。

## 4. P1-1 启动预检的加密探针是「自证式」（已修）

### 原实现（`app/startup/preflight.py:96`，第一轮 W18 新增）

```python
token = encrypt_pii(probe)          # 用当前密钥加密
ok = decrypt_pii(token) == probe    # 再用当前密钥解开
return {"status": "ok" if ok else "warning"}
```

注释写的是「PII 加密密钥不可用 —— 既有密文解不开（换机/换 ENCRYPTION_KEY）」，  
但这段代码**永远发现不了换密钥**：新密钥对新数据本来就是自洽的。  
这是典型的「做了个检查，但检查的不是那件事」。

### 已修

- 新增 `_sample_existing_ciphertext()`：裸 SQL 取**一条真实存量密文**    
  （`SELECT phone FROM users WHERE phone LIKE 'enc.v1:%' LIMIT 1`；    
  必须裸 SQL，因为 `EncryptedText` 会把 `LIKE` 的模式串也加密掉）；
- `_check_encryption_key()` 改为两段式：**自洽 + 存量可解**；    
  解密失败时 `decrypt_pii` 会原样返回密文（不抛异常），据此判定 `existing_ciphertext_undecryptable`；
- 取不到样本（新库）按 `ok` 处理，不制造假告警；取样异常一律吞掉（预检不允许因单项失败而崩）。

### 诊断包同步可见

`diagnostics._business_snapshot()` 新增 `pii_encryption` 段：  
`{key_fingerprint, status, reason, existing_ciphertext}`。  
指纹用 `pii_crypto.key_fingerprint()`（SHA-256 前 16 位），**只用于比对，不泄露密钥** ——  
以后现场问「两台机器是不是同一把钥匙」，导个诊断包就能答。

## 5. P1-2 恢复旧版本备份后不迁移 schema（未修，方案已明确）

- `main.py:527` 在**启动时**执行 `_run_alembic_upgrade()`；
- 但恢复是在**进程内**替换数据库文件（`backup_service._restore_database_from_backup`），    
  之后并没有再跑迁移，接口只回一句「建议重启应用」（`backup.py:753-762`）；
- 结果：把一年前的备份恢复到新版本程序上，**不重启就继续用** → 新代码查新列    
  → `no such column` 之类的运行期错误，且报错位置与"刚做过恢复"看起来毫无关系。

**建议**：`_restore_database_from_backup()` 成功后，在同一 try 块内调用  
`app.main._run_alembic_upgrade()`，把 `schema_upgraded: true/false` 回给前端；  
失败不回滚数据文件（数据本身是好的），但明确告知"请重启"。  
顺带把「建议重启」从"建议"改成"必须"的措辞分级（连接池已 dispose，重启只为迁移与句柄）。

## 6. P1-3 审计日志不可证：没有哈希链（军审场景的真缺口）

`app/models/audit.py` 的字段是纯业务字段（`user/action/resource/old_value/new_value/...`），  
**没有任何完整性字段**。SQLite 文件在用户机器上，用 `sqlite3` 一条 `UPDATE` 就能改历史，  
且改完与原始数据毫无区别 —— 审计要证明的恰恰是"没被改过"。

**建议（B4，需评估是否本轮做）**：

1. 追加 `prev_hash` / `entry_hash` 两列（`entry_hash = sha256(prev_hash + 规范化字段)`），     
   写入时串成链；
2. 每日把**链头哈希**写入一个独立追加文件（`logs/audit-anchor.log`），     
   这样即使整表重算，锚点也对不上；
3. 提供 `scripts/verify_audit_chain.py`（校验断点位置），并挂到诊断包；
4. 迁移成本：新增两列 + 存量行**不回溯**（从启用日起建链，历史段标记 `legacy`）。

> 这条不建议"顺手做"：它改的是审计写入的必经路径，必须配套压测与回滚预案。

## 7. P2 条目（已修 / 口径问题）

### P2-1 备份记录 `created_at` 写本地时间（已修）

`backup_service.py:554`：`BackupRecord(created_at=datetime.now())` —— 该列是 `UtcDateTime`  
（UTC 语义），UTC+8 机器上落库即"未来 8 小时"。已改 `utcnow()`。

### P2-2 时区专项扫描：143 处 `datetime.now()`，真缺陷只有 1 处

用 AST 扫全仓（`.scratch/w18b-probe/_probe_naive_now.py`），按「关键字实参/属性赋值/字典键」  
三类高置信形态定位，再逐条核对变量来源：

```
高置信命中: 11 处 / 8 文件
  → 逐条核对 now 的定义后，10 处都是 now = utcnow() / datetime.now(timezone.utc)
  → 唯一真缺陷：backup_service.py:554（已修）
```

**结论**：时间基准这条口径**基本是健康的**（`time_utils` 的单一入口起作用了）。  
反过来说，这类"看起来遍地是坑"的扫描，价值不在命中数，而在**证明它是干净的**。

> 建议：把该 AST 扫描固化成门禁（与 `check_unused_scope_params.py` 同风格），>   
> 只报「字面 `datetime.now()` 直接进 `*_at/*_time` 字段」这一种形态，避免噪声。

### P2-2b 顺手补掉一个会让 CI 变红的遗留缺口

`diagnostics._business_snapshot()` 的 5 个 `except` 分支（备份/调度器/任务/数据包/PII）  
此前**没有任何用例覆盖** —— 第一轮 W18 新增这段代码时只验证了正常路径。  
`fail_under=100` 下这会让后端覆盖率门禁直接红。已补  
`TestBusinessSnapshotDegrades`：用 `Boom` 类让四个服务构造即抛，调度器段换成  
"属性访问即抛"的替身（`from package import name` 会先取包属性，塞 `sys.modules[...] = None`  
是拦不住的——这个坑值得记一笔）。补完后 `diagnostics.py` 覆盖率 95.02% → **100%**。

### P2-3 死代码 + 命名错位（数量 vs 天数）

- `backup_service.py:887 cleanup_old_backups(keep_count)` —— **全仓 0 调用点**，    
  且语义是"按份数删"，与真正在跑的 `cleanup_by_retention_days`（按天数）**不是一回事**；
- API `BackupScheduleUpdate.keep_count`（`backup.py:104`，描述"保留备份数量"）    
  实际写入 `backup_retention_days`（`backup.py:538`），前端标签是"保留天数"。

用户看到的是"天数"，行为也是"天数"，**功能没错，但字段名与描述在骗下一个人**：  
新来的开发者按 `keep_count=10` 传"10 份"，得到的是"10 天"。  
建议：字段改名 `retention_days`（保留 `keep_count` 为兼容别名 + 注释），删掉死代码。

## 10. 一句话总结

> 前几轮修的是「算错了」和「写错了」；这一轮发现的&#x662F;**「读不了了」**——>   
> 密钥文件读不出来时系统会**默默换一把新钥匙并把旧钥匙扔掉**，>   
> 而备份包里没有钥匙、文档里没有交代、诊断里也看不出来。
>
> 这类缺陷的共同特征是：**不报错、不崩溃、不影响启动，只让数据变成乱码**，>   
> 因此任何"看日志找异常"的排查方式都发现不了它。
>
> 如果只做一件事：**B1 已经做完的那件事** —— 让密钥文件在任何情况下都不会被覆盖，>   
> 并且把"我换钥匙了"这件事弹到用户脸上。
