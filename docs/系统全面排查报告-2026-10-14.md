## 1. 高危（13 条）

### H1〔服务层〕级联彻底删除的链式 SQL 生成错误 —— 会全表误删 + 漏删子孙
- **位置**：`backend/app/services/cascade_purge_service.py:133`（`_delete_chain`），由 `:170 purge` 调用
- **现象**：对深度 ≥2 的依赖链，`idx>0` 分支执行的是**不带 `:rid` 限定的整表删除**；`idx==0` 分支用根行 id
  去比对中间表主键，锚定错层，实际删不到本行子孙。
- **根本原因**：`_descendant_chains` 返回的链是「由深到浅」（`:126` `list(reversed(new_lineage))`），
  即 `chain[0]` 是最深一跳；但 `_delete_chain` 假设 `chain[0]` 的 parent 就是 root。
- **影响范围**：`supported_villages`/`projects`/`funds`/`schools` 的「彻底删除 / 回收站清除」路径。
  例如 `DELETE FROM funds WHERE village_id NOT IN (SELECT id FROM supported_villages)`
  会删掉所有 `village_id` 悬挂或为空的经费；同时深层子孙残留为孤儿行。**数据不可逆。**
- **修复方案**：`_delete_chain` 统一锚定根行（逐层自根向下用嵌套子查询解析，或按外键图自底向上、
  每层都带 root 限定删除），删掉 `idx>0` 的 `NOT IN` 全表分支；补 3 层链（village→project→fund）断言用例。
- **证据**：
```python
for idx, (table, col, parent, parent_pk) in enumerate(chain):
    if idx == 0:
        sql = (f"DELETE FROM {table} WHERE {col} IN "
               f"(SELECT {parent_pk} FROM {parent} WHERE id = :rid)")   # parent 非 root 时锚定错误
    else:
        sql = (f"DELETE FROM {table} WHERE {col} NOT IN "
               f"(SELECT {parent_pk} FROM {parent})")                   # 无 :rid → 全表删除
```

### H3〔API〕经费明细/预算创建可指定任意 `organization_id`/`fund_id`/`budget_id` → 跨组织写入与资金篡改
- **位置**：`api/v1/fund_budgets.py:190`（`create_budget`）、`:364`（`create_transaction`，关键 `:388-396`）
- **现象**：management 角色可创建预算时填任意 `organization_id`；创建明细时填任意 `fund_id`，

- **证据**：
```python
if data.fund_id:

        fund.used_amount = quantize_money(float(fund.used_amount or 0) + float(tx_amount))
```

### H8〔核心〕`apply_scope_filter` 对 admin 全量放行，与 `filter_by_data_scope` 语义冲突且被批量消费
- **位置**：`core/data_permission.py:519`（`if is_admin(user): return query`）、`:458`；
  对照 `:198 filter_by_data_scope` / `:101-111 get_data_scope`（admin→`OWN_DEPT`）
- **消费方**：`api/v1/funds.py:407,448,531,712,760,1058,1092,1115,1146,1171,1202`、`projects.py:531,546,569,700`、
  `supported_village.py:546,639,688,800`、`validation.py:487`、`effectiveness.py:115,142,182`、

- **现象**：同一个部门级 admin 在资金/项目/受助村**列表与汇总**端点上得到**未过滤的全量数据**，

### H9〔核心〕审计中间件对每个请求追加一次独立数据库写入（写放大 + 单写者锁竞争 + WAL 膨胀）
- **位置**：`core/audit_middleware.py:57-64`、`:101-130`
- **现象**：任何非跳过路径请求结束后都 `run_in_threadpool(self._persist_api_access_log, ...)`，
  内部 `SessionLocal()` + `INSERT api_access_logs` + `safe_commit` —— 连 GET 也产生一次写事务。
- **影响范围**：全站延迟与吞吐、`-wal` 膨胀（同文件 `:19-22` 注释自记实测 22MB 未回收）、
  并发写时 `database is locked` 概率上升。
- **修复方案**：改批量缓冲（累积 N 条或 T 秒后 `bulk_insert`）、或仅记录敏感/写方法、
  或访问日志写入独立库/文件，避免与业务共用单写者。
