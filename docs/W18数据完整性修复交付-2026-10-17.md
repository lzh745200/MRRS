## 1. D1 跨机数据包导入主键碰撞（最高危）

### 缺陷

数据包导出包含自增 `id`（`_export_data_type` 逐列导出，含主键），导入时以**源机 id**
作 `ON CONFLICT` 键：

```python
# 修复前 data_package_service.py:540-546
update_cols = {c.name: c for c in stmt.excluded if c.name != pk_name and c.name in carried}
stmt = stmt.on_conflict_do_update(index_elements=[pk_name], set_=update_cols)
```

两台机器都从 `id=1` 起步 → **必现**（非概率）：
- `overwrite=True`（增量应用路径硬编码）：把本机同 id 的**真实记录整体覆写**成源机数据
  （`organization_id`/`created_at` 一并改写）；
- `overwrite=False`（普通接收默认）：`DO NOTHING` **静默丢弃**导入记录，计数却仍报成功。

**实证（修复前）**：
```
BEFORE local: 1 B机的真实村 org= 2 honors= B机自有数据
AFTER row count: 1
   1 A机的另一个村 org= 1 honors= A机数据     ← 本机数据已消失
```

### 修复

新增业务键判定，主键冲突时按「是不是同一条业务记录」分流：

```python
BUSINESS_KEYS = {
    "supported_villages": ("village_name", "organization_id"),
    "projects": ("code",), "funds": ("code",), "schools": ("code",),
}
```

| 情形 | 处理 |
|---|---|
| 主键空闲 | 直接插入（行为不变） |
| 主键占用 + 业务键**相同** | 同一业务记录 → 依 `overwrite` 更新或跳过 |
| 主键占用 + 业务键**不同** | 是另一条记录撞了 id → **去掉主键后插入**（数据库分配新 id），绝不覆写本机数据 |

**实证（修复后）**：
```
AFTER row count: 2
   1 B机的真实村 org= 2   ← 本机数据完好保留
   2 A机的另一个村 org= 1  ← 源机记录以新 id 插入
```

### 已知取舍（如实登记）

本方案**未做**完整的外键 `id_mapping` 重映射（`smart_conflict_resolver._update_foreign_keys`
已有该能力，但只被 KEEP_BOTH 路径使用）。后果：跨机同步后同一业务记录在两库可能有不同 id，
若源包中子表引用的是源机 id，插入的新行外键可能仍指向旧值。

**建议独立批次**：把 `_update_foreign_keys` 接入 bulk upsert 路径，先建「源id→新id」映射表
再逐类型重写外键。改动面涉及导入链路全部子表，不适合与本批混做。

## 2. D2 全量覆盖导入物理删除

### 缺陷

`excel_importer_service.py` 四处全量导入执行 `query.delete()`（**物理删除**，且不过滤 `is_active`）：

```python
# 修复前：只导入帮扶村
query = scoped_filter(self.db.query(SupportedVillage), SupportedVillage, self.current_user)
query.delete(synchronize_session=False)
```

因 `projects.village_id` / `funds.project_id` / `funds.village_id` 均为 `ON DELETE CASCADE`，
**只导入帮扶村也会把项目与经费一起物理删掉**，且回收站里的软删行同样被抹掉。

**实证（修复前）**：`villages 1 / projects 1 / funds 1` → 全量导入 1 行村后 `projects 0 / funds 0`。

### 修复

改为软删除（符合项目既有软删模式），不触发级联：

```python
def _soft_delete_scoped(self, model):
    query = scoped_filter(...) if self.current_user else self.db.query(model)
    query = query.filter(model.is_active.is_(True))       # 只处理可见行
    return query.update({model.is_active: False}, ...)     # 软删除
```

**实证（修复后）**：`projects 1 / funds 1` 完好保留，村由 1 变 2（旧村软删、新村插入）。

### 测试订正

`test_cov_final_excel_importer_service.py::test_delete_scoped_to_current_user` 原先断言
`delete()` 被调用——**锁定的正是缺陷本身**。已订正为断言「不物理删除 + 改为软删更新」，
并说明旧断言为何错。

## 3. D3 包内组织改写 + KEEP_BOTH 归属丢失

### 缺陷 A：导入可写入他组织（越权）

```python
# 修复前 data_package_service.py:447-454
resolved_org_id = package.org_id
source_org_code = manifest_dict.get("org_code", "")
if source_org_code:
    local_org = self.db.query(Organization).filter(Organization.code == source_org_code).first()
    if local_org:
        resolved_org_id = local_org.id      # ← 无条件覆盖调用者指定组织
```

端点已校验调用者能访问 `package.org_id`，但 service 层随后改写到**另一个**组织 →
部门级管理员把包导进本部门，数据实际写进别的部门。**实证**：`org=B` 导入落库 `org=A`。

修复：包内 `org_code` 仅在**与调用者目标组织一致**时采纳，否则忽略并告警。

### 缺陷 B：KEEP_BOTH 新行 org=NULL

`_PROTECTED_COLUMNS` 故意排除 `organization_id`（防导入值覆盖租户隔离），但 `_keep_both`
插入新行时**没补回**，导致 `org=NULL` —— 数据域过滤下对普通用户等于「导入即丢」。

修复：插入前从冲突的本地记录继承归属，取不到则回退导入记录携带值。

## 4. D6 回收站单条越权物理删除

R28-M3 只给**批量**端点接了 `_reachable_ids`；单条 `/{rid}/restore` 与 `/{rid}/purge`
仍只做「存在 + 在回收站」校验 → 部门级管理员可直接物理删除（**不可逆**）他组织记录。

修复：新增模块级 `_require_reachable()`，接入 preview/restore/purge 三个单条端点。

实现要点（避免"环境异常"被误判成"记录不存在"）：
- 全局管理员 → 直接放行；
- 判定成功且命中 → 放行；判定成功未命中 → 404（越权）；
- **判定本身失败**（模型缺组织列/会话异常）→ 交给调用方既有校验兜底，不误报 404。

## 5. P3-1 模型漏注册致新装缺表

`_MODULE_MAP` 是懒加载注册表；未登记的模型不会进入 `Base.metadata` → **全新安装的
`create_all` 不建表**（升级路径也不会补）。

- `SentimentNews`（`sentiment_news`）：舆情页在新机器上恒 500；
- **另发现** `MachineCodePermission`（`machine_code_permissions`）同样漏注册（原报告未提）。

修复：两者补登记；并补**全量守卫测试** —— AST 扫描 `models/` 下所有真实模型类，
断言全部出现在 `_MODULE_MAP`（防下一个漏网）。

**实证**：新装 `create_all` 建出 **120 张表**，含这两张；扫描未登录模型 **0** 个。
