## 二、P0 问题（必须立即修复）

### P0-1 部门级 admin 跨组织全量可见（数据隔离未收口）

**位置**：`backend/app/core/data_permission.py:395-400`（`get_org_scope`）
→ `:286-311`（`OrgScopeFilter.filter_by_org_ids`）

```python
# get_org_scope（:395-400）
role = getattr(current_user, "role", "user")
# Admin roles or explicit "all" scope → full access
if role in ("admin", "super_admin") or is_superuser(current_user) or user_data_scope == "all":
    return OrgScopeFilter(is_admin=True)     # ← role=admin（部门级）也走这里

# OrgScopeFilter.filter_by_org_ids（:297-298）
if self.is_admin:
    return query                             # ← 不加任何 WHERE，全量返回
```

而同模块 `apply_scope_filter`（`:567-614`）已按 R27-H8 收口为**严格口径**：
只有 `super_admin`/`is_superuser`/`data_scope=all` 才放行，部门级 admin 收敛到「本组织及子树」。

**运行时复现**（真实 SQLAlchemy + SQLite，部门级 admin 挂 org=10，另组织 org=20 有 1 条学校）：

```
=== get_org_scope(部门级 admin) ===
is_admin(user) = True
scope.is_admin = True          <-- 放行全量
scope.org_ids  = []

=== OrgScopeFilter 路径（学校/一户一档/影像库/消费帮扶 在用）===
可见学校数 = 1 ['外组织学校']     <-- 泄漏

=== apply_scope_filter 路径（经费/项目/帮扶村 在用）===
可见学校数 = 0 []               <-- 正确隔离

RESULT: 两套口径不一致 -> 确认漏洞
```

**影响面**：51 处 `filter_by_org_ids` 调用，横跨 6 大业务模块：

| 模块 | 泄漏内容 |
|---|---|
| 一户一档 `households.py`（16 个端点） | 户主姓名、帮扶责任人电话、成员身份证、风险预警 |
| 影像库 `media.py`（5 个端点） | 帮扶现场影像、GPS 坐标、拍摄时间 |
| 消费帮扶 `consumption.py` | 成交金额、供货方、采购方 |
| 帮扶学校 `school.py` | 学生数、联系方式 |
| 地图 / 大屏 `map.py` `bigscreen.py` | 全库地理与统计 |
| 结对 / 捐赠 `pairing.py` `donation.py` | 结对与捐赠台账 |

**修复建议**（一次性覆盖 6 大模块）：
```python
# get_org_scope 改为复用严格口径
scope = get_data_scope(current_user)          # 已含无组织 admin → OWN 的 fail-closed
if scope == DataScope.ALL:                    # 仅 super_admin / is_superuser
    return OrgScopeFilter(is_admin=True)
if scope == DataScope.OWN_DEPT:
    ids, names = _get_org_subtree(db, _get_user_org_id(current_user))
    return OrgScopeFilter(is_admin=False, org_ids=ids, org_names=names)
...
```
同时修正 `dashboard.py:184/450` 的 `has_full_access()` 分支语义（它直接返回 `self.is_admin`，
修好 `get_org_scope` 后自动收敛），并在 `CONTEXT.md` 不变量 1 补记「`OrgScopeFilter` 与
`apply_scope_filter` 同口径」的约束，加回归测试锁定。

### P1-7 后端测试必失败（本地与 CI 双红）

**实测**：`pytest tests/` 跑到 **3863 例时失败停止**（`1 failed, 3862 passed`）：
```
FAILED tests/unit/test_core_hardening_r28_build_info.py::TestHasGitWorktree::test_default_start_points_are_used
assert True is False
```

**根因（已定位到确切机制）**：该测试假设「tmp_path 向上 4 层内无 `.git`」。
但 pytest 的 `basetemp` 建在 **rootdir（`backend/`）之下**：
`backend/pytest-of-Administrator/pytest-91/test_xxx_0`，
向上第 4 层正是仓库根 `C:\military-Rural Revitalization-system`，那里**有 `.git`**：

```
   [0] ...\backend\pytest-of-Administrator\pytest-91\test_xxx_0  .git=False
   [1] ...\backend\pytest-of-Administrator\pytest-91            .git=False
   [2] ...\backend\pytest-of-Administrator                      .git=False
   [3] ...\backend                                              .git=False
   [4] C:\military-Rural Revitalization-system                 .git=True   ← 命中
```

而 `_has_git_worktree` 的窗口恰好是 `(base, *base.parents[:4])` —— 第 4 层在窗口内。

**结论**：**在任何 git checkout 内这个测试都会失败**，CI 第 12 段（final coverage gate）必红。
这不是产品代码缺陷（`build_info.py` 的 4 层窗口对生产路径是正确的），
而是**测试断言依赖环境**。

**修复**（任选其一）：
- 给该测试显式传 `start=tmp_path`（不依赖默认起点），或
- 断言改为「返回 bool」而非「返回 False」，或
- 在 `conftest.py` 把 `basetemp` 重定向到仓库外（`tmp_path_factory` + `--basetemp` 到 `%TEMP%`）。

**附带风险**：pytest 把 `basetemp` 建在 `backend/` 下会在仓库内留垃圾目录
（本次已见 `backend/pytest-of-Administrator/`、`backend/probe_bi*`），
建议在 `pytest.ini` 加 `--basetemp` 指向系统临时目录。

## 六、功能完善建议方案

### 优先级 1：补齐安全基线（阻断发布）

| 动作 | 覆盖问题 | 预估 |
|---|---|---|
| `get_org_scope` 改严格口径 + 回归测试 | P0-1（6 模块读侧泄漏） | 0.5 天 |

### 优先级 2：把「半成品」变成「真功能」

1. **多机同步扩展到 W22 三模块**（P2-2）—— 这是系统「多机协同」定位的核心缺口。
   建议同时引入**同步版本号 + 冲突可视化**（现有 `resolve-conflict` 端点只有后端，前端是否可用需核实）。
2. **增量备份要么接线要么删除开关**（P2-1）—— 当前是「有开关无行为」的误导性配置。
3. **审批审计留痕补齐**（后端报告 #22）—— 审批是本系统合规核心，但 `write_work_log`
   仅 1 处（`retry-apply`）。军事审计要求「谁在何时批了哪笔资金」可还原。
4. **系统级写操作审计入表**（后端报告 #25）—— 定时备份等后台写操作目前只在日志文件，
   `work_logs` 表不可见（因 `user_id` NOT NULL 且无 system actor 承载）。

### 优先级 3：可维护性与体验

1. **合并两套数据权限口径为单一实现**（根因治理）——
   建议 `OrgScopeFilter` 直接委托 `get_data_scope` + `apply_scope_filter`，
   并在 `CONTEXT.md` 不变量 1 登记；`scripts/check_dual_scope.py` 门禁防止再次分裂。
2. **envelope 契约收敛**（审批 19 处 + 里程碑/组织/校验规则裸 list）。
3. **筛选栏 13 处行内宽度改 Token 类**。
4. **API 层契约违规清零**（1 处相对导入 + 3 处 params 形式 + Blob 统一）。
5. **文档与实测对齐**（用例数、文件数、`build-scripts/` 描述、`.venv` 路径）。
6. **孤儿门禁接入 CI**（`scan_bare_returns.py` 等 5 个）。

### 优先级 4：面向业务的增强（可选）

- **一户一档**：预警规则目前「服务层实时计算不落库」，建议增加**预警处置闭环**
  （认领/处理/复核/归档 + 趋势看板），否则预警只是一次性提示。
- **影像库**：已有 EXIF/GPS 就近匹配与多期对比图，建议补**批量导入 + 审核流**
  （现场人员上传→管理员审核入库），否则影像可信度无法保证。
- **消费帮扶**：建议与帮扶村年度板块的 `consumption_support` 做**口径打通**
  （目前两套数据并存，存在「同一个数字两个来源」风险，正是 CONTEXT.md 指标字典要防的）。
- **离线升级**：建议增加**升级前自动体检 + 回滚点**（`upgrade_rehearsal.py` 已存在，
  但未见与真实升级链路强制绑定）。
