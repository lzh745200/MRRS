## 一、修复清单

### P0-1 部门级 admin 跨组织全量可见（军审红线 S2）

**根因**：`data_permission.py` 里两套数据权限口径只收口了一套 ——
R27-H8/R28 把 `apply_scope_filter` 改成严格口径，但 `get_org_scope`（51 处调用：
一户一档/影像库/消费帮扶/学校/地图/大屏/结对/捐赠）仍保留「admin sees all」。

**修复**（`backend/app/core/data_permission.py`）：
```python
# 现在与 apply_scope_filter 同口径
if user_data_scope == "all": return OrgScopeFilter(is_admin=True)      # 显式全局
if is_superuser(...) or normalize_role(role) == ROLE_SUPER_ADMIN:
    return OrgScopeFilter(is_admin=True)                               # 真·全局管理员
if normalize_role(role) == ROLE_ADMIN:                                 # 部门级 admin
    org_ids, org_names = _get_org_subtree(db, org_id)                  # → 本组织及子树
    return OrgScopeFilter(is_admin=False, org_ids=org_ids, ...)
```
fail-closed 补齐：无组织 → 仅本人；无会话 → 至少限本组织；组织树为空 → 至少限本组织。

**验证**（真实 SQLAlchemy + SQLite 运行时复现，修复前后对比）：

| 角色 | 修复前可见 | 修复后可见 |
|---|---|---|
| 部门级 admin（org=县级） | `本组织学校, 外组织学校` ❌ | `本组织学校` ✅ |
| super_admin | 全部 | 全部 ✅ |
| viewer | 本组织 | 本组织（不变） |

### P1-1 未分配审批人的任务任何登录用户可批

**根因**：服务层 `if not standalone and task.current_approver_id not in (None, approver_id)`
对 `None` 无条件放行；端点又未传 `standalone`。

**修复**：
- `approval_workflow_service.py`：`approve_task` / `reject_task` 未分配审批人 → **fail-closed**（仅 standalone 管理员可处理）；
- `approval.py` 两个端点显式传 `standalone=is_admin(current_user)`。

### P1-2 审批提交不校验实体归属

**修复**（`approval.py`）：新增 `_assert_entity_submittable()` + `_APPROVAL_ENTITY_MODELS` 注册表
（fund/project/school/supported_village/policy/rural_work），提交前用 `apply_scope_filter`
校验被审实体在提交人数据域内，不可见一律 **404**（不区分"不存在/无权"，避免探测他组织 id）。

### P1-3 Excel 导入无角色校验 + full 模式可软删本组织并写他组织

**修复**：
- `import_data.py::_import_entities`：`not is_admin → 403`；`mode=full` 且非超管 → 403
  （full 会先软删本组织全部数据）；
- `excel_importer_service.py`：新增 `_assert_org_reachable()`，Excel 的 `organization_code`
  决定落库组织时校验调用者可达性（全局管理员 / 本组织 / 子树内），越界抛错并计入行错误。

### P1-4 `data_scope="all"` 未守护的提权字段

**修复**（`auth/users.py`）：新增 `_assert_can_grant_data_scope()`，
create / update_user / update_permissions **三处**统一收口 —— 仅 super_admin 可授予 `all`
（原实现只校验取值合法性，部门级 admin 可把自己或下属一步变成全库可见）。

### P1-5 门禁盲区：`scan_bare_returns.py` 恒报 0 且未接入 CI

**双重根因**（比审计报告更深一层）：
1. **扫描路径写错**：`dirname(__file__)/app/api/v1` = `backend/scripts/app/api/v1` ——
   **该目录不存在**，glob 返回空列表 → 恒报 0；
2. 单行正则只认 `return {` 同行形态，跨行裸 dict 漏判；
3. 该脚本从未被任何 CI workflow 调用（孤儿门禁）。

**修复**（`backend/scripts/scan_bare_returns.py` 重写）：
- 路径修正为 `backend/app/api/v1`；
- 改用 **AST** 判定 `Return` 节点的值是否为 `ast.Dict`（支持三元/嵌套容器/多行）；
- `utf-8-sig` 读文件（防 BOM 导致整文件跳过 → 假绿）；
- **棘轮门禁**：基线 `backend/scripts/gate_baselines/bare_returns_baseline.json`（当前 244 处 / 46 文件），
  按文件对比，**只允许持平或减少**，新增即 `NEW>0` 失败；
- **接入 CI**：`.github/workflows/pr-checks.yml` 的 static-analysis 作业新增
  `Bare dict return ratchet (envelope contract)` 步骤。

**门禁有效性自检**：临时投放一个裸 dict 文件，门禁输出
`[NEW] newmod.py: 1 处（基线 0）` 且 **EXIT=1** —— 确认能抓住新增违规。

### P1-7 CI 必红测试

**根因**：`test_default_start_points_are_used` 断言「tmp_path 向上 4 层无 `.git`」，
而 pytest basetemp 默认在 rootdir（`backend/`）下，第 4 层恰是仓库根 →
**任何 git checkout 内必失败**（pr-checks 第 12 段 final coverage gate 恒红）。

**修复**：临时根下再下钻 6 层作为起点（仍走"不传参"的默认分支），断言与运行环境解耦。

## 五、未改动项及原因（复核后判定）

| 前端「3 处 `get(url,{params})`」 | **误报，不改** | 均为原生 `request.get(..., { params, responseType })`，`{params}` 是该 API 的正确用法 |

| 244 处裸 dict 全量 envelope 化 | **保留棘轮，不一次性重写** | 其中大量为内部辅助函数返回值/序列化字典（非端点信封），一次性重写会改变内部契约、风险远大于收益；棘轮保证**只减不增**，后续按模块渐进收敛 |

| 增量备份接线 | **未做（属新功能）** | 已在代码中显式标注"开关不会触发增量备份"，避免误导；接线属独立特性项 |

## 六、环境性说明（非代码缺陷）

1. **本机 `TEMP` 目录「可创建不可删除」**（杀软实时扫描持有句柄）→
   `tempfile._get_default_tempdir()` 判定不可用并回退 CWD（`backend/`），
   导致 `mkstemp`/`pytest basetemp` 产物落进仓库。
   已用 `.gitignore` 兜底（`backend/tmp*`、`backend/upload_*.rrs`）；
   并清理了历史累积的 187 个 `bumofu_pytest_appdata_*` 目录。
2. `backend\.venv` 与 `py -3.11` 在本机不可用（指向已删除的 Python311-32）→
   本次全部验证使用 `backend\.venv313`。**建议开发文档统一注明该环境**。
3. 2 项 OCR 用例需要可选依赖 `rapidocr-onnxruntime`，`.venv313` 未安装。
