# 帮扶管理信息系统 · 架构深度评估报告

- **评估对象**：`deliverables/archify/system-map-runtime.html` 所示运行时架构（25 节点 / 32 边 / 6 层）
- **评估方法**：架构图 + 源码交叉验证（main.py / config.py / data_permission.py / task_queue.py / electron/main.py 等），每条结论均有代码依据
- **评估日期**：2026-09-11
- **总体结论**：**架构定位准确、安全基线扎实，主要风险集中在"单进程承载一切"的可用性设计与迁移双轨制技术债**

---

## 一、总体评价

本系统是**离线单机优先**的军事帮扶管理系统，技术栈 FastAPI + Vue3 + Electron + SQLite。这个选型与"无网络、单机部署、审计合规"的业务约束高度匹配——**架构定位本身是合理的，不应按互联网分布式标准苛求**。评估采用"单机系统的最佳形态"为基准。

### 做得好的地方（应保持）

| 亮点 | 证据 |
|---|---|
| 数据权限**单一真源** | `core/data_permission.py` 合并了历史上 4 套并行实现，docstring 明确"all callers must import from this module" |
| 路由 100% 静态注册 | v1.11.3 事故后修复，PyInstaller 冻结包不再丢路由；坏模块启动即 fail-fast |
| 事务安全强制门禁 | `safe_commit` 统一提交 + `security_audit.py --strict` 扫描裸 `db.commit()`，CI 退出码联动 |
| 配置安全基线 | `ENVIRONMENT=production` 默认；SECRET_KEY/CSRF_KEY 留空自动生成并持久化；CSRF 默认开启 |
| 迁移 fail-loud | 生产环境 Alembic 失败**中止启动**而非静默降级；`/health` 暴露 `migration.at_head/error_type` |
| 审计自动化 | SQLAlchemy 事件监听自动留痕 26 个模型，写操作无死角 |
| 桌面端进程守护 | Electron 崩溃重启上限 3 次、端口探测 11 次、safeStorage 加密密钥、渲染进程崩溃恢复 |

## 二、问题清单（现状 → 风险 → 优化方向）

### A. 架构合理性

#### A1.【P0】异步导出任务不持久，重启即丢失
- **现状**：`task_queue.py` docstring 自述"简单的**内存**任务队列"；`async_export_service.py:478` 入队。全仓 grep 无 `resume_pending / recover` 启动恢复逻辑。`export_task` 表虽有记录，但仅存元数据。
- **风险**：用户发起大导出 → 应用重启/崩溃 → 内存任务消失，`export_task` 行**永久卡在 processing**，用户端永远转圈，且无任何提示。单机系统恰恰经常被用户手动关窗重启。
- **优化方向**：启动时（lifespan）扫描 `export_task` 表，将所有 `processing` 状态重置为 `failed(可重试)` 或重新入队；前端轮询到该状态时给出明确提示。约 30 行代码，收益立竿见影。

#### A2.【P1】单进程承载 HTTP + 6 类后台线程，无隔离
- **现状**：`main.py` lifespan 启动备份调度器、WAL checkpoint（每日 03:00）、审批提醒（30 分钟）、DB 健康监控、资源监控、task_queue——全部是**同进程 daemon 线程**（`threading.Thread(target=..., daemon=True)`）。
- **风险**：① 进程崩溃 = 请求与所有后台任务同时中断；② Python GIL 下，大导出/备份的 CPU 密集段会挤压 API 请求延迟；③ daemon 线程在退出时被硬杀，备份可能**写了一半**。
- **优化方向**：短期——给备份/导出加"原子写"（先写临时文件再 rename），保证不产生半截备份；中期——把备份调度器迁到可独立重启的子进程（`multiprocessing` 或独立 exe），与请求处理隔离。

#### A3.【P2】前端 SPA 与 API 同进程同源部署
- **现状**：FastAPI 托管前端静态资源 + SPA fallback，零跨域。
- **风险**：后端故障 = 整个 UI 不可用（用户看到的是白屏/连接失败，而非友好降级）；前后端版本必须同步升级。
- **优化方向**：作为单机系统**可接受**；但建议加一个轻量"后端不可用"降级页（Electron 侧已有 `MAX_URL_LOAD_RETRIES=5` 重试，补一个最终失败后的引导页即可）。未来若扩展 C/S 多机部署，此处需拆分。

### B. 模块划分与职责边界

#### B1.【P1】数据权限过滤依赖"逐点手工调用"，易漏
- **现状**：R26-D10 在 `data/data/reports.py` 里**手工**对村庄枚举/计数调用 `filter_by_data_scope`。同一文件里统计口径靠开发者记得加；`security_audit.py` 的 data_scope 扫描 + 豁免机制正是为兜这个底而存在（豁免项已 10+ 处）。
- **风险**：新增端点漏加过滤 = 跨组织数据泄漏，直接触碰军事审计 **S2 导出隔离红线**；扫描器只能发现"查询了 org 模型却没过滤"，无法发现"过滤条件写错"。
- **优化方向**：把数据域过滤**下沉到服务层/仓库层统一入口**（或 SQLAlchemy 全局 query 事件强制注入），让"忘加过滤"在结构上不可能，而非靠人工纪律 + 扫描器兜底。扫描器保留作回归防线。

#### B2.【P2】services/ 80+ 文件扁平堆放，无子域分组
- **现状**：`app/services/` 下 80+ 个服务文件平铺（对比 `api/v1` 已有 `system/ data/ import_export/ auth/` 分组）。
- **风险**：职责边界靠命名约定维系；新人定位"经费相关有哪些服务"只能靠全文搜索；同名概念（如 data_quality 出现在 api 和 service 两层）易混淆。
- **优化方向**：按业务域分包 `services/{villages,funds,reports,security,system,...}`，在旧路径留 `__init__.py` 重导出保兼容，分批迁移。纯结构性重构，风险低但量大。

#### B3.【P2】生命周期启动逻辑过重
- **现状**：`main.py` 987 行，其中 lifespan 串行执行 10+ 个 `_start_xxx/_check_xxx`，且 `_migrate_missing_columns`（标注 DEPRECATED）仍在启动路径上。
- **风险**：启动耗时叠加（PyInstaller 首启已实测超 3 分钟）；任何一个钩子异常都可能影响启动韧性；入口文件成为"什么都懂一点"的上帝模块。
- **优化方向**：抽 `app/startup/` 包，每个钩子一个独立注册器（含自己的异常兜底与日志），`main.py` 只保留编排清单。

### C. 可扩展性与可用性

#### C1.【P0】SQLite 单文件 = 数据单点，备份缺"可恢复性验证"
- **现状**：已有 WAL 模式 + 每日 03:00 checkpoint + 备份调度器（这套组合在单机里已是良好实践）。但未见**恢复演练**机制——备份文件能否成功还原从未被验证。
- **风险**：数据库文件损坏时才发现备份不可用（常见于备份时库正处于写事务、或文件被占用复制不完整）。对"军事帮扶数据"这是最高等级的数据风险。
- **优化方向**：① 定期自动**恢复演练**：每月把最新备份还原到临时库并跑一致性校验（行数抽查 + 完整性检查），结果写进 `/health` 或运维面板；② 备份落盘到独立物理路径（当前与数据同目录的风险需确认）；③ 明确 RPO/RTO 并写入文档。

#### C2.【P1】Electron↔后端重启策略偏脆
- **现状**：`MAX_BACKEND_RESTARTS=3`，超限后不再拉起；`BACKEND_READY_TIMEOUT=300s`（首启实测超 3 分钟的无奈之举）。
- **风险**：后端连续崩溃 3 次后用户面对黑窗/无响应，无自助恢复路径；杀软扫描导致首启慢时，5 分钟超时若被触发同样卡死。
- **优化方向**：重启计数加"冷却窗口"（如 10 分钟无崩溃则清零）；超限后 UI 显示"修复引导页"（含日志路径、一键重启按钮）而非静默放弃。

### D. 性能瓶颈

#### D1.【P1】SQLite 写并发竞争，观测有余、防护不足
- **现状**：WAL 允许单写多读；但 6 类后台线程 + API 请求共用同一写者锁。已有 query_counter / slow_request_monitor / metrics（观测层完善），未见 `busy_timeout` 与语句超时的显式防护确认。
- **风险**：备份/导出长事务与用户写操作撞锁 → `database is locked` 偶发报错，且难以复现。
- **优化方向**：核查并显式设置 `busy_timeout`（建议 5000ms+）；给后台批处理任务加写锁退避；长事务拆批提交（`safe_commit` 已具备基础）。

#### D2.【P2】全量路由模块级加载
- **现状**：`api/v1/__init__.py` 静态导入全部 46 模块（这是 PyInstaller 的正确取舍），路由加载实测 10 秒。
- **风险**：启动时间线性增长；单机场景可接受，但与 A3 叠加拖慢首启。
- **优化方向**：暂不动（正确性优先）。若后续优化，按"首屏路由优先加载"分组，其余延后——**不建议**为了启动速度回到动态导入。

### E. 安全隐患

#### E1.【P1】CSRF 中间件依赖 `BaseHTTPMiddleware`，注释自认有协议风险
- **现状**：`main.py:144` 注释明确"BaseHTTPMiddleware 会导致 h11 协议错误，仅在明确启用时注册"——即默认开启的 CSRF 保护自身带着已知稳定性代价。
- **风险**：CSRF 与特定请求形态（流式/大 body）组合时可能触发协议层错误；关掉它则失去防护，开则带病运行，形成两难。
- **优化方向**：把 CSRF 校验改写为纯 ASGI 中间件（非 BaseHTTPMiddleware），消除协议冲突；补针对性测试。

#### E2.【P2】`/shutdown` 端点密钥与日志的边界
- **现状**：仅接受 127.0.0.1 + `X-Internal-Shutdown` 密钥，未配密钥时 403 拒绝——设计正确。密钥由 Electron 每次启动随机生成（`crypto.randomBytes`）注入环境变量。
- **风险**：本机任意进程读取进程环境变量即可获取密钥（Windows 下低权限本机用户可枚举进程环境块）。单机场景风险低，但值得知晓。
- **优化方向**：可改用命名管道/本地 socket 或 Electron 直连信号量替代 HTTP 关闭端点；至少在文档中标注该信任边界。

#### E3.【P0→已达标，保持】密钥与 PII 处理
- **现状**：`pii_crypto.py`、`aes_gcm_cipher.py`、`password_encryption_service.py`、runtime_secrets 自动生成持久化、生产环境缺 ENCRYPTION_KEY 直接校验失败——**这条链路是达标且优秀的**，列出仅为说明已评估、无行动项。

### F. 技术债务与可维护性

#### F1.【P1】迁移双轨制是当前最大技术债
- **现状**：Alembic 为主 + `_migrate_missing_columns` 自动补列为兜底（代码内自标 DEPRECATED，靠 `DISABLE_AUTO_MIGRATION=1` 手动关闭，默认**仍开启**）。且历史上已发生过迁移分叉事故（commit `4c1ea8a0`：`data_report_type_001` MultipleHeads 导致打包实例启动失败）。
- **风险**：两套机制对同一 schema 各自为政 → schema 漂移 → 新装实例与升级实例表结构不一致，这类 bug 在打包环境才暴露，排查成本极高（该事故已真实发生过一次）。
- **优化方向**：① 设 `ENABLE_AUTO_MIGRATION` 默认 False，正式下线自动补列；② CI 加"alembic heads 唯一性 + linear history"检查；③ 打包验收流程加"全新装 + 旧版升级"双路径启动验证（工单 9f498517 已开始做，应固化为门禁）。

#### F2.【P2】100% 覆盖率门禁的双刃剑效应
- **现状**：强制 100% 覆盖催生了 `test_cov_gap_fill_*`、`test_coverage_gap_batch8.py` 这类"为覆盖而写"的测试文件与大量 `pragma: no cover`。
- **风险**：测试数量虚高但断言密度不均；维护者面对"改一行要补三个凑覆盖测试"的摩擦，长期会侵蚀测试文化。
- **优化方向**：保留分支覆盖门禁，但建立**显式豁免清单**（豁免需注释理由，类似 security-audit 的做法）；把增量精力转向行为断言测试。

#### F3.【P2】版本号双源风险
- **现状**：报表/模板已收敛到 `settings.PROJECT_VERSION`（本次优化成果），但 `electron/main.js:39` 仍有 fallback 硬编码 `'1.12.1'`。
- **风险**：发版漏改时 Electron 与后端版本号漂移，影响升级日志与 version.json 校验。
- **优化方向**：Electron 构建时从 package.json 注入，删除 fallback 字面量（保留 try/catch 但 fallback 到空并告警）。

## 三、图中缺失的关键模块 / 不合理依赖 / 单点故障

### 缺失模块
| 缺失项 | 影响 | 建议 |
|---|---|---|
| **恢复演练 / 备份自检** | 备份可用性未知（见 C1，最高优先） | 每月自动还原校验，结果暴露到 /health |
| **任务队列持久化/恢复** | 重启丢任务（见 A1） | 启动时恢复或重置 export_task 状态 |
| **降级页面** | 后端故障时用户无引导（见 A3/C2） | Electron 加"后端不可用"引导页 |
| **外部监控出口** | metrics 仅自采集不外发 | 离线定位下**合理**，不视为缺陷；若部署多机需补 |

### 不合理依赖
| 依赖 | 问题 | 建议 |
|---|---|---|
| API 层直调 `filter_by_data_scope`（`data/data/reports.py`） | 安全约束散落在路由层，靠人工纪律维持（见 B1） | 下沉到服务层统一入口 |
| Electron 硬编码版本 fallback | 与 PROJECT_VERSION 双源（见 F3） | 构建期注入单一来源 |
| `_migrate_missing_columns` 仍在启动路径 | DEPRECATED 代码与 Alembic 双轨（见 F1） | 下线，收敛单轨 |

### 单点故障
| 单点 | 等级 | 缓解现状 | 补强方向 |
|---|---|---|---|
| **SQLite 数据文件** | ★★★ 最高 | WAL + checkpoint + 备份调度 | 恢复演练 + 异路径备份（C1） |
| **FastAPI 进程** | ★★ | Electron 守护重启（上限 3 次） | 冷却窗口 + 原子写备份（A2/C2） |
| **runtime_secrets.json** | ★★ | safeStorage 加密 + 自动重建 | 文档标注"删除即全量重新登录/通行码失效"的影响面 |
| **Electron 主进程** | ★ | 渲染进程崩溃自动恢复 | 主进程崩溃 = 全退出，单机可接受 |

## 五、评估边界说明

- 本评估基于架构图 + 抽样源码验证，未逐行审计 80+ 服务与 60+ 模型；D1（busy_timeout）、C1（备份异路径）两项建议落地前需先确认现状配置。
- 评级以"离线单机军事系统"为基准，未套用互联网分布式标准（如多副本、水平扩展）——那些在本系统的部署约束下不适用。
