## 三、逐项风险解决方案

### R1 启动即执行 VACUUM / 全库扫描（P0-高）

- **根本原因**：`backend/app/services/database_health_service.py:108-111` 将 `last_integrity_check / last_quick_check / last_vacuum / last_wal_checkpoint` 全部初始化为 `datetime.min`，`(now - datetime.min) >= interval` 首轮恒真，"每周一次 VACUUM"的语义实际退化为"每次启动 + 每 7 天"。
- **影响范围**：每次进程启动约 1s 后执行 `check_integrity`（全库扫描）+ `quick_check` + `VACUUM`（需独占锁、产生临时文件）+ `wal_checkpoint(TRUNCATE)`；启动窗口内前端首页/仪表盘写请求在 `busy_timeout=10s` 后抛 `database is locked`（500）。`main.py:100` 已因"VACUUM 生成临时文件"禁用另一 VACUUM 源，与本处语义自相矛盾。
- **严重程度**：高 —— 可用性抖动 × 每次启动必现 × 单机桌面高频启停。
- **解决步骤**：
  1. `last_integrity_check / last_quick_check / last_vacuum` 初始化为 `datetime.now()`；`last_wal_checkpoint` 保持 `datetime.min`（轻量、启动即回收 WAL 有益）。
  2. `vacuum_database()` 改为经 `db_coordinator.exclusive_write()` 协调执行，与批量导入等长写互斥。
  3. **同步修改既有断言**：`tests/unit/test_database_health_service.py:319` `test_monitor_loop_datetime_min_initial` 当前把"首轮全触发"固化为预期；改写为"VACUUM/完整性/快速检查首轮不触发、WAL checkpoint 首轮触发"，并新增"运行满 interval 后触发"用例（缩短 interval 注入 fake clock）。**此为行为语义变更，须架构师评审签字。**
- **所需资源**：后端-A 1 人日；无新依赖。
- **验证标准**：
  - 新增用例 3 条（首轮不触发 / 到期触发 / WAL 首轮触发），覆盖率保持 100%；
  - 手工验收：启动应用后 60s 内日志无 `VACUUM` 记录、`/health` 200、启动窗口无 `database is locked`；
  - 全量回归 0 failed。
- **时间节点**：W1（09-16 前）。

### R2 multipart 不受限 + 端点"先整包入内存后校验"（P0-高）

- **根本原因**：
  - 中间件层：`backend/app/middleware/body_size_limit.py:62` `if not is_multipart and not is_large_payload_path and content_length:` —— **multipart 一律放行**（设计假设"端点级 MAX_FILE_SIZE 会控"，但多数端点没有）；
  - 端点层：`await file.read()` 将 SpooledTemporaryFile **全量读入内存后**才比较长度，校验只能"拒绝请求"，不能阻止内存峰值。已核实 12 处端点命中（`import_data.py:241/387/507`、`school.py:250/1010/342/1366`、`supported_village.py:714/1552/1578`、`users.py:859`、`report_templates.py:1248`、`subordinate_reports.py:150`、`data_sync.py:66`、`control_package.py:178/221`）。
  - 解析层：xlsx/zip 为高压缩比容器，`load_workbook`/`zf.read` 全量物化后才知道体积（`excel_importer_service.py:263-278` 校验在解析之后；`subordinate_reports.py:173` 无界 `zf.read`；`policy_import_service.py` 完全无上限）。
- **影响范围**：任一登录用户单请求即可致后端进程 OOM/被系统终止（单机离线场景 = 整个应用不可用）；`/import/entities`、`/subordinate-reports/import` 连事后校验都不存在。
- **严重程度**：高 —— 可用性 × 无需特权 × 单请求即可触发。
- **解决步骤**（三层独立合入，每层均有独立回归）：
  1. **中间件层（W1）**：`BodySizeLimitMiddleware` 对 multipart 启用 `Content-Length` 预检（阈值取路径分级：导入类 512MB / 头像 2MB / 备份恢复 10GB），并增加**流式累计字节**超限判定（不信任 Content-Length），超限返回 413 并主动断开读取。
  2. **端点层（W2）**：在 `app/utils/upload_helper.py` 新增 `read_upload_with_limit(file, max_bytes)`（分块读取 + 滚动计数 + 超限抛 `AppError(413)`，对齐 `files.py:93-101` 既有正确范式），12 处端点逐个替换 `await file.read()`。
  3. **解析层（W2）**：新增 `zip_total_uncompressed_size(zf)` 工具（`ZipInfo.file_size` 求和 ≤ 200MB）；`zf.read(name)` 统一改为限长读取；`policy_import_service` 补 MAX_FILE_SIZE/MAX_ROWS 上限（与 `data_validator_service.py:93-96` 对齐）。
- **所需资源**：后端-B 3 人日；QA 1 人日（构造 2GB 流式 body、高压缩比 xlsx/zip 样本）；磁盘临时空间 ≥ 5GB。
- **验证标准**：
  - 中间件：Content-Length 超限 → 413；流式超限（伪造小 Content-Length）→ 413；
  - 端点：12 处逐一有超限用例；压测 2GB body 打 `/import/entities` → 进程 RSS 峰值 < 500MB 且返回 413；
  - 解析层：高压缩比样本（1MB → 40GB）被拒；全量回归 0 failed、覆盖率 100%。
- **时间节点**：中间件 W1（09-18 前）；端点+解析层 W2（09-25 前）。

### R8 调度任务链无看门狗（P0-高）

- **根本原因**：`backend/app/services/backup_scheduler.py`
  - `:563-571 / 583-591`（daily/weekly）自我重排 Timer **重复 append 到 `_timers`**（每天 +9 个失效对象，慢性泄漏）；
  - `:593-609`（interval）重排 Timer **从不入表**，`stop_backup_scheduler`（:630-637）cancel 不到 → 关闭阶段仍可能触发 DB 写；
  - `_job` **先执行作业、后重排下一次**，无超时/补偿：作业阻塞（如 `src.backup(dst)` 在 BUSY 下无上限重试）即链断，任务永久静默停止；
  - `:543-551` `_scheduler_started` 置位过晚 + 启动中途失败无回滚；`stop` 与 `_job` 并发存在"复活"窗口。
- **影响范围**：自动备份、保留期回收、审批提醒、订阅分发、恢复演练等 11 个任务；最坏情形 = **数据保护能力静默丧失**（备份文件不再更新，唯一线索是一条 WARNING 日志）；重启后任务双份调度。
- **严重程度**：高 —— 静默功能丧失 × 长跑桌面常驻 × 无自愈。
- **解决步骤**：
  1. 封装 `RecurringTimer`（单类收敛 3 种调度形态）：持有自身句柄、`cancel()` 后重排变为 no-op、统一登记/注销、`stop()` 置 `_stopping` 事件 → cancel → `join(timeout)`；
  2. 每个作业包**看门狗**：作业在 daemon 线程执行，主控线程 `join(timeout=N)`；超时记 ERROR 并**仍然重排下一次**（链不断）；
  3. `start_backup_scheduler` 失败回滚已启动 Timer；`_scheduler_started` 的置位/复位与 Timer 表操作统一进同一把锁；
  4. **可观测性**：`/health` 增加 `scheduler: {jobs: {name: {last_run_at, next_run_at, last_status, last_duration_ms}}}`（同时修复 A6"启动失败只降级 warning、/health 不可见"）。
- **所需资源**：后端-A 2 人日；QA 0.5 人日（fake clock 时序用例）。
- **验证标准**：
  - 用例：作业抛异常 → 下次仍被排上；作业 sleep 超时 → 看门狗触发且链继续；`stop()` 后 fake clock 推进 24h 无任何触发；`start` 中途抛错 → 无残留 Timer；重复 start 不双跑；
  - `/health` 含 scheduler 字段且字段随作业执行更新；
  - 结构性断言：所有周期任务必须经 `RecurringTimer`（配合预防措施 P-2 的扫描门禁）；全量回归 0 failed。
- **时间节点**：W2-W3（09-30 前）。

### R6 备份快照回退产出"陈旧但合法"备份（P1-高）

- **根本原因**：`backend/app/services/backup_service.py:283-318` —— `src.backup(dst)` 遇 BUSY 异常后，回退为**直接 copy 主库文件**；此时 `-wal` 中未 checkpoint 的已提交事务全部丢失，但包仍通过 CRC + `integrity_check`（对"陈旧但合法"的库全过）并标记成功。
- **影响范围**：备份时刻存在长读/长写事务（`.rrs` 导入 `exclusive_write(timeout=120)`、导出任务）即触发；灾备恢复后静默回退最近若干次提交。
- **严重程度**：高 —— 数据保护语义被破坏 × 失败信号只在日志。
- **解决步骤**：
  1. 回退路径**删除**：checkpoint 失败 → 直接抛 `BackupIncompleteError` 删半成品（宁可当天无备份，不可假成功）；既有 fail-loud 校验（:380-427）保持不变；
  2. `backup_info.json` 增加 `snapshot_mode`（`online_backup` / `checkpoint_copy`）字段，恢复预览可见；
  3. 调度器对备份失败的告警升级为 ERROR 并在 UI 通知中心可见（复用既有消息通道）。
- **所需资源**：后端-A 1 人日。
- **验证标准**：mock `sqlite3.Connection.backup` 抛 `sqlite3.OperationalError` → 断言抛 `BackupIncompleteError`、备份目录无残包、返回值不含 success；真实长事务并发下创建备份 → 恢复后行数与当前库一致；全量回归 0 failed。
- **时间节点**：W2（09-23 前）。

### R7 恢复窗口与在途请求竞态（P1-中高）

- **根本原因**：`backend/app/services/backup_service.py:583-601` —— `engine.dispose()` 只回收**空闲**连接；已 checkout 的请求会话继续向被替换前的文件写入。`db_coordinator.exclusive_write` 只与 opt-in 长写路径互斥，普通请求小写事务不经此锁。
- **影响范围**：恢复接口被调用时恰有在途写事务（桌面端轮询/心跳即可能命中）→ Windows 直接 `PermissionError`（恢复失败）；POSIX 写入旧 inode（恢复后数据缺一段提交，且无报错）。
- **严重程度**：中高 —— 触发窗口窄 × 后果严重（恢复失败/丢写）× 管理员高频操作场景。
- **解决步骤**：
  1. 新增**维护模式闸门**：`app.state.maintenance` 标志；恢复入口置位，`get_db` 依赖在维护模式下拒绝新写请求（503，读放行）；
  2. 恢复前置等待：复用 `MetricsMiddleware` 在途请求计数，等待归零（上限 10s，超时按既有 `exclusive_write` 流程继续但记录 ERROR）；
  3. `shutil.copy` 加 3 次指数退避重试（Windows `ERROR_SHARING_VIOLATION` 场景）；仍失败 fail-loud 并保留快照（本轮已具备）；
  4. 恢复完成自动解除维护模式（`finally`），响应体带 `maintenance_window_ms`。
- **所需资源**：后端-A 2 人日；QA 1 人日（并发写 + 恢复竞态用例、Windows 真机）。
- **验证标准**：并发 20 写请求期间执行恢复 → 0 个 500（写请求获 503 或成功）、恢复后数据完整性比对一致、无 `.part`/快照残留；Windows 11 真机回归通过；全量回归 0 failed。
- **时间节点**：W3-W4（10-09 前）。

### R3 备份清理吞 `PermissionError` 仍删记录（P1-中高）

- **根本原因**：`backend/app/services/backup_service.py:832, 869` —— `except (FileNotFoundError, IsADirectoryError, PermissionError): pass` 后**无条件** `self.db.delete(config)`。
- **影响范围**：备份 ZIP 正被 `/backup/download` 流式传输、被杀软/同步盘占用时，文件删除失败被静默吞掉但记录照删 → "幽灵备份"永久占盘、UI 无法再删、`cleanup_by_retention_days` 不再重试。
- **严重程度**：中高 —— 磁盘只增不减 × 自动化路径必中。
- **解决步骤**：
  1. 两个清理函数返回值增加 `skipped: [{key, filename, reason}]`；删除失败**保留记录**；

  3. 新增"孤儿备份对账"：`list_backups` 时对记录指向但磁盘缺失的项标记 `missing=true`（供 UI 提示清理）。
- **所需资源**：后端-B 0.5 人日。
- **验证标准**：monkeypatch `os.unlink` 抛 `PermissionError` → 记录仍在、响应含 skipped、无异常上抛；占用解除后再次清理成功；全量回归 0 failed。
- **时间节点**：W1（09-18 前）。

### R4 分片上传无 TTL 清理（P1-中高）

- **根本原因**：`backend/app/services/chunked_upload_service.py:469` `cleanup_expired_sessions()` **全仓无生产调用点**（唯一引用是单元测试）；过期判定（:282-287）只改内存状态不删磁盘；模块级 `_sessions` 字典只增不减。
- **影响范围**：客户端 init 后断网/关页面 → 分片永久残留 `uploads/chunks/<session_id>/`（`MAX_FILE_SIZE` 允许声明 2GB 单会话）；内存 `_sessions` 单调增长；恶意循环 init 可持续写满磁盘。
- **严重程度**：中高 —— 磁盘+内存双泄漏 × 长跑必现。
- **解决步骤**：
  1. 将 `cleanup_expired_sessions` 接入 `backup_scheduler` 周期任务（每 30 分钟）；
  2. 清理逻辑补齐：过期会话 → `rmtree(temp_dir/<session_id>)` + 从 `_sessions` 弹出（处理目录已删的幂等）；
  3. `_sessions` 加上限（建议 200，LRU/最旧优先淘汰并同步删盘）；
  4. 顺带清理 API 层死分支：`chunked_upload.py:111-112`（`upload_chunk` 永不返回假值），`ValueError` 族统一映射 400/409 而非 500。
- **所需资源**：后端-B 1 人日。
- **验证标准**：用例：init + 上传分片 → 伪造过期 → 调度任务执行后目录与内存条目均消失；并发 500 次 init 不超上限；分片大小不匹配 → 400；全量回归 0 failed。

### R5 异步导出过期文件永不回收（P2-中）

### R9 数据包导入失败记录指向已删临时文件（P2-中）

- **根本原因**：`backend/app/services/data_package_service.py:786-801` 校验失败分支以 `file_path=temp_file.name` 建记录；API 层 `data_packages.py:584-585` 的 `finally` 立即 `unlink` 该临时文件。

### R10 本地验证环境可信度（P2-中）

- **根本原因**：① `.venv` 基于 Python **3.11.0**，其 `traceback._byte_offset_to_character_offset` 存在已知缺陷（3.11.1 修复），含非 ASCII 的异常渲染会抛 `UnicodeDecodeError`（历史 2 例"幽灵失败"根因）；② IDE 注入 `PYTHONPATH`/`NODE_OPTIONS` 指向含空字节的损坏 shim（`sitecustomize.py` / `node-language-shim.cjs`），污染每次 Python/Node 启动。
- **影响范围**：不影响产品；影响**本地验证结论可信度**（偶发失败浪费排查、stderr 噪声掩盖真实告警）。
- **严重程度**：中 —— 验证效率与可信度。
- **解决步骤**：
  1. 用 3.11.9+ 重建 `.venv`（`make venv` 新目标：`python3.11 -m venv .venv && pip install -r requirements.txt -r requirements-dev.txt`），`CONTRIBUTING.md` 写明解释器版本要求；
  2. Makefile 增加 `make test-local`：自动前置 `PYTHONUTF8=1`、清空 `PYTHONPATH/NODE_OPTIONS` 再跑门禁（一次性消除环境变量类假失败）；
  3. `.vscode/settings.json` 增加 `terminal.integrated.env.windows` 清空两项注入（团队统一）。
- **所需资源**：DevOps 0.5 人日；重建 venv 需网络与 ~5 分钟安装时间。
- **验证标准**：`python -V` ≥ 3.11.9；`python -c pass` stderr 为空；`pytest tests/unit/test_database_health_service.py -W "error::DeprecationWarning"` 全绿；全量回归 0 failed 0 warning。
- **时间节点**：W1（09-18 前）。

## 六、预防措施（避免同类问题再次发生）

### P-1 棘轮扫描门禁（仿既有 `check_soft_delete_usage.py`，接入 pr-checks `static-analysis`）

| 门禁脚本 | 拦截规则 | 防的是 |
|---|---|---|
| `check_subprocess_encoding.py` | `tests/**` 中 `subprocess.run(...)` 含 `text=True` → 红（必须显式 `encoding="utf-8"`） | Windows GBK 管道解码崩溃（本轮 #13） |
| `check_dir_replace.py` | `rmtree(..., ignore_errors=True)` 后 5 行内出现不带 `dirs_exist_ok=True` 的 `copytree` → 红 | Windows 占用连锁崩溃（本轮 R2.x） |
| `check_unbounded_read.py` | `zf.read(` / `await file.read()` 不带限长包装 → 红白名单制 | zip bomb / OOM（R2） |
| `check_os_exit.py` | `app/**` 中新增 `os._exit(` → 红 | 绕过 lifespan 优雅关闭（R12-5） |

### P-2 调度任务注册表
所有周期任务必须在 `app/services/scheduler_registry.py` 清单登记（name/interval/func/timeout），启动时逐个实例化为 `RecurringTimer` 并暴露到 `/health`；**未登记的后台线程由 `check_scheduler_registration.py` 扫描 `threading.Timer(` 直接调用并拦截**。防"任务写了但没接线/没看门狗"（R8 根因）。

### P-3 上传端点合规清单
`check_upload_endpoints.py`：扫描全部含 `UploadFile` 参数的路由，必须调用 `read_upload_with_limit(...)`；白名单豁免须同行注明理由。防新端点绕过大小上限（R2 根因的制度化）。

### P-4 依赖门禁分级
pip-audit 从"非阻断"改为分级：存在**已发布修复版本**的 high/critical → 阻断合入；无修复版本 → 必须登记豁免理由（与覆盖豁免同约定）。防 CVE 只报不修。

### P-5 评审清单（并入 PR 模板）
- 新增后台线程/Timer：必须回答"谁 stop、谁 join、异常后链是否继续、/health 可见吗"
- 新增 `except ... pass`：必须 `# pragma: no cover`+理由，或改为 fail-loud
- 新增文件写入：必须回答"异常路径谁删、Windows 占用怎么办"
- 新增依赖：`pip check` + pip-audit 分级结论

### P-6 环境一致性
`make venv` / `make test-local` 成为唯一入口；`CONTRIBUTING.md` 固化"解释器 3.11.9+、PYTHONUTF8=1、清空 IDE 注入变量"三件事；Windows 冒烟作业（R13）保证平台差异在 PR 阶段暴露。
