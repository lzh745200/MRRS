## 一、执行摘要（TL;DR）

本方案基于**运行中系统的实测数据**与代码调研，回答三件事：

1. **政策法规「上传文件保存」缺陷 → 已修复并通过双重验证**（工程师实现 + QA 独立回归，12/12 真实 HTTP 场景 + 138 后端单测全绿）。
2. **系统性能 → 已完成压测**，识别出 4 个瓶颈，且瓶颈**不在数据量**（库里仅数百行）而在**请求处理链路**。
3. **完善优化 → 按「立即 / 短期 / 中期」三阶段给出 12 项建议**，每项含现状、方案、收益、工作量与风险。

**核心判断**：先做 3 项低风险高性能改造（预计**单请求固定开销下降 30–50%**、并发能力翻倍），再推进附件体系完善与数据治理。

## 二、政策法规附件保存缺陷（已修复）

### 2.1 缺陷与根因

| 缺陷 | 用户可见现象 | 根因定位 |
|------|--------------|----------|
| **多附件保存丢失** | 一次选 N 个附件上传，保存后重开只剩 1 个 | 前端 `<el-upload multiple>` 支持多选，但后端 `_apply_attachments()` 只取 `clean[0]` 写入 `Policy` 的单文件字段；模型层面没有多附件承载列 |
| **删除附件无效** | 删掉全部附件后保存，附件依然在 | `_apply_attachments()` 首行 `if not urls: return` —— 空数组 `[]` 是 falsy，直接被跳过，等于什么都没做 |

### 2.2 修复内容

| 层 | 文件 | 改动 |
|----|------|------|
| 模型 | `backend/app/models/policy.py` | `Policy` 新增 `attachment_urls`（Text，存 JSON 数组字符串） |
| 后端 | `backend/app/api/v1/policy.py` | `_apply_attachments()` 实现**三分支语义**：`None`→不动；`[]`/全空白→**清空**；非空→**替换**（写全部 URL 到 `attachment_urls`，首个仍填 `file_path/file_type/file_size` 以兼容预览/下载）。`_attachment_urls_of()` 优先解析 JSON（容错非法值）并回退旧 `file_path` 逻辑 |
| 迁移 | `alembic/versions/policy_attachments_001_add_attachment_urls.py` | 新增迁移，`down_revision=contract_attachments_001`，已应用 |
| 前端 | `frontend/src/views/policies/Edit.vue` | 保存时 `attachment_urls: formData.attachment_urls || []`（**始终发数组**，支持清空）；移除逻辑健壮化 |
| 测试 | `backend/tests/unit/test_policy_attachments_cov.py` | 补多附件 / 清空 / 边界用例 |

### 2.3 验证结论

| 验证方 | 方式 | 结果 |
|--------|------|------|
| 工程师自测 | 指定 pytest + flake8 + eslint | 全绿 |
| 主理人复测 | 真实 HTTP 端到端（无 CSRF 绕过） | 4/4 通过 |
| **QA 独立验证** | 自写独立 E2E（12 场景：4 核心 + 5 边界 + 3 容错） | **12/12 PASS** |
| 回归 | 后端 138 单测 / 前端 34 单测 / flake8 / eslint | 全部通过，零告警 |

**结论：修复有效，无需返工。**

## 三、系统性能检测结论

### 3.1 单端点延迟基线（并发 1）

| 端点 | 平均 | p95 | 评价 |
|------|------|-----|------|
| `GET /health` | 23 ms | 32 ms | **偏高**（健康检查正常应 < 5 ms） |
| `GET /policies` | 24 ms | 35 ms | 一般 |
| `GET /supported-villages` | 20 ms | 35 ms | 一般 |
| `GET /schools` | 18 ms | 34 ms | 一般 |
| `GET /projects` | 41 ms | 62 ms | 偏慢 |
| `GET /funds` | 38 ms | 55 ms | 偏慢 |

### 3.2 并发表现（`/policies`）

| 并发 | 吞吐 QPS | 平均延迟 | p95 |
|------|---------|---------|-----|
| 1 | 49 | 20 ms | 34 ms |
| 5 | **97（峰值）** | 49 ms | 68 ms |
| 20 | **82（不升反降）** | **241 ms** | **430 ms** |

**结论**：并发 5 已达吞吐峰值；并发 20 时吞吐**下降**、延迟**劣化 12 倍** → 典型**串行化阻塞**，系统在多用户场景下会明显卡顿。

### 3.3 四大瓶颈

| # | 瓶颈 | 证据 | 影响 |
|---|------|------|------|
| 1 | **中间件栈过重** | `backend/app/main.py` 叠加 **14+ 层** middleware（QueryCounter / SlowRequest / Metrics / Audit / Logger / CSRF / CamelToSnake / Cache / Security / BodySize / RequestID …） | 连 `/health` 都要 23 ms，全端点固定开销抬升 |
| 2 | **每请求 2 个 DB 连接** | `get_current_user`（`security.py:316`）与 `get_db`（`database.py:179`）各建一个 `SessionLocal()` | 连接建立/归还翻倍，认证链路额外查一次用户 |
| 3 | **WAL 未 checkpoint** | 主库 21.3 MB，但 `-wal` 文件达 **22 MB** 未回收 | 读路径需扫描 WAL，读性能与磁盘占用双输 |
| 4 | **Schema 过重** | **127 张表 / 506 个索引**，而实际数据仅数百行 | DB 体积几乎全是结构开销；写操作索引维护成本高 |

## 四、完善优化建议（按优先级）

### 🟢 P1 · 立即执行（1–2 周，低风险高收益）

#### P1-1 中间件链精简与条件化
- **现状**：14+ 层中间件对所有请求无差别生效。
- **方案**：
  1. 将 `MetricsMiddleware` / `QueryCounterMiddleware` 按 `ENVIRONMENT` 开关（生产可关或采样）；
  2. 合并可并行的响应头处理（`SecurityHeaders` + `CacheHeaders` + `CamelToSnake` 合并为一层）；
  3. `/health`、静态资源、`/uploads` 跳过审计与指标中间件（用 path 前缀快速判断）。
- **收益**：单请求固定开销预计下降 **30–50%**，`/health` 有望回到 < 5 ms。
- **工作量**：中（1–2 天，需回归测试）。
- **风险**：低——需确保 CSRF/安全头不被误关。

#### P1-2 消除「每请求双 DB 连接」
- **现状**：认证与业务各开一个 Session。
- **方案**：`get_current_user` 改为复用 `get_db()` 注入的同一 Session（把 `get_db` 作为子依赖传入），认证查询与业务查询共享连接。
- **收益**：DB 连接开销与认证查询次数各减半，高并发下尤其明显。
- **工作量**：中（1 天，涉及依赖注入签名改动）。
- **风险**：中——需确认 Session 生命周期与事务边界（认证只读，安全）。

#### P1-3 WAL 自动 checkpoint 与容量告警
- **现状**：WAL 22 MB 长期未回收。
- **方案**：
  1. 复用已有 `db_maintenance` 调度，增加**每小时 `PRAGMA wal_checkpoint(TRUNCATE)`**（当前仅凌晨 3:00 做每日 checkpoint）；
  2. 健康检查增加 WAL 体积阈值告警（如 `-wal > 50 MB` 记 WARNING）。
- **收益**：读性能稳定、磁盘占用下降、避免 WAL 无限增长。
- **工作量**：小（半天）。
- **风险**：低。

#### P1-4 死代码与类型契约清理 ✅（本次已启动）
- **现状**：`backend/app/schemas/policy.py` 的 `PolicyResponse.attachment_urls` 只读 property 返回 `str`，与新契约 `List[str]` 语义冲突（`PolicyResponse` 实为死代码，仅测试引用）。
- **方案**：删除该死属性并同步清理测试；后续排查同类「同名不同型」遗留。
- **收益**：消除未来误用风险，类型契约一致（服务于「前后端 100% 对齐」）。
- **工作量**：小（已执行）。
- **风险**：低。

### 🟡 P2 · 短期（1–2 月）

#### P2-1 索引精简与数据库瘦身
- **现状**：506 索引 / 127 表，DBA 视角明显过载。
- **方案**：导出索引使用统计（`PRAGMA index_list` + 查询计划），合并/删除低频或冗余索引（尤其复合索引重复前缀）；每季度执行一次。
- **收益**：写放大下降、DB 体积收缩、启动更快。
- **工作量**：中。**风险**：中（须逐个验证查询计划，避免拖慢热点查询）。

#### P2-2 附件体系完善
- **现状**：多附件已可保存，但仍缺全局能力。
- **方案**：
  1. **内容去重**（同 hash 文件复用物理存储）；
  2. **孤立文件清理**（定期扫描 `uploads/`，回收无 DB 引用的文件——本次 QA 也发现验证残留文件）；
  3. 多附件**列表式预览/下载** UI（当前仅主文件可预览）；
  4. 上传校验**统一收口**（`/files/upload` 与 `/{id}/upload` 的类型/大小规则目前不完全一致）。
- **收益**：存储可控、体验完整、规则一致。
- **工作量**：中大（3–5 天）。**风险**：低。

#### P2-3 慢请求追踪与可观测性
- **现状**：已注册 `SlowRequestMiddleware`，但日志中**无慢请求记录**（阈值或级别未生效）。
- **方案**：明确慢请求阈值（如 > 200 ms）、输出结构化字段（path、耗时、SQL 次数），并对接审计日志；补充关键端点 P95 指标。
- **收益**：性能问题可主动发现而非被动投诉。
- **工作量**：小—中。**风险**：低。

#### P2-4 启动时间优化
- **现状**：启动约 8 秒（含路由加载 ~5 s、DB 自检、后台服务启动）。
- **方案**：重模块（报表/图表/导入导出）改为**首次调用时惰性加载**；后台调度器错峰启动。
- **收益**：启动体验提升（桌面端尤为明显）。
- **工作量**：中。**风险**：中（懒加载需保证线程安全）。

## 六、风险与注意事项

1. **并发瓶颈是架构级问题**：SQLite 单写者 + 单进程 ASGI，即使优化中间件，写密集场景仍有上限；若未来多用户并发显著上升，需评估 WAL 读写分离或迁移 PostgreSQL。
2. **改动须绑定回归**：P1-1/P1-2 触及所有请求链路，务必以现有 ~2300 后端用例为回归网，先小流量验证。
3. **索引精简不可激进**：506 个索引里可能有个别为特定统计口径服务，需以查询计划为依据逐个确认。
4. **Schema 精简（127 表）** 属长期治理，建议先做「新增表评审制」，避免继续膨胀。
5. **本次工作树含大量他人未提交改动**：推送仅限本次修复相关 commit，不得 `git add -A`。
